<objective>
Add a new Django management command `backfill_lco_observations` that takes an LCO proposal
code and backfills `tom_observations.models.ObservationRecord` rows from the LCO Observation
Portal, creating the non-sidereal `Target`s and `ObservationGroup`s it needs along the way.

Purpose: give an upcoming architectural exploration real LOOK observation data — completed
previous-semester records for terminal-state ground truth, and still-pending current-semester
records whose `scheduled_start`/`scheduled_end` will keep evolving through TOM's own
`updatestatus` — instead of invented fixtures. The command is also a plausible upstream
contribution to `tom_toolkit`, which today only creates records at submission time, so it stays
self-contained and generic rather than FOMO-campaign-specific.

Output: the command module, its Django `TestCase` suite with a fully mocked portal, a
pre-executed demo notebook, an operator runbook section, and the CLAUDE.md notebook-pairing
map entry.

**D-A — The new command sits ALONGSIDE the existing one; nothing existing is modified.**
A live check of the tree found `solsys_code/management/commands/backfill_lco_observation_records.py`
(365 lines) and `solsys_code/tests/test_backfill_lco_observation_records.py` (481 lines) already
present. They overlap in subject but not in contract: the existing command is coupled to a
`tom_targets.TargetList` campaign (required, prompts interactively when omitted), requires a
`--name-prefix`, skips rather than updates rows that already exist, and creates *sidereal* field
targets for unmatched requests. The new command is campaign-agnostic, updates in place,
handles observation groups, and only ever creates non-sidereal targets. Do NOT edit, rename,
deprecate or delete the existing command or its tests. Do NOT import its private helpers — the
new module is deliberately self-contained so it can be offered upstream, which makes the ~15-line
paging helper a deliberate duplicate. Add a short module docstring line in the NEW module
pointing at the older sibling and naming the contract difference, so the next reader is not
surprised by the pair.

**D-B — Scheduled times come from the observed block, via the facility, never hand-rolled HTTP.**
`GET /api/requestgroups/` is not guaranteed to embed observation blocks per request. Read an
embedded block list from the request payload when one is present, and otherwise fall back to
`LCOFacility().get_observation_status(observation_id)` — verified at
`tom_observations/facilities/ocs.py:1548-1575`, which reads `/api/requests/{id}/observations/`
with `_portal_headers()` and applies the "first COMPLETED block, else last PENDING block"
selection, returning `{'state', 'scheduled_start', 'scheduled_end'}`. That fallback is skipped
entirely under `--dry-run` and is best-effort: a failure is logged with the observation id and
counted, never fatal, and never rolls back an already-created record.

**D-C — Date filtering is on the RequestGroup `created` timestamp, filtered twice.**
Send `created_after` / `created_before` as server-side query parameters AND re-check the same
`request_group['created']` value client-side. Filtering both ends on the *same* quantity is what
makes the double filter safe; it exists because a portal that ignores an unrecognised parameter
would otherwise silently backfill the whole proposal. This mirrors the precedent in the sibling
command, which pre-filters on `name` server-side and then re-checks with a real
`str.startswith()`. Flags are named `--created-after` / `--created-before` (ISO-8601), not
`--start`/`--end`, because they filter submission time and not observing windows. There is no
`--semester` flag: a semester filter on this endpoint is unconfirmed, and the operator can
express a semester as a created-time window.

**D-D — Observation group naming.** `ObservationGroup.name` is `max_length=50`, verified at
`tom_observations/models.py:110`. Build the name as the RequestGroup name truncated so that a
` (<requestgroup id>)` suffix fits inside 50 characters, then `get_or_create` on it. The id
suffix makes the key deterministic, re-run stable, and collision-free across two RequestGroups
that share a display name. Only build a group when the RequestGroup carries more than one
request.

**D-E — Orbital-element mapping is the inverse of the library's own submission mapping.**
Verified at `tom_observations/facilities/ocs.py:843-850`. Portal wire key on the left, TOM
`Target` field on the right: `orbinc`→`inclination`, `longascnode`→`lng_asc_node`,
`argofperih`→`arg_of_perihelion`, `meandist`→`semimajor_axis`, `meananom`→`mean_anomaly`,
`dailymot`→`mean_daily_motion`, `epochofel`→`epoch_of_elements`, `epochofperih`→
`epoch_of_perihelion`; `perihdist`, `eccentricity` and `scheme` carry across unchanged. Accept
the alternate spellings `epoch_of_elements` / `epoch_of_perihelion` / `orbital_elements` if the
payload uses them, but prefer the wire names above. Validate completeness with
`REQUIRED_NON_SIDEREAL_FIELDS` plus `REQUIRED_NON_SIDEREAL_FIELDS_PER_SCHEME` imported from
`tom_targets.base_models` (schemes: `MPC_MINOR_PLANET`, `MPC_COMET`, `JPL_MAJOR_PLANET`).

**D-F — Target matching.** Match an existing target by name *or* alias through the library's own
`Target.matches.match_fuzzy_name(name)` manager (`tom_targets/base_models.py:163-181`,
matches across `target.names`, i.e. the name plus every alias). Only when that returns nothing
does the command build a new target.

**D-G — Scope fence.** This command must not import or reference the campaign-run model, the
calendar-event model, or the campaign reconciler module. Enforced by a negative gate in Task 1's
verify.

**D-H — No interactive prompts.** Unlike the sibling command, this one never calls `input()`;
it must be safe under cron and inside a notebook.
</planning_decisions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| LCO Observation Portal → command | Remote JSON crosses into the process; the portal is trusted-ish but the payload model is not guaranteed |
| command → FOMO database | Portal-derived values become persisted `Target`, `ObservationRecord` and `ObservationGroup` rows |
| operator shell → command | CLI arguments, including `--username`, chosen by whoever can run `manage.py` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-h1v-01 | Information disclosure | `backfill_lco_observations.py` stdout/stderr | high | mitigate | The portal API key reaches the process only through `facility._portal_headers()`; it is never interpolated into a message. Every failure line carries the observation id plus a short reason — never the headers, the request URL with credentials, or a raw response body. Task 1's action states this; the verifier should read the failure-path writes. |
