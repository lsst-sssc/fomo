## Questions for you (the likely misreadings)

### Q1. The allocation→observation handoff only happens after a person confirms a link
D4: *"When an observation links to an allocation's night, the allocation's event for that night
retires."* The retirement mechanics are built and tested (`allocation_projector.py`
`retired_nights()`, driven by a `CampaignRunObservation` receiver). But in production code the
**only** thing that creates a `CampaignRunObservation` is the staff "confirm record" action in
the attribution queue (`campaign_views.py` `_do_confirm_record()`, ~line 1422). The
exact-identity system-link path (`write_and_reconcile_campaign_run(observation_record=...)`,
`campaign_utils.py` ~line 1071) has no production caller — `load_telescope_runs` does not pass
one. Auto-attribution by similarity is out of scope by decision (Phase 28).

- [ ] Is "an allocation night retires only after staff confirm the observation belongs to that
      run" what you intended? Or did you expect some links (e.g. an LCO request submitted
      *from* a run, or a record whose proposal/window exactly matches) to be made automatically?

### Q2. A human-confirmed allocation night is *not* retired — both events stay on the calendar
Phase 35 CR-05 (accepted by you at UAT 2026-09-16): if a person has confirmed an allocation
night's companion row, linking a real observation to that night does **not** delete the
allocation event. The calendar then shows both the allocation night and the observation's
event. This deliberately narrows ROADMAP Phase 35 Success Criterion 3 / ALLOC-03 and D2's
"that event retires when a real observation links up".

- [ ] Still happy with "a human confirmation outranks automatic retirement", given it shows
      the night twice?

### Q3. Which real allocations ever get per-night events (and so can hand off)?
ALLOC-01 keeps Phase 26's rule: a queue-scheduled, class-wide or satellite run keeps **one
whole-window container event**, never per-night events. Per-night sunset→sunrise events (and
therefore per-night retirement) only exist for runs with a resolved site and a
classical/awarded window. Classical schedule lines normally have no `ObservationRecord` (D3).

- [ ] For the runs you actually care about (e.g. KEY2026B-004 on LCO, 3I monitoring), is it
      right that the allocation shows as one container and never hands off night by night?
      Or did D2/D4 mean queue allocations too?

### Q4. "Visibly grouped" (D1) = shared target name in the title + a pop-up link, nothing in the month grid
D1: *"Per-night blocks, visibly grouped … the `ObservationGroup` contributes identity (shared
title stem, series key, link back to the group)."* Built as:
- the title stem is the **target name**, e.g. `[O] TFN-1m0 11P`, `[X] 1m0 11P` (live DB) —
  so two different cadence groups on the same target share a stem;
- the group itself appears only when you open an event: "Observation series: *group name* —
  Night n of N — View record" (`event_form.html:148-156`, `observation_series_decoration`);
- real FKs `CalendarEventMeta.observation_record` / `.observation_group` carry the identity.

- [ ] Does that meet "visibly grouped"? Or did you expect grouping visible on the month view
      (group name/short key in the title, a shared colour, etc.)?

### Q5. "Running unattended on the real host" is built but not switched on
The milestone goal includes *"the whole pipeline running unattended on the real host"*. All the
code is done (SCHED-08/09/10, DISCOVER-01), but the audit lists as still outstanding on the real
host: run `python manage.py check_unattended`, fix what it reports, install the printed cron
line, and configure the heartbeat (runbook fresh-host steps 3–4).

- [ ] Close v2.4 now and treat the install as an operator task, or install first so the goal
      is true in practice when the milestone is tagged?

### Q6. Two of your Phase 34 UAT ideas don't appear to have landed
PROJECT.md says these were deferred "to Phase 37's vocabulary work", but no Phase 37
plan, summary or verification mentions them (`34-UAT.md` test 2 note):
1. failed/aborted records keeping their **last scheduled** window instead of the original
   request window (expired ones keep the original);
2. a clearer "not attempted" marker for `site_lookups` in `--dry-run` sweep output.

- [ ] Still wanted? If yes → capture as todos or a v2.5 item; they're not v2.4 blockers.

### Q7. PROJ-06 wording vs what's tested
PROJ-06 says titles "fit a month cell". The tested contract is "marker and telescope token both
within `title[:16]`"; the longest live title is 35 characters.

- [ ] Look at a busy month on the calendar: do titles fit well enough? If yes, reword PROJ-06
      to match the test; if not, it's a real gap.

## Per-decision checks

Each row: what was intended → what was built → where → a concrete thing to look at.

### D1 — One event per observation, grouped by cadence
- **Intent:** per-night blocks for a cadence group, one `CalendarEvent` per `ObservationRecord`;
  a run linked to the group inherits real nights, never a synthetic span.
- **Built:** PROJ-01/04/06. Projector `solsys_code/observation_projector.py`
  (`title_for()` :226, `series_group_for()` :261), keyed by `facility.get_observation_url()`.
- **Interpretation:** see Q4.
- [ ] Open the calendar on the 11P cadence (group `11P_1M0-cad-20260903-1004_dither`): one
      event per night, not one span; the pop-up says "Night n of N".

### D2 — Base layer owns events; campaigns annotate
- **Intent:** one writer per source; a linked run decorates, never creates, observation-backed
  events.
- **Built:** ANNOT-01/02, PROJ-05. Three namespaces with three sole writers (audit seam #1):
  `campaign_reconciler.py` (`RUN:`), `allocation_projector.py` (`ALLOC:`),
  `observation_projector.py` (facility URL). Campaign prefix/link is rendered at display time
  from `CalendarEventMeta.run` (`campaign_decoration()` in `calendar_display_extras.py`), never
  written into the event.
- **Interpretation:** see Q2.
- [ ] Take an attributed observation event, run a sweep
      (`python manage.py project_observation_calendar`), and confirm the campaign label is still
      shown and the sweep reports it `unchanged`.

### D3 — Classical schedule lines are allocations, with or without a campaign
- **Intent:** no synthetic `ObservationRecord`; the allocation is generic; sunset/sunrise
  per-night events for anyone who imports a schedule file.
- **Built:** ALLOC-01/02/04/05. `load_telescope_runs` now writes campaign-less `CampaignRun`s
  (`source=CLASSICAL`, collision-safe `source_identifier`), and `allocation_projector.py`
  projects `ALLOC:{pk}:{night}` events keyed by the **site-local** night. One-time
  `cutover_classical_allocations` converted the dev DB (56 `RUN:` → 0, 0 → 57 `ALLOC:`, no
  duplicates).
- [ ] Re-import a real schedule file (`load_telescope_runs`) twice: same nights, second run
      reports nothing changed; a Chilean and an Australian night land on the right local date.

### D4 — Narrowing is the handoff between layers
- **Intent:** allocations → per-night sunset/sunrise events; observations → block events that
  narrow window → placed → observed; a linked observation retires its allocation night.
- **Built:** PROJ-02 (stage rule `record_time_window`), ALLOC-03 (retire on link, restore on
  unlink). SCHED-06 proven on the real DB: records 4378332 (11P) and 4378046 (10P) narrowed
  queued → observed through the receiver alone.
- **Interpretation:** see Q1, Q2, Q3.
- [ ] Link a record to a classical run's night via the attribution queue: the allocation night
      disappears; unlink it: the night comes back; the observation event itself never changes.

### D5 — Event-driven trigger, sweep as backstop
- **Intent (note):** subscribe to TOM's `observation_change_state` hook.
- **Built, deliberately different:** spike 001-b showed that hook misses the schedule-only
  placement save, so TRIG-01 uses a FOMO-owned Django `post_save` receiver registered in
  `apps.ready()`; TRIG-03 sweep `project_observation_calendar` is the backstop.
- **Known residual (F-34-1):** `updatestatus` never re-saves terminal records, so events for
  records that went terminal before the 34-05 fix stay stale until a sweep runs — the
  unattended runner's sweep step covers this once installed (Q5).
- [ ] Agree that post_save instead of the TOM hook is the right reading of D5.

### Items the note left unresolved — how they were settled
- [ ] **Expired/failed nights: drop out or get marked?** → **Marked, never dropped** (PROJ-03:
      `[X]`-style marker on the window night). OK?
- [ ] **Where group identity lives** → real FKs on FOMO's `CalendarEventMeta`, not
      `tom_calendar` fields (PROJ-04). OK?
- [ ] **Is `tom_calendar` TOM-org maintained?** → yes (ships in tomtoolkit 3.0.1); upstreaming
      deferred as UPSTREAM-01 until the projector has proven itself here.

### Milestone-goal items beyond D1–D5
- [ ] **Unattended pipeline** (SCHED-08/09/10, DISCOVER-01) — `run_unattended` runs 5 steps
      under cron + `flock -n`, a failing step never aborts the tick, email on failure plus a
      heartbeat, admin-editable `WatchedProposal` list, no credential in logs. See Q5.
- [ ] **Public tallies** (TALLY-01/02) — log out, open a campaign: each run row and the

- [ ] **`run_status` stays a staff decision** (TALLY-03) — nothing sets it from linked records.
      Written only at `campaign_views.py` (staff decision view).
- [ ] **Unused awarded nights look unused** (UNUSED-01) — a past, never-observed allocation
      night is muted/dashed with `[U]`; the legend's `[U]` swatch filters to them.
- [ ] **One status vocabulary** (STATUS-01/02) — `solsys_code/status_vocabulary.py` is the only

- [ ] **Coverage gaps count every observation** (GAPB-01) — a campaign's gap analysis no
