## Questions for you (the likely misreadings)

### Q1. The allocation→observation handoff only happens after a person confirms a link
D4: *"When an observation links to an allocation's night, the allocation's event for that night
retires."* The retirement mechanics are built and tested (`allocation_projector.py`
`retired_nights()`, driven by a `CampaignRunObservation` receiver). But in production code the
**only** thing that creates a `CampaignRunObservation` is the staff "confirm record" action in
the attribution queue (`campaign_views.py` `_do_confirm_record()`, ~line 1422). The
exact-identity system-link path (`write_and_reconcile_campaign_run(observation_record=...)`,
`campaign_utils.py` ~line 1071) has no production caller — `load_telescope_runs` does not pass
one. Auto-attribution by similarity is out of scope by decision (Phase 28).

- [x] Is "an allocation night retires only after staff confirm the observation belongs to that
      run" what you intended? Or did you expect some links (e.g. an LCO request submitted
      *from* a run, or a record whose proposal/window exactly matches) to be made automatically?
      **Answered 2026-10-02: not what I meant — exact-identity matches should be linked
      automatically.** Evidence from the live DB: the "38 orphans awaiting attribution" are 19
      record+event pairs (the banner counts a record and its own projected event separately;
      confirming the record attributes the event too). 9 pairs are 10P records discovered today
      (`proposal=KEY2026B-004`, `target=10P`, inside run 69's window) that the scorer cannot
      single out because it never compares target — runs 69/71/73 all score 0.90 High, so no
      bulk checkbox. 10 pairs are Didymos `LCO2026A-003` field pointings inside run 1's window
      (run 1 is the only run with that proposal). All 182 existing links are staff-confirmed;
      74 of them to run 69 alone, and every discovery tick adds more. Decision: when a new
      record's proposal_code + target (or proposal unique within the campaign) + window match
      exactly ONE approved run, create the system link (`confirmed_by=None`, undoable) through
      the existing `write_and_reconcile_campaign_run(observation_record=...)` path; similarity
      matching stays manual. Routed as a requirement correction + inserted gap-closing phase
      (fix-routes table below). Side note for that phase: count a record and its event once in
      the banner.

### Q2. A human-confirmed allocation night is *not* retired — both events stay on the calendar
Phase 35 CR-05 (accepted by you at UAT 2026-09-16): if a person has confirmed an allocation
night's companion row, linking a real observation to that night does **not** delete the
allocation event. The calendar then shows both the allocation night and the observation's
event. This deliberately narrows ROADMAP Phase 35 Success Criterion 3 / ALLOC-03 and D2's
"that event retires when a real observation links up".

- [x] Still happy with "a human confirmation outranks automatic retirement", given it shows
      the night twice?
      **Answered 2026-10-06: yes, keep as built.** Revisit if a real doubled night appears on the
      calendar; none is known today. Captured as a todo at sign-off.

### Q3. Which real allocations ever get per-night events (and so can hand off)?
ALLOC-01 keeps Phase 26's rule: a queue-scheduled, class-wide or satellite run keeps **one
whole-window container event**, never per-night events. Per-night sunset→sunrise events (and
therefore per-night retirement) only exist for runs with a resolved site and a
classical/awarded window. Classical schedule lines normally have no `ObservationRecord` (D3).

- [x] For the runs you actually care about (e.g. KEY2026B-004 on LCO, 3I monitoring), is it
      right that the allocation shows as one container and never hands off night by night?
      Or did D2/D4 mean queue allocations too?
      **Answered 2026-10-06: yes, as built.** One whole-window container is right for
      KEY2026B-004, whose requests are mostly for the generic 1m0 / Sinistro class. Didymos run 1
      being per-night is also right: the proposal (LCO2026A-003) is for generic 2m0 MuSCAT, but
      the target's declination meant every request was `site: coj`, so in practice it is a
      single-site run on FTS. The recorded site, not the proposal's class, decides the calendar
      form — which is why F6's help text matters. Two things came out of this answer: F9 and
      F10 below.
