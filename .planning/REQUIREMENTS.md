# Requirements: Telescope Runs Calendar — v2.3 Automatic Run Sync & Outcome Propagation

**Defined:** 2026-09-01
**Core Value:** Robotically scheduled LCO/SOAR observations and their outcomes appear and update on the calendar and their campaign runs without an operator running anything.

## v1 Requirements

Requirements for this milestone. Each maps to roadmap phases.

### Schema & Identity Foundation

- [x] **SCHEMA-01**: A phase-time investigation spike settles whether `CampaignRun.campaign` becomes nullable (and how) so a routine, non-campaign LCO/Gemini queue observation can still get a persistent `CampaignRun` identity
- [x] **SCHEMA-02**: The spike settles a `source_identifier`-style field (or equivalent) plus its `UniqueConstraint` so each adapter's write-time identity key (LCO portal URL, Gemini observation ID, classical `(telescope, instrument, start_time)` tolerance match) maps cleanly onto `CampaignRun`, extending Phase 26's read-time identity-key findings to the write path
- [x] **SCHEMA-03**: The spike confirms whether the classical adapter's tolerance-windowed match is a sufficient write-time identity surface, or needs a facility-specific key of its own

### Adapter Consolidation

- [ ] **ADAPT-01**: `load_telescope_runs` creates or updates a `CampaignRun` instead of writing calendar events directly
- [ ] **ADAPT-02**: `sync_lco_observation_calendar` creates or updates a `CampaignRun` instead of writing calendar events directly, and automatically links the realising `ObservationRecord` via `CampaignRunObservation` at creation time (exact identity, not scored attribution)
- [ ] **ADAPT-03**: `sync_gemini_observation_calendar` creates or updates a `CampaignRun` instead of writing calendar events directly, and automatically links the realising `ObservationRecord` via `CampaignRunObservation` at creation time
- [ ] **ADAPT-04**: Each rewired adapter's own idempotency guarantee (no-churn on an unchanged re-sync) is verified against the new `CampaignRun` write path, not assumed to carry over from the old `CalendarEvent` write path
- [ ] **ADAPT-05**: The migration from an adapter's old direct-`CalendarEvent`-write path to its new `CampaignRun`-write path has an explicit, stated cutover sequencing that never produces a duplicate or orphaned calendar event during the transition window

### Outcome Propagation

- [ ] **OUTCOME-01**: An `ObservationRecord`'s terminal status updates its linked `CampaignRun.run_status` automatically, reading only confirmed `CampaignRunObservation` links — never a scored attribution candidate
- [ ] **OUTCOME-02**: A `CampaignRun` with zero confirmed observation links is left untouched by outcome propagation — it never fires on an unconfirmed candidate
- [ ] **OUTCOME-03**: A multi-record `CampaignRun`'s status is derived by an explicit, documented aggregation rule (any-success-wins-once-all-terminal) rather than a naive "worst status wins" that would let one failed observation regress an otherwise-successful run
- [ ] **OUTCOME-04**: Outcome propagation never overwrites a staff-set terminal status (`mark_cancelled`/`mark_weather_failure`) or a run a human has already advanced past `OBSERVED` into `REDUCED`/`PUBLISHED`

### Unattended Scheduling

- [x] **SCHED-07**: A phase-time investigation spike settles the scheduling mechanism (cron+flock vs. a task queue) against the real target deployment's constraints, including credential handling and overlap prevention
- [ ] **SCHED-08**: The three sync commands plus the reconciler run on a documented recurring schedule with no operator action, guarded against overlapping invocations
- [ ] **SCHED-09**: A failed unattended run is visible to an operator through two independent layers — in-command failure notification (reusing the existing `_notify_staff()` email idiom) and a heartbeat/dead-man's-switch that also catches the scheduler itself failing to invoke
- [ ] **SCHED-10**: No credential value (API keys, passwords) appears in any log line or notification generated by the unattended execution path

### Unattended Discovery

- [ ] **DISCOVER-01**: A configurable watch-list (e.g. a `WatchedProposal` admin-editable model) replaces the `backfill_lco_observation_records`-style per-invocation `--proposal`/name-prefix arguments, so discovery of robotically-scheduled observations runs unattended against every currently-watched proposal

### Status Vocabulary Unification (carried from v2.2)

- [ ] **STATUS-01**: One status vocabulary replaces the three parallel prefix maps (`_CLASSICAL_STATUS_PREFIX`, `_FAILURE_PREFIX_BY_STATUS`, `_RUN_STATUS_CALENDAR_PREFIX`), which today agree with `calendar_display_extras._TERMINAL_PREFIXES` only by convention
- [ ] **STATUS-02**: A general terminal-state classifier replaces v2.2's `status == 'COMPLETED'` check, once per-facility `get_terminal_observing_states()` differences are reconciled

### Provenance-Blind Gap Analysis (carried from v2.2)

- [ ] **GAPB-01**: `campaign_gap.claimed_dates()` counts every observation on the campaign calendar, not only those with a `CampaignRun`, so classical and queue time is no longer reported as unclaimed

### Unused Allocation (carried from v2.2)

- [ ] **UNUSED-01**: Awarded nights that were never scheduled or observed are visually distinct from realised nights, making unused allocation legible at a glance

### Window Narrowing UI (carried from v2.1, re-scoped)

- [ ] **SCHED-06**: A space-mission run's window visibly narrows in the staff UI as its linked `ObservationRecord`s are scheduled and observed, re-scoped against the v2.2 four-stage window pipeline (RECON-02..04) rather than its original pre-pipeline design

## Out of Scope

Explicitly excluded. Documented to prevent scope creep.

| Feature | Reason |
|---------|--------|
| ESO sync (SEED-001/002) | Operator's stated ask was LCO/SOAR specifically; ESO stays dormant on its own seeds until a future milestone |
| A task-queue scheduler (Celery/huey/APScheduler) | Research recommends cron+flock — no broker/worker infra buys anything for a single-server, few-jobs-an-hour deployment; revisit only if the target host's constraints (Phase-time spike) say otherwise |
| Per-campaign configurable outcome-aggregation strictness (e.g. "all nights must succeed" mode) | Real feature idea surfaced by research, but not blocking — a v2.3.x consideration once the default any-success-wins rule is proven against real data |
| Auto-attribution of orphan events/records to a CampaignRun by scored similarity | Would silently recreate the unconfirmed-merge risk Phase 28's `ATTRIB-03` structurally closed — outcome propagation and adapter linking must use exact identity or human-confirmed links only, never the attribution scorer |
| A full alerting/notification pipeline | Over-scoped versus the stated "visible to an operator" bar — email + a dead-man's-switch ping is sufficient |
