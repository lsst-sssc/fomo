<objective>
Close G-36-5. `Command.handle()` in `solsys_code/management/commands/check_unattended.py`
(lines 607-617) builds one `line` string per `CheckResult`, writes it unconditionally to
`self.stdout`, and then writes the identical string again to `self.stderr` whenever the status is
not `ok`. On a terminal -- and under any `2>&1` -- those two sinks are one destination, so every
warning and every failure renders twice, the second copy red because Django's `BaseCommand.__init__`
sets the standard-error wrapper's default style to its error style. The operator hit it during UAT
round 3 with exactly one non-`ok` check (`watched_proposals`, the D-08 empty-list warning), so
exactly one line doubled.

This is not a regression. `git blame` puts the whole emission block at `fc2e2bc`, the command's first
commit, and 36-04-PLAN.md:182 specified the dual-write in so many words. The design never considered
that the two streams can be one destination. The tests could not catch it either: `_run()` hands the
command two separate `io.StringIO` sinks, so the merge never happens, and three assertions pin the
same line in both captures -- the bug written down as the expectation.

Three things happen here. The MECHANISM is fixed first: each result line goes to exactly one stream,
chosen by its status, with standard output flushed before each standard-error write so a merged
destination still reads in order. The TESTS are fixed in the same task and before the fix is called
done -- a helper that merges both streams into one sink, an exactly-once assertion, a multi-failure
boundary case, and a routing test -- because the defect class is defined by a test the suite could
not previously express. The PAIRED DOC follows: the runbook's preflight step tells the operator which
stream carries what, and what a bare `>` redirect drops.

One piece of housekeeping rides along and goes FIRST, for a mechanical reason: the operator
hand-edited step 2 of "Setting it up on a fresh host" during UAT and that edit is sitting
uncommitted in the working tree of the same file Task 3 edits. `git add` stages whole files, so
committing it on its own before anything else touches that file is the only way both commits stay
honest.

Purpose: SC 5 -- an operator sets up or verifies the whole schedule from one runbook section without
reading source. A preflight that prints the same line twice in two colours makes a reader stop and
wonder what differs between the copies; it is the first command a fresh-host operator runs, and its
output is the whole basis for trusting the host. SCHED-10 is untouched by design and re-gated.

Output: an emission loop that writes each line once to one stream, a test module that can see this
class of defect at all, a runbook step that states the routing and the redirect an operator should
use, and the operator's own API-key wording committed cleanly.

**No tracer in the plan-shape sense; Task 2 is the thin end-to-end path.** This is gap closure
against a shipped command, so there is no unproven architecture to slice. Task 2 nonetheless runs the
whole path the gap lives on -- a non-`ok` `CheckResult` → the emission loop → one stream → a single
merged sink → an exactly-once assertion -- and proves it before any prose is written about it.

**Scope fence (hard).** This plan closes G-36-5 and nothing else. G-36-1, G-36-3 and G-36-4 are
already closed by plans 36-07, 36-06 and 36-08; their gates are re-run here purely as
did-not-break checks. See "Deferred (do not touch)" below.
