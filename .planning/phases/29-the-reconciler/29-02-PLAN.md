<objective>
Complete D-02: before minting a per-night event, the reconciler looks for an event already
attributed to this run for that night (a `load_telescope_runs`-created blank-`url` classical event
linked through `CalendarEventMeta.run` by Phase 28's attribution queue) and re-keys it in place to
`RUN:{run_pk}:{date}` instead of minting a second event for the same physical night. Then prove the
whole classical branch, and prove RECON-04's non-interference rule.

Purpose: D-02 is one of the two genuinely new mechanisms in this phase — no adopt implementation has
ever shipped, only the spike's measurement of it. It is what gives every classical night one stable
uniform key identity and closes the `event.telescope_label_meta.run`-always-unset gap WR-03
(`27-REVIEW.md`) deferred to this phase.

Output: `_adopted_event_for_night()` plus the adopt step in `_reconcile_classical_nights()`, and the
`TestClassicalStage1` / `TestAdoptAndRekey` / `TestQueueOwnershipDoesNotTouchRecordEvents` classes.
</objective>

Add `_adopted_event_for_night(run, night, site_zone) -> CalendarEvent | None` to
`campaign_reconciler.py`. It queries `CalendarEventMeta.objects.filter(run_id=run.pk)` with
`select_related('event')`, converts each candidate event's `start_time` into `site_zone` (a
`ZoneInfo` built once per run from `run.site.timezone`, not per night), takes `.date()`, and returns
the first event whose site-local date equals `night`. Order the queryset by `event__start_time` so
the pick is deterministic when two candidates somehow share a night. Return None when nothing
matches.

Resolve RESEARCH.md Assumption A3 explicitly in the docstring: match on `CalendarEventMeta.run_id`
plus the site-local night **only** — do NOT add the `event__telescope=run.telescope_instrument`
filter the research sketch showed. The companion FK is already an explicit human-confirmed
attribution statement written by Phase 28's queue; adding a free-text telescope comparison on top of
it can only cause a miss (a `CampaignRun.telescope_instrument` string like `FTN/MuSCAT3` need not
equal a `load_telescope_runs` `telescope` value like `FTN`), and a miss silently contradicts D-02 by
falling through to minting a duplicate event for a night that already has one.

Wire it into `_reconcile_classical_nights()` so the per-night resolution order is: (1) an existing
event at `run_night_url(run, night)`; (2) failing that, `_adopted_event_for_night(...)`; (3) failing
both, mint. Both (1) and (2) go through `_may_write()` before any write — the ownership rule stays
the first condition in the write path. When (2) matches, call
`update_calendar_event_key_and_fields(event, run_night_url(run, night), fields)` with the
existing-event field set from plan 29-01 (`title`, `description`, `target_list` only — never

same candidate and report through `preview_calendar_event_action()` with the merged url+fields, so a
dry-run count of an about-to-be-adopted night reports `updated`, not `created`.

Document in the function docstring why re-keying is safe for the other writer:
`load_telescope_runs` looks up by `(telescope, instrument, start_time ± 5 min)` and never reads or
writes `url`, so moving the url does not break its own idempotent lookup — this is exactly the
asymmetry D-02 cites as the reason adopt was chosen for classical runs while gap-fill was chosen for
queue runs. Also record the accepted consequence carried over from plan 29-01: `title` and
`description` on an adopted night alternate between the two writers on re-ingest.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| adopt query -> existing `CalendarEvent` rows | The adopt step is the only path where the reconciler writes a row it did not create, so it crosses from "our namespace" into another writer's rows |
| `CalendarEventMeta.run` (staff-confirmed attribution) -> write authority | A Phase 28 confirmation is what grants the reconciler permission to re-key a classical event |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-05 | Tampering | `_adopted_event_for_night` -> re-key write | mitigate | The candidate set is `CalendarEventMeta.objects.filter(run_id=run.pk)` — an event with no companion row, or one whose `run` is unset or points elsewhere, is structurally outside the query; `_may_write()` is still applied before the write as defence in depth |
| T-29-06 | Tampering | Re-key moving `start_time` off `load_telescope_runs`' ±5-minute lookup key, causing a duplicate row on the next ingest | mitigate | The existing-event field set excludes `start_time`/`end_time`/`telescope` (locked in plan 29-01, asserted by `TestAdoptAndRekey`) |
| T-29-07 | Tampering | Reconciler overwriting an `ObservationRecord`-derived event, destroying the run-vs-realisation distinction | mitigate | Queue runs take the container branch only; `TestQueueOwnershipDoesNotTouchRecordEvents` asserts `modified` is unchanged on the record-derived row after two reconcile passes |
| T-29-SC | Tampering | npm/pip/cargo installs | accept | No packages installed in this phase; no legitimacy audit applies |
