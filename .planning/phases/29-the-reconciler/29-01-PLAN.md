complete `solsys_code/campaign_reconciler.py` module (D-03's single shared per-run function with

Key builders (per 26-DECISION.md's locked scheme, cited in the docstrings):
- `run_container_url(run)` returns `f'RUN:{run.pk}'` — the bare whole-window container key used by
  the queue, class-wide and satellite branches.
- `run_night_url(run, night)` returns `f'RUN:{run.pk}:{night.isoformat()}'` — **always
  date-bearing, including for a single-night classical run.** This is a deliberate divergence from
  the ported `_project_calendar_event()` code, which used the bare key when `n_nights == 1`:
  26-DECISION.md ("Criterion 3 / SPIKE-03") locks the classical form as `RUN:{run_pk}:{date}` and
  the bare form as the queue/container family, so the key form must unambiguously say which family
  an event belongs to. `{date}` is the site-local observing night; `sun_event()`'s sunset for
  `night` has that same site-local date, which Task 3 of plan 29-02 asserts rather than assumes.
- `owned_events(run)` returns
  `CalendarEvent.objects.filter(Q(url=run_container_url(run)) | Q(url__startswith=run_container_url(run) + ':'))`.
  The trailing colon is required — without it run pk=3 also matches run pk=34's events.

Title/description builders:
- `event_title(run)` — `f'{run.campaign.name}: {run.telescope_instrument}'`, with
  `f' (window {run.window_start}..{run.window_end})'` appended when `window_start != window_end`,
  and the `RUN_STATUS_CALENDAR_PREFIX` value plus one space prepended when `run.run_status` is a key
  of that dict. The resulting string must be byte-identical to what `campaign_views` produced for a
  cancelled/weathered run (prefix, space, base, optional window suffix) so
  `calendar_display_extras`'s terminal-prefix ring keeps applying.
- `event_description(run)` — `run.observation_details`, with
  `f'\nRun status: {run.get_run_status_display()}'` appended when the status prefix applies.

`_skip_reason(run) -> str | None` — the stage-0 guard, evaluated in this order, returning the first
match: `'not approved'` when `run.approval_status != CampaignRun.ApprovalStatus.APPROVED`;
`'missing telescope/instrument'` when `run.telescope_instrument` is blank; `'TBD window'` when
either `window_start` or `window_end` is unset; `'unresolved site'` when `run.site` is None and
`run.telescope_class` is blank. Otherwise None. These reason strings are D-05's itemized skip
vocabulary. This guard preserves today's exact "no event yet" cases from
`_project_calendar_event()`, plus the new approval gate (an unapproved web submission must never
reach the calendar).

`_may_write(event, run) -> bool` — RECON-05's ownership rule, and the **first** condition checked in
every write path. Returns True when `event` is None. Otherwise look up
`CalendarEventMeta.objects.filter(event=event).first()`: when a companion row exists and its
`run_id` is set, return `run_id == run.pk`; when there is no companion row or its `run` is unset,
return True only when the event's `url` is in this run's `RUN:` namespace (equal to
`run_container_url(run)` or starting with that plus a colon). Everything else returns False — a
hand-created entry, a conference, a proposal deadline or an un-attributed sync-command event is
never created, modified or deleted.

`_link_event_to_run(event, run)` — `CalendarEventMeta.objects.get_or_create(event=event)`, then set
`run` and save with `update_fields=['run']` only when `meta.run_id != run.pk`. Never writes
`is_verified`, `confirmed_by` or `confirmed_at` — an adopted row's telescope-label verification
history and Phase 28 attribution audit must survive untouched. This is the writer WR-03
(`27-REVIEW.md`) deferred to this phase.

`_reconcile_container(run, *, dry_run) -> ReconcileResult` — the whole-window branch shared by
queue-scheduled, class-wide and satellite runs (RECON-02 queue half, RECON-03). Port
`_project_calendar_event()`'s satellite date math verbatim: `start_time` is `window_start` combined
with midnight UTC, `end_time` is `window_end` combined with 23:59 UTC. Field set on both create and
update: `title`, `description`, `target_list` (= `run.campaign`), `telescope`
(= `run.telescope_instrument`), `start_time`, `end_time` — the container is the only writer of the
bare `RUN:{pk}` key, so it is authoritative for every field, and its span must track window edits
(26-DECISION.md measured exactly this: only start/end changed, `updated=1`, key stable). Resolve the
existing event with `CalendarEvent.objects.filter(url=...).first()`, apply `_may_write()`; on False
return `ReconcileResult(blocked=1)` and `logger.warning` the event pk and run pk. Under `dry_run`
return the count implied by `preview_calendar_event_action()` and write nothing (no event, no
companion row). Otherwise call `insert_or_create_calendar_event({'url': ...}, fields=...)` when no
event exists and `update_calendar_event_key_and_fields(existing, url, fields)` when one does, then
`_link_event_to_run()`.

`_reconcile_classical_nights(run, *, dry_run) -> ReconcileResult` — the per-night branch (RECON-02
classical half). Port `_project_calendar_event()`'s ground loop: `n_nights =
(run.window_end - run.window_start).days + 1`, iterate `night = window_start + timedelta(days=i)`,
call `sun_event(run.site, night, kind='sun')` (never `kind='dark'`), and set `start_time`/`end_time`
from the returned sunset/sunrise via `.to_datetime(timezone=dt_timezone.utc).replace(microsecond=0)`.
**Do not** reproduce the analog's `try/except ValueError: logger.debug(...); raise` wrapper — per
D-06 the `ValueError` propagates uncaught out of `reconcile_run()` and is caught only by the batch
loop (29-03) or the staff-action call site (29-04), each of which already has its own differentiated
handling. Key each night with `run_night_url(run, night)`.

Field authority for the per-night branch, which differs deliberately from the container branch and
must be documented in the function docstring: on **create**, write `title`, `description`,
`target_list`, `telescope`, `start_time`, `end_time`; on **update of an event that already exists**,
write only `title`, `description`, `target_list`. `start_time`, `end_time` and `telescope` are never
rewritten after creation, for two reasons — (a) a night adopted from `load_telescope_runs` (plan
29-02's D-02 step) carries that command's file-derived BoN/EoN window, which is more precise than
the reconciler's coarse sunset-to-sunrise span and must not be overwritten; (b)
`load_telescope_runs` keys its own idempotent lookup on `(telescope, instrument, start_time ± 5
min)`, so moving `start_time` off the value it keys on would make its next re-ingest create a second
event for the same night. Refreshing `title`/`description` is required so a `mark_cancelled` /
`mark_weather_failure` decision still reaches this run's events, exactly as `_set_run_status()` does
today. Note in the docstring the accepted consequence: for an adopted night, `title`/`description`
alternate between this module and `load_telescope_runs` on re-ingest — key stability, not field-write
exclusivity, is what D-02's churn analysis guaranteed.

`reconcile_run(run, *, dry_run=False) -> ReconcileResult` — the public D-03 entry point. Return
`ReconcileResult(skipped_reason=_skip_reason(run))` immediately when that guard fires. Otherwise
dispatch, in this order: `run.telescope_class` non-blank -> container (RECON-03, and the SPACE class
shares this branch since the whole-window math is identical — resolving RESEARCH.md Assumption A2 in
favour of one branch, not two); `run.site` is not None and
`run.site.observations_type == Observatory.SATELLITE_OBSTYPE` -> container (the ported satellite
case); `run.source in QUEUE_SOURCES` -> container (RECON-02 queue half, D-07: branch purely on
`source`, never on a text heuristic over `telescope_instrument`/`site_raw`); otherwise -> classical
per-night. Docstring must state that it is safe to call redundantly (idempotent) as
defence-in-depth for the staff-action call sites, per the threat model below.
