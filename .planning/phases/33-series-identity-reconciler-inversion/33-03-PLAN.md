<parallel_safety>
Plans 33-01 and 33-03 share wave 1 with no `depends_on` edge, and both run `python manage.py test`
and `pre-commit run ruff --all-files`; this plan additionally runs `python manage.py migrate`.
Running them concurrently is safe — verified, not assumed:

- `src/fomo/settings.py:126-131` declares `DATABASES['default']` with no `TEST` key. Django's
  SQLite backend resolves the test database as `TEST['NAME'] or ':memory:'` and then opens
  `file:memorydb_default?mode=memory&cache=shared`, an in-process in-memory database
  (`django/db/backends/sqlite3/creation.py`, `_get_test_db_name`). Two concurrent
  `manage.py test` processes therefore never share a database. This plan's Task 3
  `MigrationExecutor` test builds and migrates that in-memory database, not the developer one.
- `.planning/config.json` sets `workflow.use_worktrees: true`, so same-wave plans execute in
  separate git worktrees: ruff's `--fix` writes and the generated migration file stay inside this
  plan's own checkout. The shared `~/.cache/pre-commit` store is read-only once hook environments
  are installed, and pre-commit serialises store installation behind its own `.lock` file.
- 33-01's and 33-03's `files_modified` lists are disjoint. `manage.py migrate` in Task 1 is the
  only write to the developer database anywhere in wave 1 — no task in 33-01 opens it.

Task 1's `manage.py migrate` therefore has no concurrent writer, but it does depend on the
developer database being present, which a fresh worktree cannot assume; see Task 1's
`<precondition>`. Criterion 1's load-bearing proof is Task 3's `MigrationExecutor` test against
the in-memory database, which holds regardless of what the developer database contains.
</parallel_safety>
