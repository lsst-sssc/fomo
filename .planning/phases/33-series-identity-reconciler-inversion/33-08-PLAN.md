The plan-checker flagged `estimate.tokens: 130000` at `confidence: low`, with Task 3 spanning two
notebook re-executions plus four runbook edits, and offered a split into a later wave. Deliberately
not split, for two reasons.

the FINAL code: Task 1's night derivation, Task 2's two new counters, and the earlier-wave display
changes from plans 33-06 (wave 1) and 33-07 (wave 2) all show up in their committed output. A
separate later plan would either re-execute them a second time — paying the most expensive part
of Task 3 twice — or commit output produced before the prose describing it was written.

Second, CLAUDE.md's paired-docs rule binds the notebooks and the affected `docs/runbooks/` page to
the plan whose tasks change the documented behaviour, and that is this plan: Tasks 1 and 2 are
what make both artifacts stale. Moving them out would leave a behaviour-changing plan with no
paired-docs coverage, which is the exact breach the rule exists to prevent (breach history: Phase
5, Phase 6, quick task `260726-kdp`).

If execution does hit context pressure, the natural seam is the four
`docs/runbooks/telescope_runs_calendar.rst` edits: they depend only on Tasks 1 and 2 having
landed, not on the notebook output, so they can be lifted into a `33-09` wave-4 gap-closure plan
carrying the same paired-docs obligation without touching Tasks 1 or 2. The checkpoint added at
the head of this plan costs near-zero execution tokens, so the estimate is unchanged by it.

## Flagged assumptions

- **The noon anchor supersedes 26-DECISION.md D-10's derivation for the event-to-night mapping.**
  That milestone-era comparison called the measured event `pk=54` (`2026-07-08T14:08:19Z`, Sydney)
  a 2026-07-09 night, using a plain site-local `.date()`. Under the anchor `sun_event()` itself
  uses, 00:08 local on 2026-07-09 belongs to the night that began at sunset on 2026-07-08. This
  plan treats the noon anchor as correct and D-10's `.date()` as the defect CR-02 reports; the
  forward mapping (`run.window_start + timedelta(days=i)` to a url) is untouched, and Task 1's
  re-homed test carries the citation. This assumption is no longer left to the plan: the
  `checkpoint:decision` at the head of `<tasks>` puts both readings to the operator with their
  evidence before Task 1 runs, and `keep-d10` is a real answer there, not a formality.
- **PROJ-04's `ordering` edge is still open and is deliberately not pre-empted here.** The
  abstained backstop truth about `observation_group` reverse-manager iteration order
  (33-VERIFICATION.md `insufficient_spec_items`, mirrored as 33-UAT.md test 3) is an operator
  decision for `/gsd-verify-work 33`: either a held-out/property-based test is added before Phase
  34's projector starts writing those links, or the absence evidence is accepted. No plan in this
  gap-closure run authors a predicate for it, and none of this run's changes reads
  `group.calendar_event_metas`.
- **Detach, not delete, for a superseded `RUN:` entry.** The review's suggested CR-03 test asserts
  "exactly one event remains for that night". This plan asserts exactly one *attributed* entry
  remains, because deleting the reconciler's own superseded event would contradict the
  user-directed rule recorded at 29-REVIEW.md CR-01 ("DETACH, not delete or flag-only"). The
  detached entry stays on the calendar as an un-attributed row and is offered by
  `orphan_calendar_events()` for a human to discard — visible and reversible rather than silently
  destroyed.
- **A blocked night keeps its url in the active set.** Only skipped nights drop out. The
  companion-row `run_id` filter inside `unlink_event_from_run()` already prevents a foreign
  attribution from being cleared, so this is belt-and-braces; Task 1's blocked-night test is what
  pins it.
