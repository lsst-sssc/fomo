Create `solsys_code/management/commands/cutover_classical_allocations.py`, modelled closely on the
existing one-time site-repair command.

Module docstring (the analog's style — explain why the command exists, what it deliberately does NOT
touch, and the dry-run contract):
- it converts the legacy blank-url classical calendar events, written by the classical loader before
  this phase, into allocation records plus `ALLOC:`-keyed events, so the calendar has exactly one
  writer per night;
- it needs no schedule file: every fact it uses is already in the events it is converting;
- it deliberately does NOT touch any event outside the blank-url classical set — a `RUN:`-keyed
  event is the reconciler's and the sweep's business, and a facility-url-keyed observation event is
  the observation projector's; it never infers a run's source from a site or a telescope name;
- it never deletes a calendar event: what it cannot explain, it reports;
- it is one-time but safe to re-run, and is documented as such in the runbook alongside the
  site-repair command.

Implementation:

1. Candidate set: `CalendarEvent.objects.filter(url='')`. Group by the `Source line:` value parsed
   out of each event's description — the line the classical loader wrote as the third line of the
   description. Parse it with a small helper that returns the text after the literal marker on the
   first description line that starts with it, or None.

2. Per group: run `parse_run_line()` and `get_site()` on the recovered line; derive the nights with
   `_iter_run_nights()` and the window from its first and last entries; build the sub-night times
   with `_window_token_to_time()`; compute the key with `_source_identifier()`. Reusing the ingest
   command's own helpers is what guarantees a converted run is indistinguishable from one a fresh
   import would have produced — do not re-derive any of them here.

3. Create or update the run with `insert_or_create_campaign_run({'source_identifier': key}, fields)`
   using the same field mapping the ingest command builds, with `campaign` taken from the group's
   events' `target_list` (they all carry the same one; when they disagree, that group is
   unexplainable — report it and leave it).

4. Re-key each event in the group: derive its night with `observing_night(event.start_time, ZoneInfo(site.timezone))`,
   build the allocation url, and call `update_calendar_event_key_and_fields(event, url, fields)` with
   the title and description the allocation projector would write and `target_list=run.campaign`.
   `start_time` and `end_time` are NOT in that field set, so the stored spans are kept byte-identical
   and no sun-event computation is needed. Then call `adopt_event_into_run(event, run)` to
   self-attribute it; a False return means a staff member attributed it elsewhere — report that
   event and leave its attribution alone.

5. D-18, the rule that makes this command safe to run: any group or event the command cannot explain
   is left completely untouched and recorded with its own reason under its own counter. The reasons
   to distinguish are: no parseable source line; an unknown or ambiguous telescope; a site with a
   blank timezone; a group whose events disagree on their campaign; a foreign attribution; and any
   other exception, recorded with `type(exc).__name__`. Print one line per unexplained event with
   its primary key, its title and its reason. When any such counter is non-zero, end `handle()` by
   raising `CommandError` with a message telling the operator to resolve the listed events in the
   admin and re-run — that is what produces the non-zero exit. Nothing is deleted on any path.

   The `CommandError` message must be self-contained: the total unexplained count and the reason
   breakdown, in the message itself, not only on the preceding stdout lines. A caller that drives
   this command through `call_command()` rather than a shell — 35-07 Task 3's notebook does exactly
   that — catches the exception and has only the message to display, and the operator reading that
   notebook must be able to see what was left alone without re-running anything. Say in the
   command's own docstring that the non-zero exit is operator-facing: it tells a human to resolve
   the listed events, and nothing in this repository gates a pipeline step, a CI step or another
   command on this command's exit code (35-RESEARCH.md Open Question 2, resolved).

6. `--dry-run`: read-only. Report the run-level action through `preview_campaign_run_action()` and
   the event-level action through `preview_calendar_event_action()`; create no run, re-key no event,
   write no attribution. State in the flag's help text that a dry run still exits non-zero when it
   finds an unexplainable event, because that is the condition the operator must clear before the
   real run.

7. Summary: lines processed, groups found, runs created/updated/unchanged, events re-keyed, events
   left unexplained broken down by reason, and — as the last line — the total number of `ALLOC:`-keyed
   calendar events now in the database. That final count is the number ROADMAP Success Criterion 5 is
   checked against, so name it in the line rather than leaving it a bare integer.
