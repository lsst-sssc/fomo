**CR-02:** an allocation night's boundaries are a function of three inputs --
`(run.night_start_utc, run.night_end_utc)`, `run.site`, and `night` -- because `_mint_fields()`
computes them via `sun_event(run.site, night, kind='sun')` (`allocation_projector.py:545`). The
`minted_sub_night_window` token plan 35-19 introduced records only the first. So once provenance is
recorded, changing `run.site` produces no comparison that can detect it: both set-field
comparisons are skipped (null against null), the both-set short-circuit is skipped, and the token
test finds `none|none == none|none` and returns False, astropy-free, forever. The reviewer
reproduced a ~15-hour error reported as `unchanged`, permanently, by moving a run from La Silla to
Siding Spring after one reconcile.

It is reachable by two ordinary staff actions: `CampaignRunAdmin` does not list `site` in
`readonly_fields`, so a staff member correcting a mis-resolved site lands here directly; and
`campaign_views._resolve_site()` rewrites `run.site` on an already-APPROVED run whenever the
current site is a tier-3 placeholder, then calls `reconcile_run(run)` -- and the approve branch
had already projected that run's nights against the placeholder's coordinates.

This is the same signature as iteration 7's CR-01 -- admin-reachable, silent, permanent stale data
-- one input over. The fix is to make the token carry every input the mint depended on, and to
treat a pre-release token as provenance unrecorded so existing rows re-resolve once through the
bounded branch 35-19 already built.

Purpose: restore ROADMAP SC-1 (the event an allocation shows is the span the run currently
declares) for a site correction as it already holds for a sub-night window change, and ALLOC-02's
site-local night promise on a corrected site.

Output: a versioned, site-carrying provenance token; a read predicate that tests the version rather
than mere presence; a column wide enough to hold it, proven by test; and a runbook and demo
notebook that describe what this round's two behaviour changes actually do.

The assumption-delta detector fired on this phase's scope (`detected: true`, signals:
`pluralization` on the terms "second" and "fallback"). CR-02 is exactly that seam, so the decision
is recorded here rather than left implicit.

**The noun that is now primary:** the **full mint-input identity** of a night's boundaries. Plan
35-19 modelled the recorded fact as "the sub-night pair". The review shows the real fact is
"(sub-night pair, site, night)" -- the sub-night pair is one component of an identity, not the
identity itself.

**Decision: `promote`.** The token becomes the mint-input identity; the sub-night pair is demoted
to one of its components. Rationale in one line: an `add-alongside` design (a second column
recording the site next to the existing one) would leave two half-facts that a third mint input
would have to be added alongside a third time, and the whole defect is that a partial record reads
as agreement -- one record of the whole identity cannot have that failure mode, a set of partial
records always can.

**What rides along with the promotion, and what does not:**

- The `night` component is NOT stored in the token. It is already carried by the event's own key
  (`ALLOC:{run.pk}:{night.isoformat()}`), and `_span_needs_remint(run, night, existing)` is only
  ever called with the night that key encodes -- so the night is a constant of the comparison, not
  a variable it can miss. State this in the token function's docstring; it is the one component
  whose absence is safe, and a reader must be able to tell that from the code rather than guess.
- The COLUMN NAME `minted_sub_night_window` is deliberately left unchanged. A `RenameField`
  migration plus both admin `readonly_fields` lists is real scope in a round the user has bounded
  to three findings, and the name is not load-bearing for correctness. The docstrings carry the
  real meaning instead.
- **What would force a later rename (the trigger, recorded so it is not rediscovered):** a THIRD
  mint input entering `_mint_fields()`'s boundary computation -- for example a per-run dark-window
  override or a site-elevation correction feeding `sun_event()`. At that point rename the column
  rather than widening the token a second time under a name that names one of three inputs.

**Invariant test (Task 2):** `TestMintInputInvariant` walks each recorded mint input, changes it,
and asserts the next reconcile re-mints -- the sub-night pair and the site today. Its class
docstring states the invariant in words and names the trigger above, so a future change that mints
from an unrecorded input has a failing-or-obviously-incomplete test adjacent to it. Stated honestly
as a limitation rather than overclaimed: this test cannot detect a NEW input nobody wrote a case
for; it can only make the omission visible to the next person editing `_mint_fields()`.
</assumption_delta_decision>
