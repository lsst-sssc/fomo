<design_rationale>
Read this before Task 1. It records the three places this plan's design differs from the fix text
printed in 35-REVIEW.md, so the executor does not "helpfully" revert to the snippet.

**1. The foreign-ownership arm in the review's snippet is unreachable here, and pretending
otherwise re-opens D-16's "third outcome" hole.** The review's snippet has an implicit else --
`not deletable_ids` with `confirmed_declined == 0` -- that falls through to `active_urls.add(url);
continue` with no counter and no log. In this module that is the forbidden third outcome (NF-01,
D-16): a candidate that is neither deleted, nor declined, nor counted foreign. It is also
unreachable: `project_allocation()`'s per-night loop already calls `_may_write(existing, run)` at
`allocation_projector.py:765` and `continue`s a foreign-owned night under `blocked` BEFORE the
re-mint branch is reached. `_may_write()` admits exactly three row states (no companion row, a
companion row whose `run` is unset, a companion row pointing at this run), and
`_clearable_declined_and_unattributed()` classifies all three as either deletable (no
`confirmed_by`) or declined (`confirmed_by` set). So the partition at this call site is TWO-way,
not four-way. Write it as a two-way partition, and say in a comment why the foreign arm is absent
rather than leaving a silent fall-through that a later reader will mistake for a bug.

**2. The shared guard alone does not close what CR-01's own headline claims.**
`_clearable_declined_and_unattributed()` declines on `confirmed_by` and nothing else
(`campaign_reconciler.py:504-510`). CR-01's headline says the re-mint "silently destroys
`confirmed_by`/`confirmed_at` AND the `observation_record` link", and the reviewer's probe 9
reproduced an `observation_record` + `is_verified=False` row being wiped. Applying the review's
snippet verbatim closes probe 8 and leaves probe 9 open -- a half-closed critical, which is how
this phase acquired iterations 7 and 8. So the guard here is the shared rule PLUS one re-mint-local
addition: a companion row carrying `observation_record`, `observation_group`, or `is_verified` set
False also declines. `is_verified` is the production-reachable half of that shape (it is the one
companion-row field NOT in either admin surface's `readonly_fields`, so staff can set it today),
and the two link fields are covered for the same reason at no extra cost.

**3. Decline, do not preserve.** The review offers "preserve the companion row across the
delete/create" as an alternative. Rejected, for three reasons worth writing down: (a) decline is
the rule all four sibling delete/detach paths in this module and `campaign_reconciler.py` already
apply, and CR-01's whole complaint is that this path diverges from them -- a different fifth rule
does not close that; (b) preserving would make the re-mint branch a new writer of `confirmed_by`
and `observation_record`, contradicting `CalendarEventMeta`'s own class docstring ("Both are
written only by the observation projector ... the same rule that already governs `run`"); (c) a
declined re-mint is VISIBLE -- a `detach_declined` counter the sweep summary prints and the
runbook explains, plus a warning naming the run, the night and the reason -- so the operator can
act, which is exactly the remedy the sibling paths already give. The residual is stated honestly
in `<verification>`: a declined night keeps a boundary the run no longer declares until a person
resolves it, and that is a smaller, louder failure than silently erasing a human stamp.

**4. CR-03 needs both halves, and they are not the same mechanism.** Reordering so
`_mint_fields()` runs before `existing.delete()` closes probe 6 (the raise happens before any
destruction). It does NOT close a raise from `insert_or_create_calendar_event()`,
`_link_event_to_run()` or `_record_sub_night_provenance()` -- those run after the delete by
necessity. `transaction.atomic()` around the group closes that half. Implement both; test both
separately, because a single test cannot tell which mechanism saved the night.
</design_rationale>
