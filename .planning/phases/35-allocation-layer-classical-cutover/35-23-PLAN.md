The assumption-delta detector fired on this phase's scope (`detected: true`, signals: `pluralization`
on "second" and "fallback"). Both signals come from the ROADMAP's round-history annotation prose, not
from a new second case entering the code, so for those two the decision is **`no-change`**: nothing
in "the second `gaps_found` pass" or "the half-null stored-boundary fallback" names a noun whose
identity model this round alters.

The ONE genuine identity question this round raises is real, and it is recorded here for the whole
round (plan 35-24 implements it; it is written down once so the two cannot drift apart).

**The noun:** what the provenance token's site component NAMES. Plan 35-21 modelled it as the site's
IDENTITY (`run.site_id`). The round-5 verifier reproduced a ~15-hour error, reported `unchanged`
forever, by correcting an `Observatory` row's `lat`/`lon`/`altitude`/`timezone` in place without
changing `run.site`: the boundaries are a function of the site's CONTENTS, and the token records only
which row supplied them.

**Decision: `promote`** -- the site component becomes the site's boundary-relevant contents
(`lat`, `lon`, `altitude`, `timezone`), carried as a short fingerprint alongside the existing
`site_id`. Rationale in one line: `site_id` answers "which row" when the question the comparison
actually asks is "which position", and a partial record that reads as agreement is precisely the
defect class CR-02 and this escalation share.

**What rides along, and what deliberately does not:**

- `site_id` is KEPT next to the fingerprint rather than replaced by it. It costs a handful of
  characters, it keeps the stored token legible in a log line and in the admin, and removing it would
  change the documented behaviour that a site SWAP re-mints. Accepted cost, stated rather than
  hidden: two distinct `Observatory` rows with byte-identical position and timezone would re-mint on
  a swap between them for no boundary reason. That re-mint is bounded (one per night, once) and
  passes through this plan's decline guards.
- The fingerprint is a HASH, not the raw values. A raw `(lat, lon, altitude, timezone)` rendering
  would run past any reasonable column width once an IANA name like `America/Santiago` is included;
  a fixed-width digest keeps the worst-case token bounded and testable against the field's own
  declared `max_length`.
- **The trigger that would force a further change, recorded so it is not rediscovered:** a boundary
  input that is neither the run's own fields nor the site's position -- for example a per-run
  dark-window override, or a leap-second/IERS-dependent term entering `night_bounds()`. At that
  point the token stops being "(run fields, site position)" and the column should be renamed rather
  than widened a third time under a name that names one of four inputs.
</assumption_delta_decision>
