## Summary

Reviewed the phase diff (`4e2d3f1..HEAD`) for the memoised `sun_event()`, the new crossing search, the
test-only settings block, the `migration` tag, the `--parallel` + coverage setup, and the docs. I also
traced callers (`campaign_gap.observable_dates`, `allocation_projector`) and checked the installed
coverage 7.13.5 and multiprocessing sources.

These parts hold up:
- **Memo key.** It includes lon, lat, altitude, timezone, date and threshold, the same four fields
  `allocation_projector._site_position_fingerprint` covers.
- **Copies.** `sun_event()` returns a `.copy()` of each cached `Time`.
- **Exceptions.** A call that raises is not cached.
- **Mocks.** No test outside `test_telescope_runs.py` patches `telescope_runs` internals, so no mock
  can leave fake values in the memo.
- **Threads.** `lru_cache` is thread-safe. Under a race the worst case is computing the same key
  twice.
- **IERS drift.** The 1-minute tolerance in `allocation_projector` / `calendar_utils` still covers
  IERS-driven drift.
- **Settings guard.** Django's `ManagementUtility` always reads the subcommand from `argv[1]`.
  `coverage run` rewrites `argv` so `argv[0]` is `manage.py`. Under spawn/forkserver,
  multiprocessing `spawn.prepare()` restores the parent `sys.argv` in each worker. No WSGI,
  runserver, shell or ipykernel process puts `test` at `argv[1]`.
- **Migration tag.** All six `MigrationExecutor` classes are tagged, and no other module uses
  `MigrationExecutor`.
- **Notebook.** The stored outputs match the code: the sun-event times moved by under 0.03 s from
  the pre-phase outputs, and the memo, copy and moved-site cells agree with the implementation.

The one real behaviour change is that the 10-minute coarse grid now misses short dark windows that the
1-minute grid found (WR-01). I confirmed this numerically. It conflicts with the gap analysis's
documented rule that any non-zero dark window counts as observable. The remaining items are
robustness and accuracy notes.

## Warnings

### WR-01: The 10-minute coarse grid misses dark/sun windows shorter than about 10 minutes, so the gap analysis now calls those dates "unknown"

**File:** `solsys_code/telescope_runs.py:231-242` (interaction with `solsys_code/campaign_gap.py:103-129`)

**Issue:** `_find_crossing()` finds a crossing only where two adjacent coarse samples change sign. If
the sun spends less than one coarse step below (or above) the threshold, both crossings fall in one
600 s interval and there is no sign change. The function then returns `[]` and `sun_event()` raises
`ValueError`. The code comment accepts this as "the earlier 1-minute grid had the same weakness at a
smaller scale". The scale grew tenfold, though, and the result feeds a documented rule:
`campaign_gap.observable_dates()` states "D-04: any non-zero dark window counts as observable -- no
minimum-duration threshold". It catches `ValueError` and puts the date in the "unknown" bucket.

Reproduced with the same sample grid both algorithms use, at lon 10.75 E, `Europe/Oslo`, 2026-05-20,
threshold -15 deg:

```
54.8627 N  dense(1-min) 2 crossings   coarse(10-min) 0   minutes below threshold: 5
54.8647 N  dense(1-min) 2 crossings   coarse(10-min) 0   minutes below threshold: 1
```

Before this phase those dark windows were observable. Now `observable_dates()` drops them, and with
no error. In practice the band is narrow (a few thousandths of a degree of minimum-altitude margin,
about 1-2 % of boundary-crossing dates per site-year). But `test_grazing_boundary_counts_match` checks
only two dates that were chosen because both algorithms agree on them. It never tests the
short-window case, so this regression is not pinned.

**Fix:** When the coarse scan finds a local extremum close to the threshold, refine around it before
deciding there is no crossing. This costs one extra transform, and only near the polar-day/night
boundary. For example, after `alt` is computed:

```python
# A local extremum of (alt - threshold) whose sign is not crossed between samples can still hide
# a double crossing inside one coarse step. Look closer at the nearest-to-threshold interior extremum.
interior = np.arange(1, alt.size - 1)
is_min = (alt[interior] <= alt[interior - 1]) & (alt[interior] <= alt[interior + 1])
is_max = (alt[interior] >= alt[interior - 1]) & (alt[interior] >= alt[interior + 1])
candidates = interior[(is_min & (alt[interior] > 0)) | (is_max & (alt[interior] < 0))]
if candidates.size:
    i = candidates[np.argmin(np.abs(alt[candidates]))]
    fine = offsets[i - 1] + np.arange(0, 2 * coarse_step_min * 60.0 + 1, 30.0)  # 30 s samples
    fine_alt = _solar_altitude(anchor + fine * u.s, location) - threshold_deg
    # ...splice any fine-grid sign changes into `brackets` (as offset pairs) before bisection
```

Then add an oracle case at 54.8627 N / 2026-05-20 / -15 deg that expects two crossings. Or, if the
limitation is kept on purpose, update the D-04 docstring in `campaign_gap.observable_dates()` to say
that dark windows shorter than about 10 minutes may be classed as unknown.

## Info

### IN-01: `concurrency = ["multiprocessing"]` turns off coverage's thread tracing

**File:** `pyproject.toml:126`

**Issue:** In coverage 7.x (`collector.py`, installed 7.13.5), `self.threading` is set only when
`"thread"` is in `concurrency` or `concurrency` is empty. Listing only `"multiprocessing"` means
`threading.settrace` is never installed, so code that runs in a non-main thread is recorded as
uncovered. Nothing in the unit suite runs app code in a thread today: there are no `async` views,
no `ThreadPoolExecutor`, and the `functional` live-server tests are not run under coverage. Any
future threaded code would read as 0 % covered, with no error.

**Fix:** `concurrency = ["multiprocessing", "thread"]`.

### IN-02: `n_steps` rounding can shorten the search window for non-default steps

**File:** `solsys_code/telescope_runs.py:236-238`

**Issue:** `n_steps = int(round(search_hours * 60 / coarse_step_min))` rounds to the nearest integer.
When the step does not divide the window, the last sample can fall short of
`anchor + search_hours`. For example, `coarse_step_min=26` gives 55 steps = 1430 min, leaving the
last 10 minutes unscanned. That contradicts the docstring's "closed [0, search_hours] window". The
defaults (24 h, 10 min) divide exactly, and every current caller uses them.

**Fix:** `n_steps = int(np.ceil(search_hours * 60 / coarse_step_min))`.

### IN-03: An exact-zero sample or midpoint breaks the sign tests (carried over from the old code)

**File:** `solsys_code/telescope_runs.py:240`, `:251-254`

**Issue:** `alt[:-1] * alt[1:] < 0` ignores an interval whose endpoint is exactly on the threshold,
so that crossing is lost. In the bisection, if `mid_val == 0` then `lo` moves to `mid` and `lo_val`
becomes 0. Every later `mid_val * lo_val < 0` is then false, so `lo` slides toward `hi`, giving an
error of up to half the 600 s bracket. This needs bit-exact float equality, so it is practically
unreachable. The old code had the same flaw on a 60 s scale.

**Fix:** Use `<= 0` for the bracket test with de-duplication, and stop narrowing once `mid_val == 0`
(for example `hi = np.where(mid_val == 0, mid, hi)`).

### IN-04: `TEST_CACHES` has no `LOCATION`, so the "private cache" it adds shares storage with the default test cache

**File:** `solsys_code/tests/test_campaign_views.py:47`, `:787-789`, `:873-875`; `src/fomo/settings.py:212`

**Issue:** `LocMemCache` keys its storage on `LOCATION` through the module-level `_caches` dict.
`TEST_CACHES` and the settings block both omit `LOCATION`, so they share the `''` store. Under the
test command, the newly added `@override_settings(CACHES=TEST_CACHES)` therefore isolates nothing
from other tests in the same worker. It only helps on a host whose `local_settings.py` overrides
`CACHES`, which is the case the comment names. The classes do `cache.clear()` in `setUp`, so nothing
fails today, but the "private cache" wording overstates what the decorator does.

**Fix:** Give it a distinct name, as `test_campaign_approval.ISOLATED_TEST_CACHES` already does:
`{'default': {'BACKEND': '...LocMemCache', 'LOCATION': 'campaign-views-tests'}}`.

### IN-05: The `ORACLE_DATES` comment overstates DST coverage

**File:** `solsys_code/tests/test_telescope_runs.py:633-635`

**Issue:** The comment reads "One date in each DST-change month for both zones". The tuple has April,
June and December only:
- It has no September date (Santiago starts DST) and no October date (Sydney starts DST).
- 2026-04-05 is the first night after both April transitions, not a night that spans one. The
  2026-04-04 night is the one that spans them.

The search itself does not depend on the timezone, only the anchor does, so the risk is low. But the
comment claims coverage the test does not have.

**Fix:** Add `date(2026, 4, 4)`, `date(2026, 9, 5)` and `date(2026, 10, 3)`, or reword the comment to
match the dates actually used.

### IN-06: `_cached_crossings()` duplicates `Observatory.to_earth_location()`'s construction

**File:** `solsys_code/telescope_runs.py:313`, `:350-351`

**Issue:** `sun_event()` calls `site.to_earth_location()` only for its validation and throws the
result away. `_cached_crossings()` then rebuilds the `EarthLocation` by hand, "exactly as
`Observatory.to_earth_location()` builds it". If the model method ever changes (for example, an
ellipsoid or geocentric construction), the two would silently diverge. They are currently protected
by `test_result_is_bit_identical_to_a_direct_search`, which compares against `site.to_earth_location()`.

**Fix:** Move the construction into one helper, for example a module-level
`Observatory.earth_location_from(lon, lat, altitude)` static method that both call.
