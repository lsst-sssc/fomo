### Pillar 6: Experience Design (N/A, unchanged)

No interaction pattern, loading state, error state, empty state or confirmation flow changed. The phase did change how fast one server-side path runs, and that is recorded as a performance observation, not a visual finding:

- `sun_event()` in `solsys_code/telescope_runs.py` now memoises its crossing search per process. Its consumers include `solsys_code/campaign_views.py` (the campaign gap-analysis view), `solsys_code/campaign_gap.py`, `solsys_code/calendar_utils.py`, `solsys_code/models.py`, `solsys_code/observation_projector.py` and `solsys_code/allocation_projector.py`.
- Per the 39.1-01 summary, the crossing search now costs 15 AltAz transforms per two-crossing night, down from 21, and about 173 samples instead of 1,461. A second identical call makes no transforms at all.
- Effect on the rendered page: the gap-analysis view's first load should be faster when it computes sun-event times. This was **not measured in a browser** in this audit, so it is stated as an expectation from the phase's own measurements, not as a verified user-facing timing.
- Accuracy: the 39.1-01 summary records a maximum change of 0.044 s against the pre-phase algorithm (limit 1.0 s; skycalc contract 120 s). Displayed times to the second may shift by at most about 0.05 s. The 39.1-01 summary notes that Phase 40 (WARN-05) will re-execute the three demo notebooks that print these times to the second; no rendered page was checked for this in this phase.

Test-only settings (`LocMemCache`, `MD5PasswordHasher`) apply only under `manage.py test`. The 39.1-02 and 39.1-03 summaries record that `manage.py shell` and the other non-test commands still use the file cache and PBKDF2 hasher, so no runtime UI behaviour is affected.
