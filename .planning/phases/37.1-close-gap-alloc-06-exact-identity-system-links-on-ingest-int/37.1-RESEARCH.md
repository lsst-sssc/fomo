### Locked Decisions

**Which records get linked, and when**

- **D-01: Every unlinked record an ingest command touches is a link candidate — created, updated and unchanged alike.** `sweep_proposal()` re-reads every request of a watched proposal on every tick, so this covers the 19 record+event pairs already on the live DB (they link on the first tick after deploy) and the common case where staff create the run *after* discovery found the records (runs 69–75 were created 2026-10-01 for records discovered 2026-09-29). "Newly ingested" in ALLOC-06 is satisfied because the sweep is the ingest path; the rule is not restricted to the `created` branch. Idempotence (success criterion 6) comes from the `get_or_create(observation_record=...)` contract — a second pass finds the existing row and writes nothing, so `confirmed_at` never churns.
- **D-02: `backfill_lco_observation_records` also links existing unlinked records it re-encounters.** Today that command `continue`s on an already-existing record before doing anything else (`skipped_existing`); the link attempt must happen for those too, so re-running it over `LCO2026A-003` links the 10 live Didymos field-pointing pairs. Its `already existed` count stays; a system-links count is added.
- **D-03: The record's status is irrelevant to linking.** An expired, cancelled or failed request that exactly matches the run is still that run's attempt: the public tally counts it under `[X]`/`[F]` (37 D-11), and 35 D-05 already means a never-placed record retires no night. Identity and outcome stay separate.
- **D-04: Reporting — a count in the summary line plus one stdout line per link.** The sweep summary gains `system links: N` (dry run: `would link: N`), which flows unchanged into `WatchedProposal.last_run_summary` and the unattended `step discovery:` log line. Each link (or would-be link under `--dry-run`) also writes one stdout line naming record → run and the match basis (D-11), so a dry run shows exactly which pairs would link. `--dry-run` writes no link (T-kpy-01 discipline: reads only).

**What staff see, and what undo means**

- **D-05: A system link renders as "System (exact match)" in the Confirmed table's existing "Confirmed by" column** (`campaign_tables.AttributionConfirmedTable.confirmed_by`, where `confirmed_by=None` is blank today). No new model field, no new column; the same rendering is used wherever else `confirmed_by` is shown for a link (e.g. the calendar pop-up's attributed-run block, if it names the confirmer). `confirmed_by=None` *is* the provenance — the contract `allocation_projector.py:958` and `campaign_utils.py:1050` already rely on.
- **D-06: Undo of a system link is the existing staff undo, unchanged.** `AttributionDecisionView._undo_confirmation()` deletes the `CampaignRunObservation` row and writes an `ObservationRecordDismissal` for the pair (28 D-13). That dismissal is exactly what stops the next discovery tick re-linking the pair (D-09), and the matcher already excludes dismissed runs, so the record may become a zero-candidate orphan — accepted. The 35 D-11 `post_delete` receiver restores the allocation night (success criterion 4). The default undo reason text is reused.
- **D-07: The match basis ("proposal + target + window" vs "proposal unique within campaign + window") is named in the per-link log line only.** Nothing new is stored on the row.
- **D-08: A failed link write for one record is skipped and counted, never a step failure.** If the write raises (e.g. `IntegrityError` because staff linked the record to another run between the sweep's read and its write), the record keeps whatever state it has, a `links skipped: N` counter and a stderr line record it, and the discovery step is not marked failed — a lost race is not an operator-visible failure (Phase 36 D-01..D-03 per-step / per-proposal isolation). Each link write runs in its own `transaction.atomic()` savepoint, as `_do_confirm_record()` does, so a caught `IntegrityError` cannot poison the sweep's outer transaction or a test transaction.

**Counting a record and its event once**

- **D-09: A record-backed calendar event is never an event-side orphan.** `campaign_attribution.orphan_calendar_events()` excludes any event whose `CalendarEventMeta` carries `observation_record` (set by the observation projector, Phase 33/34). Its attribution is worked only through its record — confirming or system-linking the record attributes the event via 35 D-08. Consequences, all by construction: the "Calendar events awaiting attribution" worklist lists only hand-entered / legacy / reconciler events; `orphans_needing_attribution_count()` (the banner and the page sections) counts the pair once; `unattributable_orphan_count()` (the done-state "N orphans still have no matching run" copy) counts it once. The existing test `TestOrphanQuerysets.test_event_with_observation_record_but_no_run_is_still_included` (`solsys_code/tests/test_campaign_attribution.py:739`) asserts the old behaviour and must be inverted, not deleted. — **Reversibility:** reversible — one queryset filter and its tests.
- **D-10: Every count still comes from the shared helpers in `campaign_attribution.py`** — no inline `.count()` anywhere (success criterion 5; the silent-drift hazard `orphans_needing_attribution_count()`'s docstring names).

**Exact-match rules at the edges**

- **D-11: The match rule, in order.** Let *P* be the record's proposal code (`ObservationRecord.parameters['proposal']`, the flat key both backfill commands write), *T* its `target_id`, and *(s, e)* its window from `calendar_utils.record_time_window()` reduced to UTC dates (the placed block once scheduled, else the request window — the same derivation `campaign_attribution._record_window()` uses). Candidates are `CampaignRun` rows with `approval_status=APPROVED`, `proposal_code == P`, both `window_start` and `window_end` set, and `window_start <= s` and `e <= window_end` (inclusive containment, D-12).
  1. If exactly one candidate has `target_id == T` → link it (the 10P case: runs 69/71/73 share proposal and campaign and differ only by target).
  2. Else, if no candidate carries *T* and exactly one candidate sits in a campaign (`TargetList`) that *T* belongs to → link it (the Didymos field-pointing case: run 1 is the only `LCO2026A-003` run in the campaign the sidereal field targets were added to).
  3. Anything else — zero candidates, two or more by target, two or more by campaign, a candidate set with no target match and no campaign match — stays in the queue, untouched.
  A pair with an `ObservationRecordDismissal` row is never linked (success criterion 3), and a record that already has any `CampaignRunObservation` row is never touched.
- **D-12: "Window inside the run's" = containment, compared as dates, inclusive.** Both the record window's start date and end date fall within `[window_start, window_end]`. A request window that straddles the run's edge is left for a person. Dates, not site-local nights, so the rule also works for class-wide runs (`site=None`) where no observing night can be derived.
- **D-13: A run with no window (a TBD row, `window_start`/`window_end` null) is never a system-link candidate and never counts toward ambiguity.** It stays a scorer candidate in the queue as today.
- **D-14: Only `approval_status=APPROVED` runs count — for linking and for ambiguity.** Pending and rejected runs neither link nor block a link. `run_status` is ignored: a cancelled or weathered approved run still receives an exactly-matching record (same reasoning as D-03).
- **D-15: Target match takes precedence over the campaign fallback** (the ordering in D-11). The fallback applies only when no containing same-proposal run carries the record's target — it must not be reached in the 10P case, and it must be reached in the Didymos case.

## Summary

This phase adds no dependency and no model field. It is four small code changes plus paired docs: (1) a new peer module holding one exact-identity matcher and one system-link writer; (2) a call to it from `sweep_proposal()` and from `backfill_lco_observation_records` (including the already-existing-record branch the latter currently `continue`s past); (3) one `.exclude(...)` on `orphan_calendar_events()`; (4) a `render_confirmed_by()` on the Confirmed table. Everything downstream of the link row (night retirement, event adoption, undo, dismissal) already exists and was exercised in a throwaway probe this session: a plain `get_or_create` of the link row is enough, because the 35 D-11 `post_save` receiver does the re-projection.

Three things in CONTEXT.md need the planner's attention before tasks are written. **(a)** D-11 step 2 filters runs by window *before* judging whether the proposal is unique in the campaign; roadmap success criterion 2 says the proposal must be unique *in the campaign* for the fallback to fire. The live DB shows why this matters: campaign 8 (`KEY2026B-004_targets`, the sweep's own auto-collected list) holds seven same-proposal runs, so the roadmap reading never fires the fallback there, while the CONTEXT reading would fire it whenever exactly one of the seven windows happened to contain a record for a target that has no run (Open Question 1). **(b)** D-04 says the new count reaches "the unattended `step discovery:` log line"; it does not — that line is `swept: N, failed: M` only. The count reaches `WatchedProposal.last_run_summary` and, via the per-link stdout lines, the `discovery stdout:` INFO log lines (Pitfall 6). **(c)** django-tables2 never calls `render_<col>` for `None` values unless the column declares `empty_values=()`, so D-05 needs that on the column (Pitfall 4).

**Primary recommendation:** Build `solsys_code/campaign_system_links.py` with `find_exact_run(record)` (pure read, accepts an unsaved record so `--dry-run` can ask about a record that does not exist yet) and `attempt_system_link(record, *, dry_run, stdout, stderr)`; write the link with a bare `CampaignRunObservation.objects.get_or_create(...)` inside its own `transaction.atomic()` (extracted so `write_and_reconcile_campaign_run` calls the same helper); resolve Open Question 1 before planning.

### Pattern 1: The matcher is a pure read that accepts an unsaved record

**What:** `find_exact_run(record) -> SystemLinkMatch | None`, where `SystemLinkMatch` is a `NamedTuple(run, basis)`. It never writes. It must work for a record that does not exist yet, because the dry-run branch of `sweep_proposal()` and of the Didymos command has no saved record for a "would create" request. Guard every `record.pk`-dependent query on `record.pk is not None`, and guard the campaign step on `record.target is not None and record.target.pk is not None`.

**When to use:** Called by `attempt_system_link()` only. No view, no receiver imports it.

**Rules (D-11/D-13/D-14, with the Open Question 1 resolution applied to step 2):**

```python
# solsys_code/campaign_system_links.py  (skeleton; single quotes, Google docstrings per CLAUDE.md)
from typing import NamedTuple

from solsys_code.campaign_attribution import _record_window  # the one definition of a record's window dates
from solsys_code.models import CampaignRun, CampaignRunObservation, ObservationRecordDismissal

BASIS_TARGET = 'proposal + target + window'
BASIS_CAMPAIGN = 'proposal unique within campaign + window'


class SystemLinkMatch(NamedTuple):
    """The one approved run an observation record exactly matches, and why."""

    run: CampaignRun
    basis: str


def _proposal_code(record) -> str:
    """Trimmed ``parameters['proposal']``, or '' when absent / not a string."""
    parameters = record.parameters if isinstance(record.parameters, dict) else {}
    value = parameters.get('proposal')
    return value.strip() if isinstance(value, str) else ''


def find_exact_run(record) -> SystemLinkMatch | None:
    proposal = _proposal_code(record)
    if not proposal:          # PITFALL 1: runs default to proposal_code='' -- a blank must never match a blank
        return None
    if record.pk is not None and CampaignRunObservation.objects.filter(observation_record_id=record.pk).exists():
        return None
    start, end = _record_window(record)    # (None, None) on bad data; see Pitfall 3 about TypeError
    if start is None or end is None or end < start:
        return None
    ...
```

Candidate query (a NULL window never satisfies `__lte`/`__gte`, and the DB check constraint `campaign_run_window_start_end_null_together` keeps the two fields null together, so D-13 needs no extra clause) [VERIFIED: `solsys_code/models.py`, constraint name quoted in Code Examples]:

```python
candidates = list(
    CampaignRun.objects.filter(
        approval_status=CampaignRun.ApprovalStatus.APPROVED,
        proposal_code=proposal,
        window_start__lte=start,
        window_end__gte=end,
    )
)
```

Step 1: `by_target = [r for r in candidates if r.target_id is not None and r.target_id == record.target_id]`; exactly one → `SystemLinkMatch(run, BASIS_TARGET)`; two or more → return `None` (ambiguous; do not fall through to step 2).

Step 2 (only when `by_target` is empty), per the recommended reading of Open Question 1: collect `campaigns = set(record.target.targetlist_set.values_list('pk', flat=True))`; collect **all** approved, windowed, same-proposal runs in those campaigns **regardless of whether they contain the window**; if exactly one exists and it is in `candidates`, match it with `BASIS_CAMPAIGN`; otherwise `None`.

Last gate: if `ObservationRecordDismissal.objects.filter(observation_record_id=record.pk, run_id=match.run.pk).exists()` → `None`. The dismissal veto is applied to the *winner after* the pick, not as a pre-filter (Open Question 2).

### Pattern 2: `attempt_system_link` is the single entry point both commands call

**What:** One function that does find → (dry run: report) → (real: write in its own savepoint, count, report), returning a short outcome string. The two commands only increment counters from the returned outcome.

```python
LINKED, WOULD_LINK, NO_MATCH, SKIPPED = 'linked', 'would_link', 'none', 'skipped'

def attempt_system_link(record, *, dry_run: bool, stdout, stderr) -> str:
    try:
        match = find_exact_run(record)
    except Exception as exc:  # noqa: BLE001 -- one unreadable record must never stop a sweep
        stderr.write(f'System link check failed for observation_id={record.observation_id!r}: {type(exc).__name__}')
        return SKIPPED
    if match is None:
        return NO_MATCH
    if dry_run:
        stdout.write(f'Would system-link ObservationRecord observation_id={record.observation_id!r} '
                     f'to CampaignRun #{match.run.pk} ({match.basis}).')
        return WOULD_LINK
    try:
        created = create_system_link(record, match.run)   # own transaction.atomic() inside
    except Exception as exc:  # noqa: BLE001 -- D-08: a lost race is not an operator-visible failure
        stderr.write(f'Could not system-link observation_id={record.observation_id!r}: {type(exc).__name__}')
        return SKIPPED
    if not created:           # someone linked it first; get_or_create returned their row
        return NO_MATCH
    stdout.write(f'System-linked ObservationRecord observation_id={record.observation_id!r} '
                 f'to CampaignRun #{match.run.pk} ({match.basis}).')
    return LINKED
```

Only the exception class name goes to stderr/logs (the D-17 convention already used in `sweep_watched_rows()`), never `str(exc)`.

### Pattern 3: The link write is a bare `get_or_create`, extracted once

**What:** Add to `campaign_utils.py`:

```python
def create_system_link(record: ObservationRecord, run: CampaignRun) -> bool:
    """Create the exact-identity system link (confirmed_by left None). Returns True when a row was created."""
    with transaction.atomic():
        _link, created = CampaignRunObservation.objects.get_or_create(
            observation_record=record,
            defaults={'run': run, 'confirmed_at': timezone.now()},
        )
    return created
```

and make `write_and_reconcile_campaign_run(..., observation_record=...)` call it instead of its inline `get_or_create` (so there is exactly one definition of "a system link"). The 35 D-11 `post_save` receiver on `CampaignRunObservation` then re-projects the run; do not call `reconcile_run()` as well.

**Probe results (throwaway test module outside the repo, run through `python manage.py test`, this session):**

- `write_and_reconcile_campaign_run({'pk': run.pk}, {}, observation_record=rec)` on an existing approved queue run returned `action: unchanged`, left `source='lco_queue'` and `approval_status='approved'` untouched, created the link with `confirmed_by None` and a `confirmed_at`, and a second identical call produced no `confirmed_at` churn. So the CONTEXT discretion question is answered: it is safe, and the WEB-source guard is inert with empty `fields`.
- It also calls `reconcile_run(run)` after the receiver already ran: 79 queries vs 42 for the bare `get_or_create` on a per-night run (both retired the placed night: ALLOC events 3 → 2 → 1 across two links); 43 queries for a queue run (adoption confirmed: `CalendarEventMeta.run == run`, `confirmed_by` None).
- `get_or_create` on a record already linked to a *different* run returns `created=False` with that other run's row and raises nothing. Django's own `get_or_create` already absorbs the unique-constraint race, so the "write raises" branch of D-08 is rare; the real race outcome is `created=False`, which must not count as a system link.

### Anti-Patterns to Avoid

- **A second count:** any `.count()` on orphans outside `orphans_needing_attribution_count()` / `unattributable_orphan_count()` (D-10).
- **Linking from the `ObservationRecord` post_save receiver or from a view** (roadmap-locked).
- **Pre-filtering dismissed runs before picking the winner** (Open Question 2).
- **Calling `reconcile_run()` after the link** — the receiver already re-projects; a second pass doubles the work.
- **Using `_eligible_runs_for_record()` for the candidate set.** It admits `PENDING_REVIEW` runs and is the scorer's gate; the exact-identity rule is APPROVED-only (D-14). Reuse its *campaign-membership idea* (`record.target.targetlist_set`), not the function.

## Common Pitfalls

### Pitfall 1: A blank proposal code matches every run that has none
**What goes wrong:** `CampaignRun.proposal_code` defaults to `''` and `blank=True`; `ObservationRecord.parameters['proposal']` can be missing or `None` (`_build_parameters` stores `request_group.get('proposal')`). Filtering `proposal_code=proposal` with `proposal == ''` would match every run without a code. **Evidence:** 32 runs on the live DB have a blank `proposal_code` [VERIFIED: read-only sqlite query of `src/fomo_db.sqlite3`, `select count(*) ... where proposal_code=''` → 32].
**How to avoid:** return `None` immediately when the trimmed proposal is empty. Add a unit test with a record whose `parameters` is `{}` and a blank-code approved run containing the window.
**Warning signs:** a link whose basis line prints an empty proposal.

### Pitfall 2: The Didymos command's created record is stale after the status refresh
**What goes wrong:** `ObservationRecord.objects.create(...)` returns an in-memory instance with no `scheduled_start/end`; `facility.update_observation_status(observation_id)` loads and saves a *different* instance. Matching on the stale instance uses the request window rather than the placed block.
**How to avoid:** `record.refresh_from_db()` after the status-refresh attempt (also when it failed — harmless) and before `attempt_system_link()`. The existing test mocks `update_observation_status`, so a new test must make the mock write `scheduled_start/end` to the DB (as `test_created_record_triggers_status_refresh` already does) and assert the link was made against the refreshed window.

### Pitfall 3: `_record_window` degrades on `KeyError`/`ValueError` only
**What goes wrong:** `_record_window()` catches `(KeyError, ValueError)` [VERIFIED: `campaign_attribution.py:665-681`]. A record with `parameters=None` raises `TypeError`; the matcher runs for *every* record a sweep touches, including malformed ones, so one bad record would abort the sweep.
**How to avoid:** `attempt_system_link()` wraps `find_exact_run()` in a broad `except Exception` that reports the class name and returns `SKIPPED` (shown in Pattern 2). Existing tests create records with `parameters={}`; that path returns `(None, None)` and must yield "no match", not an error.

### Pitfall 4: `render_confirmed_by` is never called for `None`
**What goes wrong:** django-tables2 3.0.0 short-circuits before any `render_<col>` call: `if value in column.empty_values ...: return default` [VERIFIED: `django_tables2/rows.py:168-169`]. The Confirmed table's column is declared `confirmed_by = tables.Column(verbose_name='Confirmed by')` [VERIFIED: `campaign_tables.py:644`], so a system link would keep rendering the placeholder no matter what `render_confirmed_by` does. **How to avoid:** declare `tables.Column(empty_values=(), verbose_name='Confirmed by')` (the same idiom the file already uses at `:87`, `:564-569`, `:642`) and render `'System (exact match)'` only when `isinstance(record, CampaignRunObservation) and value is None`; keep today's placeholder for a `CalendarEventMeta` row with `confirmed_by None` (those are self-attributed `ALLOC:`/`RUN:` events and adopted record events, which are not system links). No template references `confirmed_by` [VERIFIED: `grep -rln "confirmed_by" --include=*.html .` returned nothing], so the table is the only display site.

### Pitfall 5: The queue-run adoption silently needs a resolvable site or class
**What goes wrong:** in the first probe a queue run with neither a site nor a `telescope_class` produced `reconcile ... skipped_reason='unresolved site'` and the record's event was *not* adopted (`event adopted into run: False`), because `reproject_allocation_if_dispatched()` returns early when `_skip_reason(run)` is not None. Live runs 69-75 carry `telescope_class='1m0'` [VERIFIED: read-only sqlite query] so they adopt; test fixtures must too.
**How to avoid:** every fixture run in the new tests sets `telescope_class='1m0'` (queue/container case) or a resolved `site` with `source='csv_import'` or `'classical_file'` (per-night case), plus `window_start/end` and `approval_status=APPROVED`.

### Pitfall 6: D-04's "`step discovery:` log line" claim is wrong as written
**What goes wrong:** `step_discovery()` returns `summary=f'swept: {rows_swept}, failed: {failed_count}'` (plus failing codes) [VERIFIED: `unattended.py` read this session], and the runbook shows `step discovery: ok | swept: 1, failed: 0`. The per-proposal summary string only reaches `WatchedProposal.last_run_summary`. The per-link stdout lines do reach the log: `step_discovery()` logs each captured stdout/stderr line at INFO as `discovery stdout: ...` / `discovery stderr: ...`.
**How to avoid:** do not change `sweep_watched_rows()`'s 3-tuple (callers and tests depend on it). Write the runbook as: the count is in the admin's "Last sweep summary" and each link is a `discovery stdout:` log line; the `step discovery:` line is unchanged. If the user wants the count on the step line itself, that is a separate change to `sweep_watched_rows()` and `step_discovery()` (Open Question 3).

### Pitfall 7: Date containment is on UTC dates, which is conservative at the local-night edges
**What goes wrong:** `_record_window()` returns `start.date()` / `end.date()` of UTC datetimes. A block observed on a run's last local night can fall on `window_end + 1` in UTC (any site west of UTC, e.g. Chile or Hawaii), so that record is "outside" and stays in the queue. This is the safe direction (never a wrong link) and D-12 chose it, but it will surprise someone testing with a per-night classical run. Request windows are unaffected.
**How to avoid:** document it in the module docstring and the runbook; use mid-window dates in per-night tests; add one explicit boundary test (block on `window_end` date links, block on `window_end + 1` does not).

### Pitfall 8: "Undo dismissal" now re-links on the next tick
**What goes wrong:** `undo_dismissal` deletes the `ObservationRecordDismissal` row; its confirm dialog says the pair "will return to the worklist above". With this phase, the next sweep tick re-links an exact match as a system link instead. That is logically consistent (the veto was the dismissal) but contradicts the UI text for exactly-matching pairs.
**How to avoid:** note it in the runbook's undo paragraph; do not change the dialog text unless the user asks (Open Question 4).

### Pitfall 9: The sweep's own TargetList is the run's campaign for KEY2026B-004
**What goes wrong:** target 153 (10P) belongs to TargetList 8, `KEY2026B-004_targets`, which is also `campaign_id` of runs 69-75 [VERIFIED: read-only sqlite queries]. The sweep adds every touched target to that list after the loop, so any newly discovered target immediately becomes a "member of the campaign". Under the CONTEXT reading of D-11 step 2 that makes the campaign fallback reachable for targets that have no run (Open Question 1).

### Pitfall 10: Existing tests that assert the exact summary line
`_expected_summary()` builds the full line literally for 22 sweep tests. Extend the helper (new params default 0, new fields appended) in the same task that changes the summary, or 22 tests fail at once.

## Open Questions

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Wrong automatic attribution (integrity of the coordination record) | Tampering | Exact identity only: APPROVED runs, unique winner, containment in window, dismissal veto, never overwrite an existing link (`get_or_create` on `observation_record` + the unique constraint); undo is one staff click and writes a dismissal |
| A blank or attacker-shaped proposal string matching runs that have none | Spoofing | Empty-proposal early return (Pitfall 1); the swept proposal is the watched/`--proposal` code, so a request cannot choose its own `proposal` |
| Log injection through portal-supplied names | Information disclosure / Tampering | Format identifiers with `!r` as the existing sweep lines do |
| A failing link write halting unattended discovery | Denial of service | Per-record savepoint plus catch-and-count (D-08); a failed link is a `links skipped` count, not a `StepResult(failed=True)` |
