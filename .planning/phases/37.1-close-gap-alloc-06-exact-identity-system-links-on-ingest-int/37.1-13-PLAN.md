`--recheck-unscheduled` re-run, a request whose block started and took data must have its scheduled
start and end stored, and its `ALLOC:` calendar twin must retire.

Round-5 live verification (UAT test 6) printed `schedules rechecked: 10, blocks found: 0`. Read-only
portal GETs on 2026-10-05 showed why: the LCO portal reports the block of a request that started, took
data and stopped early as state **FAILED**, not ABORTED. `select_schedule_block()` and `BlockState` in
`solsys_code/observation_blocks.py` know only COMPLETED, ABORTED, IN_PROGRESS and PENDING, so the four
Didymos requests whose only block is FAILED (4253588, 4272067, 4276100, 4282342) still get no times and
their `ALLOC:` twins on July 12, 17, 19 and 20 stay. 37.1-07's rule was built on the assumption that
such blocks read ABORTED; the portal reply was never fetched then.

Developer decision (2026-10-05), honoured exactly: **only a FAILED block that took data retires the
night** -- some `configuration_statuses[].summary.time_completed > 0`. A FAILED block with no time
completed gives no times and keeps its ALLOC night. FAILED-with-data ranks with ABORTED/IN_PROGRESS in
the existing order (first COMPLETED, else the last started block, else the last PENDING). This plan's
treatment of an unusable `summary` or `time_completed` (missing, None, non-numeric -- including a
numeric string -- bool, NaN, zero or negative): **no data**, never an exception. The other portal block
states the rule does not name, NOT_ATTEMPTED and CANCELED, never give times; the docstring says so.

- **A-17 (no-data treatment, this plan's decision).** `time_completed` counts only as an `int` or
