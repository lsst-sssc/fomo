- FOMO's own block rule lives on unregistered FOMO facility subclasses.

That recreates, on the automated path, exactly the symptom G-37.1-1-alloc was opened for. The 37.1-08 docstring and runbook both state that it cannot happen.

### Gaps Summary

One gap, with one root cause.

The discovery sweep's write path treats a failed live lookup as "the portal says there is no block":
- It compares and writes empty times and commits the new failed status.
- The F2 finished-record skip then reads that record as already resolved.

The result is the exact G-37.1-1-alloc symptom: an allocation night that had retired comes back and stays back. It arrives on the unattended path with no staff action and no signal. The 37.1-08 gate docstring and the runbook both say this cannot happen.

The defect predates 37.1-08, which left the `compare_schedule` line unchanged. 37.1-08 is what made it consequential: it rewrote the premise of the skip to depend on every FOMO path resolving the block, and it documented that dependency as safe.

In the unattended runner the trigger is narrow but real:
- The poll's per-record call (or the whole poll step) fails.
- In the same tick, discovery's lookup for that request also fails.
- A brand-new request already in a failed state whose first lookup fails ends up frozen the same way.

Fix as 37.1-REVIEW CR-01 proposes:
- `compare_schedule` must be False on `lookup_failed`.
- Hold back the status change, or store a marker the gate honours, so the next tick retries.
- Add a regression test starting from a record that already has times.
- Correct the docstring and runbook sentence; regenerate the notebook if any output changes.

Warnings WR-01..WR-05 are not must-have failures. WR-02 (the untimed or malformed portal reply on the status_refresh write path) and WR-04 (FAILED blocks) deserve a decision in the same gap-closure round.

Everything else is verified: G-37.1-1-allocurl, G-37.1-1-pager, plan 07, plan 08's success path, and all 49 earlier truths with no regression.
