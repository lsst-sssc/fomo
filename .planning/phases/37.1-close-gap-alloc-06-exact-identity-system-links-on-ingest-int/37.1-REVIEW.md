### WR-25: A matched block that never ran becomes the record's permanent "observed" telescope, with no signal to the operator

**File:** `solsys_code/calendar_utils.py:378-379`; `solsys_code/management/commands/project_observation_calendar.py:95-122`;
downstream `solsys_code/campaign_gap.py:159-168`, `solsys_code/observation_projector.py:187-189`;
`docs/runbooks/telescope_runs_calendar.rst:697-714`

**Issue:** When exactly one block starts at the stored instant, `resolve_placement_block()` returns it "whatever
state that block is in now" (A-44). That includes PENDING, NOT_ATTEMPTED and CANCELED blocks.

For a COMPLETED record whose times TOM's rule stored from a leftover pending block (the tracer's `site-on-pending`
case), `resolve_observed_site()` therefore writes that never-run block's site and telescope into `observed_site`
and `observed_telescope`. It then never looks again (line 92). The consequences:

- `observed_token()` draws `[O] FTN` for an observation FTN never made.
- `campaign_gap.observation_site_obscode()` resolves the record to Haleakala, not Siding Spring, so
  `observation_claimed_dates()` claims a night at a site where nothing was observed. It also leaves the real
  observing site's night unclaimed.

That is the developer's chosen route (A): telescope and night stay together. The trade-off is that the code now
confidently writes wrong observed-site data for exactly the records that need the new "Correcting one record that
already holds both times" procedure. Before 37.1-15, an inconsistent label at least differed from the night it
was drawn on.

Nothing marks these records:

- The lookup counts them as an ordinary `site_lookups: 1`.
- There is no log line.
- The runbook gives no way to find them. "It applies to a finished record whose stored block is not the one
  FOMO's rule chooses" assumes the operator already knows which records those are.
- The only way to find them is the developer's manual human check 4 in 37.1-16-SUMMARY.md, which compares each
  record against the live portal.

**Fix:** Keep the A-44 return value, but emit a signal when the matched block is not one FOMO's rule would count
for the request. Use a fixed message that names only the observation_id (the SYNC-09/D-13 contract). A minimal
version is below. Either surface the flag through `resolve_observed_site()` as a counter, for example
`site_lookups_noncounting`, or log it there. Then point the runbook's correction paragraph at that line or
counter as the way to find records to correct.

```python
# calendar_utils.resolve_placement_block(), single match
if len(matching) == 1:
    chosen = matching[0]
    if select_schedule_block([chosen], request_finished=request_finished) is None:
        logger.warning(
            'observation_id=%r: stored times match a block that never counted; see the runbook correction.',
            observation_id,
        )
    return chosen
```

That adds no portal call and no second `select_schedule_block()` call on the fallback path. The plan's
"exactly one call" probe would need adjusting, or the check can be inlined on `chosen['state']`.

### IN-35: The new A-33 clause in the module docstring gives a reason that does not support its claim

**File:** `solsys_code/observation_blocks.py:38-40`

**Issue:** "...keeps that block's times, as every earlier rule did (37.1-15 A-33); that too holds on the live
lookup path, because an embedded block list is re-read on every sweep and the portal can later mark that pending
block not attempted or cancelled." The "because" clause explains why A-33 does not hold on the embedded path, not
why it holds on the live path. The parallel sentence at lines 28-31 gets this right, using a semicolon.

### IN-36: The new TOM's-rule sentences omit TOM's first tier, the COMPLETED block

**File:** `solsys_code/observation_blocks.py:55-57`; `docs/runbooks/telescope_runs_calendar.rst:641-644, 1865-1867`

**Issue:** Each passage correctly states TOM's rule as "the first COMPLETED block, else the last PENDING block,
else no times". It then says that whenever the portal still lists a pending block, TOM's rule stores that pending
block's times, and "otherwise" no times. A request finished through TOM's routes with a COMPLETED block and a
leftover pending block, which is common for a COMPLETED request, gets the COMPLETED block's times. Its night is
retired correctly, and FOMO's rule agrees. As written, the sentences tell an operator that every TOM-route record
with a pending block listed needs the correction.

**Fix:** Qualify each passage with "when the portal lists no completed block but still lists a pending block,
TOM's rule stores that pending block's times; when it lists neither, no times".

### IN-37: "Always" and "ever" overclaim beside the fallback and the documented re-lookup

**File:** `docs/runbooks/telescope_runs_calendar.rst:302-304`; `solsys_code/calendar_utils.py:306-307` and the
`Returns:` section (lines 333-336); `solsys_code/management/commands/project_observation_calendar.py:48-49`

**Issue:**

- **Runbook line 304:** "so it is always the block the record's times came from, whichever rule stored them",
  followed directly by the fallback for times that match no block, where by definition the block is not the one
  the times came from. That is the `site-on-neither` case: drawn 09-06, labelled coj from the 07-12 block.
- **`resolve_placement_block()` docstring:** "So the telescope it names and the times the record draws come from
  the same block" has the same gap.
- **`Returns:` section:** still says a None result means the call "returned no usable block (see
  select_schedule_block)". It does not say that a matched block is returned even when it is not usable.
- **"Once per record, ever":** the runbook's "(a single live portal call per record, ever)" and
  `resolve_observed_site()`'s "at most once per record, ever" now sit beside a documented procedure (step 2 of
  the correction) whose purpose is a second lookup. They also sit beside the pre-existing retry after
  `site_lookup_failed`.

**Fix:**

- Write "whenever a listed block starts at the stored start, it is the block the record's times came from".
- Add "(a block matched by its start is returned whatever its state)" to the `Returns:` section.
- Change "ever" to "once it succeeds, unless its observed-site parameters are removed".
