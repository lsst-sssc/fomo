### Are the previous findings closed?

- **WR-01 (non-list block-list reply): closed on the live path.** `ScheduleBlockRuleMixin.get_observation_status`
  (`observation_blocks.py:148-152`) raises before `select_schedule_block` runs. Each caller handles the raise:
  - `_resolve_schedule` (`backfill_lco_observations.py:356-360`) catches it as `lookup_failed`.
  - TOM's `update_observation_status` raises before its write loop, so it writes nothing.
  - `update_all_observation_statuses` adds the record to `failed_records`.
  - `_refresh_one_facility` re-checks the record and labels it `UnexpectedBlockPayloadError`.
    `_exception_label` adds no status code because the error is not a `RequestException`.
  - Both Didymos catches take `Exception`.
  - `calendar_utils.resolve_placement_block` never calls `get_observation_status`, so it is unaffected.

  The message holds only the id and the type name. The embedded-list path is still tolerant; this was
  accepted as A-5 (see IN-01 below).
- **WR-02 (failed recheck lookup not retried): closed for watched proposals.**
  - `_failed_lookup_needs_marker` returns True only when the lookup failed and
    `_schedule_lookup_is_needed(..., recheck_unscheduled=False)` is False. In practice that is an unmarked
    failed-state record, at the same portal state, missing a time. Such a record is only ever looked up
    under the flag.
  - A dry run can never write or remove the mark. `_resolve_schedule` returns `lookup_failed=False` under
    `dry_run`, so `mark_lookup_failed` is always False there. The `not compare_schedule` branch of
    `_changed_record_fields` carries any existing mark across.
  - For watched proposals, lookups per tick stay bounded by the size of the listing.
  - Gap: the retry depends on the unattended runner sweeping the proposal, and a `--proposal` recheck of an
    unwatched code is never swept. See WR-01 below.
- **WR-03 (stale runbook bullet): closed.** The bullet at `telescope_runs_calendar.rst:415-430` is qualified

## Warnings

### WR-01: A failed `--proposal X --recheck-unscheduled` lookup on an unwatched proposal is marked, but nothing ever retries it, and the runbook tells the operator not to re-run

**File:** `solsys_code/management/commands/backfill_lco_observations.py:422-423`, `:647-649`, `:1106-1107`,
`:1207-1208`; `docs/runbooks/telescope_runs_calendar.rst:593-602`;
`docs/notebooks/pre_executed/backfill_lco_observations_demo.ipynb` cell 39

**Issue:** The WR-02 fix assumes the record's proposal is swept again by the unattended runner. Many
places say so:
- the gate docstring: "so the unattended runner, which never passes the flag, retries it"
- `sweep_proposal`'s `recheck_unscheduled` argument doc
- the `Command` docstring
- the `--recheck-unscheduled` help text: "A record whose lookup fails is marked, so the unattended runner
  retries it"
- the runbook: "the unattended runner looks it up again on every tick until a lookup succeeds; there is no
  need to run the recheck again for it"
- notebook cell 39: "the one the unattended runner makes"

The runner does not sweep every proposal. `unattended.step_discovery` calls `sweep_watched_rows`, which
sweeps only `WatchedProposal.objects.filter(is_active=True)` (`backfill_lco_observations.py:991`). The
runbook offers the single-proposal form at `:593-594` (`--proposal LCO2026A-001 --recheck-unscheduled`), and
the `Command` docstring says a `--proposal` code "does not have to be a WatchedProposal row". If that code
is not an active watched proposal, the sequence is:
1. The failed lookup writes `schedule_lookup_failed: True`.
2. The summary counts the record as `updated: 1`.
3. The runbook tells the operator a re-run is unnecessary.
4. No unattended tick ever looks the record up.

The aborted block's times are never stored and the run's allocation night stays on the calendar. This is
the same silent loss WR-02 was meant to close, now on the operator's documented single-proposal path, and
the docs actively steer the operator away from the recovery. The help text is also over-broad: a failed
lookup on a completed record missing a time is not marked (by design, see `TestRecheckUnscheduledSweep.
test_a_failed_recheck_lookup_on_a_completed_record_missing_a_time_is_not_marked`).

**Fix:** Correct the docs. Make the runbook sentence conditional:

```rst
A record whose recheck lookup fails, and which the ordinary per-tick skip would otherwise leave
alone, is marked ``schedule_lookup_failed``. If the proposal is an active watched proposal, the
unattended runner looks it up again on every tick until a lookup succeeds. Otherwise run
``backfill_lco_observations --proposal <code>`` (no flag needed) again until
``block lookups failed`` is 0.
```

Give the help text, the `Command` docstring, the gate docstring, the `sweep_proposal` argument doc and
notebook cell 39 the same "for an active watched proposal" qualifier. Optionally, make `Command.handle()`
write a stderr hint when `--proposal` is given, the proposal is not an active `WatchedProposal`, and
`block lookups failed` is above 0.

## Info

### IN-01: An embedded `observations` value that is not a list is still read as "no block" on the discovery sweep (accepted as A-5, but the stated reason does not cover the cheap fix)

**File:** `solsys_code/management/commands/backfill_lco_observations.py:344-350`, `:798`

**Issue:** `embedded = blocks is not None` treats any non-None `observations` value as an embedded block
list, including a dict, a string or an envelope. `select_schedule_block` then returns None, and
`_resolve_schedule` returns `(None, None, False, True)`. Because `compare_schedule` is True and
`lookup_failed` is False, three things happen:
- an existing record's stored times are overwritten with None;
- a held-back status change is committed;
- the `schedule_lookup_failed` mark is dropped.

This runs even for a record the F2 gate would skip, because the embedded branch runs before the skip.
This is the WR-01 hazard on a second path. A-5 accepts it because `calendar_utils.resolve_placement_block`
must never raise and the listing carries no embedded blocks today. The first reason applies to
`select_schedule_block`, not to `_resolve_schedule`. Tightening only the embedded check here leaves
`select_schedule_block` and `calendar_utils` untouched. There is no live exposure today, so this stays Info.

**Fix:** `embedded = isinstance(blocks, list)`. A non-list value then falls through to the gated live
lookup, which already raises `UnexpectedBlockPayloadError` for a bad body.

### IN-02: `sweep_watched_rows()`'s per-proposal failure line still has no newline, so in the unattended log it merges with the next proposal's first line (deliberately left as A-9)

**File:** `solsys_code/management/commands/backfill_lco_observations.py:1051`, together with
`solsys_code/unattended.py:457-470`

**Issue:** IN-02's stated goal is "the unattended discovery step logs one record per line". Only
`sweep_proposal`'s writes gained a `\n`. `sweep_watched_rows` still writes `f'Proposal {code!r}: {summary}'`
with no newline into the same raw `io.StringIO` that `step_discovery` splits with `splitlines()`.

When proposal A fails and proposal B then writes a stderr line, the log gets one record like this:
`discovery stderr: Proposal 'A': failed: HTTPErrorFailed to resolve observed block for observation_id='30'.`
That one line hides both the failed proposal's class name and the first stuck observation id. Under
`call_command` the bug does not show, because `OutputWrapper` adds the newline.

**Fix:** `stderr.write(f'Proposal {row.proposal_code!r}: {summary}\n')`. Add a two-row test: the first row
raises, the second has a failed lookup, and `splitlines()` must return separate entries.

### IN-03: WR-02's mark turns a one-time recheck failure into an unlimited per-tick retry (makes deferred IN-01 / A-6 more likely to hit)

**File:** `solsys_code/management/commands/backfill_lco_observations.py:452-482`, `:903-905`

**Issue:** Before this round, a failed-state record with no times cost lookups only during a manual recheck.
Now, if one operator recheck runs during a partial portal outage, for example `/observations/` returning
5xx or a non-list body, every legacy failed-state record in the proposal gets marked. Every tick after that
then makes two GETs per marked record until each lookup succeeds.

That is self-healing when the outage is transient. For a request that fails every time it has no limit,
and nothing escalates. Such a record is a finished, failed-state record, so it is not covered by the
status_refresh failure email that A-6 relies on for visibility. So the plan's statement "the unattended
per-tick lookup count stays bounded as F2 made it" holds only per tick, not over time.

**Fix:** Same as the deferred IN-01: store an attempt count in the marker
(`parameters['schedule_lookup_failed'] = n`) and either stop or log at WARNING past a threshold. At minimum,
note in the runbook that a recheck run during a portal incident marks every record it touches.

### IN-04: The paired runbook does not explain the summary counts after a failed recheck lookup

**File:** `docs/runbooks/telescope_runs_calendar.rst:594-597`, `:593-602`

**Issue:**
- `:595-597` says that on later ordinary ticks the finished no-time records "are back under
  `fallback lookups skipped`". A record marked by a failed recheck stays under `fallback lookups needed`
  on every tick until a lookup succeeds.
- A failed recheck lookup reports the record as `updated: 1`, because the mark is a `parameters` change,
  even though its status, times and allocation night did not change. A dry run of the same command
  reports it `unchanged`. Neither behaviour is mentioned, so an operator reading `updated: 1` may believe
  the recheck succeeded.

**Fix:** Add one sentence after "A dry run makes no lookup and marks nothing.": "Such a record is counted
under `updated` (the mark is the change) and stays under `fallback lookups needed` on later runs until its
lookup succeeds."

### IN-05: The `UnexpectedBlockPayloadError` docstring makes a wrong claim about `calendar_utils`

**File:** `solsys_code/observation_blocks.py:66-69`

**Issue:** The docstring says the error subclasses `ValueError` "so the handlers that already catch it (and
`calendar_utils`'s own `ValueError` catch) keep working". `calendar_utils.resolve_placement_block` makes its
own `make_request` call and never calls `get_observation_status`, so it can never see this exception. Its
`ValueError` catch is for a non-JSON body. Every real caller catches `Exception`, so the `ValueError` base
class protects nothing. The claim could mislead a later change into relying on it.

**Fix:** Change the sentence to: "It subclasses `ValueError` because the body is a bad value; every caller
catches `Exception`, so the class only names the failure."

### IN-06: New facility tests check the exception class by name string instead of the class

**File:** `solsys_code/tests/test_observation_blocks.py:146-168`; notebook cell 42

**Issue:** `assertRaises(ValueError)` followed by `type(cm.exception).__name__ == 'UnexpectedBlockPayloadError'`
also passes for any same-named class, and a rename produces a confusing failure. This was most likely left
over from the RED step, before the class existed.

**Fix:** `from solsys_code.observation_blocks import UnexpectedBlockPayloadError` and
`with self.assertRaises(UnexpectedBlockPayloadError)`.

### IN-07: The `mark_lookup_failed` / `lookup_failed` pairing is documented but not enforced

**File:** `solsys_code/management/commands/backfill_lco_observations.py:562-564`, `:579-580`

**Issue:** The docstring says "pass True only together with `lookup_failed`". Nothing checks it. If a caller
passes `mark_lookup_failed=True` after a successful lookup, the code writes the mark together with the
resolved times (`compare_schedule` stays True). The record is then looked up on every tick until a later
lookup happens to clear the mark. Both current call sites are correct, because they derive the flag from
`_failed_lookup_needs_marker(..., lookup_failed=lookup_failed)`.

**Fix:** Write `if mark_lookup_failed and lookup_failed:` at `:579`, or raise `ValueError` when it is passed
without `lookup_failed`.
