## Warnings

### WR-12: `ProtectedUserDeleteView` catches `ProtectedError` only in `form_valid()`, so an HTTP `DELETE` to the same URL still returns a 500

**File:** `solsys_code/views.py:761-791` (Django's `DeletionMixin.delete`, `django/views/generic/edit.py:220-228`)

**Issue:** Django 5.2's `BaseDeleteView` still inherits `DeletionMixin`. `post()` was rerouted
through `form_valid()`, but `DeletionMixin.delete()` was kept, and `View.dispatch()` routes the
HTTP `DELETE` method straight to it. That method calls `self.object.delete()` directly and never
reaches the overridden `form_valid()`.

So the WR-10 guard covers only the POST that TOM's templates send. Any client that issues
`DELETE /users/<pk>/delete/` for a protected account still gets the unhandled `ProtectedError`
and an HTTP 500. Such a client could be HTMX (`hx-delete`, and `django_htmx` is installed),
`fetch`, or a script holding a session and a CSRF token.

Probe: `self.client.delete(reverse('user-delete', kwargs={'pk': confirmer.pk}))` as a superuser
logged `Internal Server Error: /users/<pk>/delete/` and raised `ProtectedError`.

WR-10's stated contract is "refuse, not crash", and its docstring says the view "leaves the
account in place and sends the operator back to the user list". Both are true for one of the two
HTTP methods the view accepts. Nothing is deleted, so the data is safe. But the operator-facing
500 the fix set out to remove is still reachable, and the new tests exercise only `client.post`.

**Fix:** Route `DELETE` through the same guarded path, or stop accepting it. Either:
```python
class ProtectedUserDeleteView(UserDeleteView):
    http_method_names = ['get', 'post', 'head', 'options']  # DELETE bypasses form_valid()
    ...
```
or
```python
    def delete(self, request, *args, **kwargs):
        """Send an HTTP DELETE through post() so form_valid()'s ProtectedError guard applies."""
        return self.post(request, *args, **kwargs)
```
Then add a test next to the POST tests: `self.client.delete(...)` for a confirming user is not a
500, and the user still exists.

## Info

### IN-09: The comment directly above the new WR-11 comment says the opposite about `confirmed_by IS NULL`

**File:** `solsys_code/models.py:139-142` vs `144-149`

**Issue:** The Phase 28 paragraph still says that an event link written before Phase 28 has
`confirmed_by` NULL, and "so NULL means 'confirmed before audit fields existed', not
'unconfirmed'". The new WR-11 paragraph five lines below says that `confirmed_by IS NULL` is
exactly what lets the reconciler release or delete an event. The code agrees with WR-11:
- `campaign_reconciler.py:482-483` and `537-539` count only non-NULL confirmations as declines.
- `allocation_projector.py:1004` clears only NULL-confirmed metas.

The runbook now also says a NULL event confirmation reads as "unconfirmed and free for the next
reconcile to release or delete". A maintainer reading the older paragraph will draw the wrong
conclusion about which rows are guarded. The older paragraph also hides a real pre-existing gap:
a pre-Phase-28 admin-picker attribution is treated as unguarded.

**Fix:** Reword the Phase 28 paragraph to match the reconciler. For example: "NULL is read as
unconfirmed by the reconciler and the attribution sync, which may release or delete such an
event; a pre-Phase-28 attribution therefore has no human guard". If those historical rows matter,
record the gap in the ledger.

### IN-10: The WR-09 savepoint covers the re-projection, but the `campaign_run_links` lookup guarded by F-34-1 still runs bare in the caller's transaction

**File:** `solsys_code/observation_projector.py:682-693`; `solsys_code/allocation_projector.py:1647,1738`

**Issue:** The F-34-1 `try` around `list(instance.campaign_run_links.select_related('run'))`
swallows a query fault, but the query has no savepoint of its own. On SQLite, the current default,
this is harmless: a failed read does not poison the transaction, and Django sets
`needs_rollback` only for writes made under `mark_for_rollback_on_error`.

On PostgreSQL, which `CLAUDE.md` lists as a supported production backend, a failed statement
aborts the whole transaction. The receiver logs and carries on, then the caller's next query
raises `InFailedSqlTransaction`. That is the same "never abort the caller's save" promise that
WR-09/CR-01 just closed for the re-projection. The `CampaignRun.objects.filter(...).first()`
lookups ahead of the CR-01 savepoints in both `allocation_projector` receivers have the same
shape. This is pre-existing and not a regression from these commits.

**Fix:** Move the lookup into the savepoint when convenient, for example
`with transaction.atomic(): links = list(...)` inside the existing `try`. The same applies to the
two `run = ...first()` lookups. Alternatively, note in the receiver docstring that the guarantee
is SQLite-scoped.

### IN-11: The refusal message tells a non-superuser deleting their own account to use the admin, which they cannot reach

**File:** `solsys_code/views.py:784-790`

**Issue:** TOM's `dispatch()` lets any logged-in user delete their *own* account. When that
account is protected, the message reads "Deactivate the account instead (clear "Active" on its
admin page)". A non-staff user has no admin access, and is then redirected to the Users list
page. Probe: a self-delete POST by a non-superuser confirmer returned 302 to `/users/` with this
message. That is harmless, since nothing is deleted, but the remedy offered is not one this
person can carry out.

**Fix:** Branch the wording on `self.request.user.is_staff` (or on `is_superuser`). For a
self-service caller, say "ask an administrator to deactivate it instead".
