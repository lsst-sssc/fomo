## Warnings

### WR-08: Deleting a *staff* link in the admin inline still writes no dismissal, so the next sweep re-creates it as a "System (exact match)" link

**File:** `solsys_code/admin.py:350-368`; `solsys_code/tests/test_admin.py:708-720`; `docs/runbooks/telescope_runs_calendar.rst:645-647`

**Issue:** The WR-01 fix writes the dismissal only when `obj.confirmed_by_id is None`. The
exact-identity matcher has two vetoes:
- an existing link
- a dismissal (`campaign_system_links.py:172-200`)

Once a staff link is deleted with no dismissal, neither veto exists any more. If the pair is an
exact match, the next `backfill_lco_observations` tick links the record to the same run again
through `create_system_link()`. That is common: many staff links are exactly the pairs 37.1 now
auto-links, for example pre-37.1 confirmations.

The re-created link has `confirmed_by=None`. So the staff member's "this pair is wrong" decision
is overridden, and the replacement link is labelled "System (exact match)". That is the false
machine provenance WR-03 and WR-04 were fixed to prevent.

The attribution page's Undo (`campaign_views.py:1552-1585`) writes a dismissal for staff links and
system links alike, so the two staff removal paths now disagree. The new test
`test_deleting_a_staff_link_in_the_inline_writes_no_dismissal` locks the gap in. The runbook only
says deleting a *system* link "counts as a person's decision".

I reproduced it with a probe:
1. A staff-confirmed link deleted through `CampaignRunAdmin.save_formset` left no dismissal.
2. `attempt_system_link(record, dry_run=False, ...)` then returned `linked`.
3. The new row's `confirmed_by_label()` was `System (exact match)`.

**Fix:** Write the dismissal for every deleted `CampaignRunObservation`, matching the Undo:
```python
for obj in formset.deleted_objects:
    if isinstance(obj, CampaignRunObservation):
        with transaction.atomic():
            ObservationRecordDismissal.objects.get_or_create(
                observation_record_id=obj.observation_record_id,
                run_id=obj.run_id,
                defaults={'dismissed_by': request.user, 'dismissed_at': timezone.now(),
                          'reason': 'Removed in admin.'},
            )
            obj.delete()
    else:
        obj.delete()
```
Invert `test_deleting_a_staff_link_in_the_inline_writes_no_dismissal` to assert the dismissal
exists. Reword the runbook sentence to "Deleting a link in that admin inline ...".

### WR-09: The CR-01 savepoint fix covers two of the three `reproject_allocation_if_dispatched()` call sites; `receiver_on_record_save` still lets a failed projection silently roll back the caller's record save

**File:** `solsys_code/observation_projector.py:695-707` (third call site of the function wrapped at `solsys_code/allocation_projector.py:1655-1656,1744-1745`)

**Issue:** CR-01's fix comment states the general rule: a failed ORM write inside the
re-projection sets `needs_rollback` on the caller's atomic block, and the receiver's
`except Exception` cannot undo that. `receiver_on_record_save` calls the same
`reproject_allocation_if_dispatched(link.run)` with no savepoint. Its docstring relies on
`project_record()`'s own savepoint, which does not cover this second step.

When the record is saved inside any atomic block, a failing linked-run projection rolls back the
record's own save without raising. Examples of such blocks:
- the Django admin change form (`ObservationRecord` is registered by tom_observations)
- `update_or_create`
- any caller that wraps its own writes

The same failure also defeats the per-link isolation that WR-02 (35-REVIEW.md) added. After the
first failure every later query in the block raises `TransactionManagementError`, so the later
runs' re-projections all fail too.

I reproduced it with a probe:
1. Patched `reproject_allocation_if_dispatched` to perform one failing save.
2. Inside `transaction.atomic()`, set `record.status = 'CANCELED'` and called `record.save()`.
3. Read the record back: its status was still `COMPLETED`, and no exception had reached the
   caller.

This file is outside the fix-commit scope, but the fault is the very failure mode CR-01 closed,
on the very function it wrapped.

**Fix:**
```python
for link in links:
    if link.run is None:
        continue
    try:
        with transaction.atomic():
            reproject_allocation_if_dispatched(link.run)
    except Exception as exc:  # noqa: BLE001
        logger.warning(...)
```
Alternatively, move the savepoint into `reproject_allocation_if_dispatched()` itself, so every
caller gets it. Add a regression test mirroring
`test_a_failing_receiver_write_does_not_roll_back_the_link` for a record save.

### WR-10: `PROTECT` turns TOM's own user-delete page into an HTTP 500 for any staff member who confirmed a link

**File:** `solsys_code/models.py:626-633`; `solsys_code/migrations/0024_campaignrunobservation_confirmed_by_protect.py:16-20`; `docs/runbooks/telescope_runs_calendar.rst:642-645`

**Issue:** TOM Toolkit exposes `users/<pk>/delete/` (`tom_common.views.UserDeleteView`). A
superuser can delete any account there, and every user can delete their own. The view is a plain
`DeleteView`, so `form_valid()` calls `self.object.delete()`, which does not catch
`ProtectedError`.

Under `SET_NULL` that delete succeeded. Under `PROTECT`, it now escapes as an unhandled
exception. A probe POST as a link-confirming staff user returned **500** (`ProtectedError ...
'CampaignRunObservation.confirmed_by'`), and the user survived. Only the Django admin's delete
path renders a friendly "protected related objects" page.

The runbook's new "cannot be deleted -- deactivate it instead" is accurate about the outcome but
gives no hint that the TOM UI path crashes. Operators following TOM's own user list will hit a
server error page.

**Fix:** Pick one of these:
- Keep `PROTECT` and override or wrap `user-delete` in FOMO's `urls.py`, so the view catches
  `ProtectedError`, shows a message ("this account confirmed N campaign links; deactivate it
  instead") and redirects.
- Hide the delete action in `tom_common/user_list.html` for accounts with confirmations.

Either way, add a test that POSTs to `reverse('user-delete', ...)` for a confirming user and
asserts a non-500 response. Also name the TOM page in the runbook sentence.

### WR-11: The WR-03 rationale applies equally to `CalendarEventMeta.confirmed_by`, which is still `SET_NULL` and guards automated deletes

**File:** `solsys_code/models.py:143-150`; `solsys_code/campaign_reconciler.py:481-483,535-540`; `solsys_code/allocation_projector.py:1003-1006`; `docs/runbooks/telescope_runs_calendar.rst:642-645`

**Issue:** WR-03 was fixed because `confirmed_by IS NULL` is read as "machine, safe to undo".
`CalendarEventMeta.confirmed_by` carries the same load-bearing meaning in three places, and is
still `on_delete=SET_NULL`:
- `_clearable_and_declined()` releases or deletes stale events only when
  `confirmed_by__isnull=True`, and counts the rest as `declined`.
- `_clearable_declined_and_unattributed()` uses the same split.
- `_sync_observation_attribution()`'s unlink half clears only `confirmed_by__isnull=True` metas.

So deleting a staff account that confirmed calendar events, which `PROTECT` on
`CampaignRunObservation` does not prevent, silently strips the human guard from every event they
confirmed. The next reconcile may then detach or delete those events.

The new runbook sentence ("a staff account that has confirmed a link cannot be deleted --
deactivate it instead") reads as a complete rule, but it covers only record links. A staff
account with only event confirmations deletes cleanly and loses them.

This hazard predates 37.1 (Phases 29/35). It is flagged here because the WR-03 fix's stated
invariant, and its operator guidance, are only half true.

**Fix:** Apply the same `on_delete=models.PROTECT` to `CalendarEventMeta.confirmed_by`, with an
`AlterField` migration, and add a parallel `ProtectedError` test. If that is judged too broad for
this phase, change the runbook sentence to cover calendar-event confirmations too, and record the
remaining gap in the disposition ledger.

### IN-06: `high_band_attribution_candidates` docstring now overclaims "Never raises", and the new query duplicates data the template already loaded

**File:** `solsys_code/templatetags/attribution_display_extras.py:29-30,44-47`

**Issue:** The tag now issues its own `CalendarEventMeta.objects.filter(...).exists()` before
delegating, so "Never raises: delegates entirely to `candidates_for_event()`" is no longer true.
A database error in the new query propagates into the modal render. The template branch that
calls the tag has already evaluated `event.telescope_label_meta.run`, so the companion row is
cached on the event.

**Fix:** Read the cached row instead of re-querying. Wrap it in
`try: meta = event.telescope_label_meta except CalendarEventMeta.DoesNotExist: meta = None`, then
`if meta is not None and meta.observation_record_id is not None: return []`. Reword the docstring.

### IN-07: The runbook's "delete the link and add a new one" recipe cannot be done in one save for the same record, and two saves leave a dismissal standing beside a confirmed link

**File:** `docs/runbooks/telescope_runs_calendar.rst:647-649`; `solsys_code/admin.py:315-368`

**Issue:** `save_formset` saves new rows before it deletes marked rows. On top of that, the
add-form's constraint validation checks `unique_campaign_run_observation_record` against the
still-present old row. So "delete the system link and re-add the same record as my own
confirmation" fails validation in a single save.

In two saves, the first save writes the WR-01 dismissal (`Removed in admin.`) and the second
creates the staff link. The Dismissed section then lists a dismissal for a pair that is
confirmed, with an "Undo dismissal" button.

**Fix:** Either document the two-save behavior, or, when a staff link is created in
`save_formset`, delete any `ObservationRecordDismissal` for the same `(record, run)` pair.

### IN-08: `write_and_reconcile_campaign_run` does not document the new `IntegrityError` it can now raise

**File:** `solsys_code/campaign_utils.py:1093-1103,1114-1115`

**Issue:** `create_system_link()` now raises `IntegrityError` for a created-but-rolled-back row.
`write_and_reconcile_campaign_run(..., observation_record=...)` calls it without a `try` and
without a `Raises:` entry. No current caller passes `observation_record`, since `load_telescope_runs`
omits it, so this is unreachable today. A future adapter could still be surprised.

**Fix:** Add a `Raises: IntegrityError` entry to the docstring, or catch and report it like
`attempt_system_link()` does.
