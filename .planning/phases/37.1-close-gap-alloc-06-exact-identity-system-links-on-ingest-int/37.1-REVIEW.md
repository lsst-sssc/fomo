### IN-39: `resolve_placement_block()`'s edited `Returns:` block still claims every block carries `state`, and says a missing `state` key is turned into None

**File:** `solsys_code/calendar_utils.py:334-341`

**Issue:** The block now says a block matched by its start "is returned whatever its state". The same block still
says:

- that the result has `'site'/'enclosure'/'telescope'/'state'` keys
- that the failure modes caught and converted to None include "missing 'state' key"

Neither is true:

- A matched dict is returned exactly as the portal listed it (lines 379-382 and 389). Nothing checks its keys.
- `select_schedule_block()` reads `block.get('state')` and skips entries that have no state.
- No path in this function can raise `KeyError`, so no missing key is ever "caught".

So a single-match block with no `state`, `site` or `telescope` key comes back non-None. The caller handles that:
`resolve_observed_site()` uses `.get()`, and `derive_telescope(None, ...)` gives a failed lookup. But the docstring
describes a contract the function does not enforce. This is the same "Returns: overclaims" gap IN-37 set out to
close.

**Fix:**

```
Returns:
    dict[str, Any] | None: the matched block dict exactly as the portal listed it (its
        'site'/'enclosure'/'telescope'/'state' keys are not checked -- callers read them with .get());
        a block matched by its start is returned whatever its state, even one select_schedule_block()
        would not count. None if the API call failed, timed out, returned a body that is not a list,
        or no block matched and select_schedule_block() chose none. Never raises -- every failure mode
        (network error, library auth/validation exception, malformed/non-JSON body) is caught ...
```

### IN-40: The new "when it lists neither" clause is followed by "the per-tick skip leaves the record alone", which is false for a record in COMPLETED state

**File:** `docs/runbooks/telescope_runs_calendar.rst:646-647`; `solsys_code/management/commands/backfill_lco_observations.py:436-437`

**Issue:** IN-36's fix adds a third case to TOM's rule: "when it lists neither, it stores no times". Both passages
then go on: "Whichever it stores, the per-tick skip then leaves the record alone too" (runbook), and "Either way
this skip leaves the record alone" (docstring).

`_schedule_lookup_is_needed()` returns `recheck_unscheduled or existing_record.status not in failed_states`
(line 476) for a terminal record that is missing a time. So a COMPLETED record with no times is looked up again
on every tick. The runbook says so itself 24 lines earlier, at line 622: "The exception is a completed record
that is still missing its scheduled times."

The case is close to unreachable in practice, since a COMPLETED request normally lists a COMPLETED block. But the
sentence as written is unconditional, and the paragraph contradicts itself.

**Fix:** Limit the sentence to failed states. For example: "Whichever it stores, for a request in a failed state
the per-tick skip then leaves the record alone too (a completed record left without times is still looked up, as
above)." Apply the same qualifier to the docstring's "Either way".

### IN-41: The re-lookup gate is described as "the keys are removed", but it tests only that `observed_site` is truthy, and the runbook still says "made once"

**File:** `solsys_code/management/commands/backfill_lco_observations.py:518-520`; `solsys_code/management/commands/project_observation_calendar.py:48-51, 72`; `docs/runbooks/telescope_runs_calendar.rst:712`

**Issue:**

- **`_preserve_observed_site_keys()` (edited).** It says the sweep "treats their presence as 'already looked
  up': the record is looked up again only if they are removed." The real gate (`project_observation_calendar.py:93`)
  is `record.parameters.get('observed_site')` alone, and it tests truthiness, not presence:
  - removing only `observed_telescope` and `observed_enclosure` never triggers a re-lookup
  - `observed_token()` then returns None, so the entry falls back to the coarse label permanently
  - an `observed_site` that is present but holds None or an empty string is looked up again

  The runbook recipe removes all three keys, so the documented procedure works. The general statement is still
  wrong.
- **`resolve_observed_site()` docstring.** Line 72 still says "never looked up again" with no qualifier. Lines
  48-51 now give the qualified form ("unless its observed-site parameters are removed"), so the same docstring
  says both.
- **Runbook line 712.** The correction paragraph, whose purpose is a second lookup, still says "The
  observed-telescope lookup is made once".

**Fix:**

- In `_preserve_observed_site_keys()`: "...treats a stored `observed_site` as 'already looked up': the record is
  looked up again only if `observed_site` is removed (or empty)."
- In `resolve_observed_site()` line 72: "...is not looked up again, even if its times later change, until its
  `observed_site` is removed."
- In runbook line 712: "The observed-telescope lookup is not repeated once it has succeeded, and without this
  step...".

### IN-43: In the regenerated output, the step-(5) record creations appear inside sweep 2

**File:** `docs/notebooks/pre_executed/backfill_lco_observations_demo.ipynb` cell `d4a7c2e1` (outputs 5-9); also
cell index 33 (`02c66802`; its `Target post save hook` line moved in this regeneration) and cell index 19 (the
`facility terminal states:` line split into two stdout fragments)

**Issue:** TOM's `observation_change_state` hook logs through `logger.info` (`tom_common/hooks.py:33`), which goes
to stderr. Jupyter flushes stderr and stdout independently. In the committed output the order is:

1. "sweep 2: WINDOW_EXPIRED..." (stdout)
2. "from PENDING to WINDOW_EXPIRED" (stderr)
3. three "from None to COMPLETED" lines (stderr)
4. sweep 2's own `stdout: requestgroups seen: ...` summary (stdout), followed by everything from sweep 3

The three COMPLETED lines come from creating 900662, 900663 and 900664 in step (5), after sweep 3. This
regeneration added the third.

A reader treating the executed output as a record, as CLAUDE.md's paired-docs rule intends, sees three COMPLETED
records apparently created by sweep 2. The order is also not reproducible: the `Target post save hook` line moved
between cells' output positions in this run.

**Fix:** In the notebook's setup cell, quiet the hook logger: `logging.getLogger('tom_common.hooks').setLevel(logging.WARNING)`.
Alternatively, call `sys.stdout.flush()` and `sys.stderr.flush()` at the end of `_finished_sweep()` and before
step (5). Then regenerate.
