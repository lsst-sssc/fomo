## Warnings

### WR-20: The rule checks block state, not request state. A finished request that still lists a PENDING block now records that block instead of the block that took data, and the record is never looked at again

**File:** `solsys_code/observation_blocks.py:163-169` (the rule) and `:198-219` (`get_observation_status()`
has the request `state` but does not pass it on);
`solsys_code/management/commands/backfill_lco_observations.py:350-356` (`_resolve_schedule()`) and
`:451-457` (`_schedule_lookup_is_needed()`, the finished-record skip). TOM's
`update_all_observation_statuses()` (`tom_observations/facility.py:573`) excludes terminal records.

**Issue:** Most of the new prose says the placed block wins *while the request is pending*:

- module docstring `:21`: "While a request is still pending, its record follows the block the scheduler
  has placed"
- `select_schedule_block()` docstring `:125-126`: "while the request is still pending, the block the
  scheduler has placed is its live schedule"
- runbook `:1419`: "the placed one while the request is pending"
- notebook cell `b9d3e7a0`

The code never reads the request's state. A PENDING block beats every block that took data whatever state
the request is in, including WINDOW_EXPIRED, CANCELED, FAILURE_LIMIT_REACHED and NOT_ATTEMPTED.

That matters at the one tick that is never repeated: the request's change to a finished state. Take a
per-night run and a request with blocks `[FAILED with data on 07-12, PENDING on 07-19]`. The 07-19 block
did not run (weather), and the portal has not yet moved it to NOT_ATTEMPTED when the request turns
WINDOW_EXPIRED. Then:

1. `step_status_refresh()` stores WINDOW_EXPIRED with the **07-19** times. The old order stored 07-12.
2. `retired_nights()` retires 07-19, a night on which nothing was observed. It brings back 07-12's `ALLOC:`
   entry, although data was taken that night. The record is drawn `[X]` over a block that never ran.
3. The record is now finished at the portal's state and has both times. So TOM's update loop skips it
   (terminal), the discovery sweep skips it (`_schedule_lookup_is_needed()` reaches `return False` at
   `:457`), and `--recheck-unscheduled` skips it too, because it only looks at records missing a time.
   Once the portal later moves the block to NOT_ATTEMPTED, no FOMO path ever reads the block list again.

The old order made the same error only when no block had taken data. The new order also lets a leftover
PENDING block push aside a block that took data. Three passages assume the block stored at that last
transition is the right one:

- `_schedule_lookup_is_needed()` docstring `:413-418`: "a record that reaches a failed state through one of
  them already holds its block and this skip stays correct for it"
- runbook `:591-597`: "That is what keeps the per-tick skip safe for those records"
- `Command` docstring `:1133-1137`: "A request in one of the facility's failed request states can still
  carry a block that took data ... FOMO's block rule ... stores that block's times"

No test covers a finished request with a PENDING block. Every multi-block test in this round uses a PENDING
request (or the COMPLETED request for which a COMPLETED block wins), plus WINDOW_EXPIRED with two FAILED
blocks.

How often this happens depends on portal behaviour I could not check: whether a request can be finished
while one of its blocks still reads PENDING. The plan's own portal research (A-24, A-25) did not look at
this. Because the result is permanent and silent, it is a Warning and not just a note.

**Fix:** Pass the request state through, so the PENDING tier wins only while the request can still run.
For example, in `observation_blocks.py`:

```python
def select_schedule_block(blocks: Any, request_finished: bool = False) -> dict[str, Any] | None:
    ...
    if request_finished:
        # A finished request will run no further block: a block that took data outranks a leftover PENDING one.
        return last_started if last_started is not None else last_pending
    return last_pending if last_pending is not None else last_started
```

Then call it with `request_finished=state in self.get_terminal_observing_states()` in
`ScheduleBlockRuleMixin.get_observation_status()`, and with `request.get('state')` checked the same way in
`_resolve_schedule()`'s embedded branch. `resolve_placement_block()` runs only for COMPLETED records, so it
can keep the default.

Add a test that ticks a WINDOW_EXPIRED request with `[real 4253588 FAILED, PENDING 07-17]` through
`step_status_refresh()`. It should assert that the record stores 07-12 and that 07-12 is retired.

If the developer would rather not change the rule, two things are needed instead:

- Confirm against the portal that a finished request never lists a PENDING block, and write that down as
  the basis in the `select_schedule_block()` docstring.
- Reword the "while the request is still pending" passages to "while the block list holds a pending block".

### IN-29: Notebook cell `b9d3e7a0` says the sample lists test each kind of started block "in both orders"; only one kind is tested in both orders

**File:** `docs/notebooks/pre_executed/backfill_lco_observations_demo.ipynb`, cell `b9d3e7a0` (index 45)
and its code cell `b9d3e7a1` (index 46)

**Issue:** The markdown says: "The next cell first runs the rule on four sample lists, a pending block
against each kind of started block in both orders." The code runs:

- `failed+data then pending` and `pending then failed+data` (both orders)
- `aborted then pending` (one order)
- `in progress then pending` (one order)

The pending-first order is never shown for the aborted and in-progress blocks. Cell 33 has

tests do cover all pairs, so the claim is true of the rule but not of what this cell shows.

**Fix:** Change the sentence to "four sample lists: a pending block against a block that failed after
taking data in both orders, then against an aborted and an in-progress block". Or add the two missing
orders to the tuple and regenerate the notebook.

### IN-30: The module docstring still says a block that stopped early retires its night "exactly like a COMPLETED one"

**File:** `solsys_code/observation_blocks.py:9-11`

**Issue:** "Under Phase 35 D-05/D-06 a block that was placed and stopped early after taking data retires
its night exactly like a COMPLETED one". Under the new order this is no longer true for a request with
more than one block:

- A COMPLETED block wins over a later PENDING block, so its night stays retired.
- An ABORTED, IN_PROGRESS or FAILED-with-data block gives way to a later PENDING block. Its night then
  comes back, and stays back if that placed block completes.

The docstring's own tiers paragraph (`:18-25`) says this, so the module now contradicts itself.

**Fix:** "...retires its night like a COMPLETED one while it is the request's chosen block (see the
tiers below: a later placed block takes over, and the earlier night then comes back)".
