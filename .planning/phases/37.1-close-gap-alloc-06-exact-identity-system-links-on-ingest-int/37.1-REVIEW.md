### WR-13: The notebook guard passes a notebook whose current source routes Django to the developer database, as long as its committed output is stale

**File:** `solsys_code/tests/test_pre_executed_notebooks.py:83-125, 175-184`

**Issue:** `isolation_problems()` checks the following facts independently, and none of them
ties the current source to an actual scratch routing:
1. Some `tempfile.mkdtemp(prefix='fomo-notebook-db-')` call appears before `django.setup()`.
   Nothing checks that the path assigned to the variable comes from it.
2. Some `os.environ['FOMO_DATABASE_PATH'] = <anything>` appears before `django.setup()`. The
   value is never inspected.
3. The setup cell *reads* `DATABASES['default']['NAME']` (`_reads_resolved_database_name`).
   Printing the value passes; the README and plan 37.1-05 both require a check that refuses to
   continue.
4. The committed output names a `fomo-notebook-db-*` path. That output can predate the current
   source, because nothing requires one fresh top-to-bottom run (for example, consecutive
   `execution_count`s 1..N). Plan 37.1-06 ran that check once by hand, but the guard does not.

I confirmed two bypasses by calling `isolation_problems()` on modified copies of
`import_campaign_csv_demo.ipynb`. Both returned `[]`:
- **Assignment bypass:** set
  `os.environ['FOMO_DATABASE_PATH'] = str(repo_root_path / 'src' / 'fomo_db.sqlite3')`, turn
  the `assert` into a `print`, and keep the old committed output. Re-executing that notebook
  writes to the developer database. This is exactly the regression the module exists to block
  (G-37.1-3).
- **Detection bypass:** remove the routing and replace `django.setup()` with
  `from django import setup as _s; _s()`. `django_setup_cells()` then finds no setup cell, so the
  notebook counts as "not Django-backed" and is not checked at all.
  `test_the_real_notebook_check_is_not_vacuous` catches this only for the four notebooks it
  names. It would miss the same edit in `backfill_lco_observations_demo`,
  `campaign_lifecycle_demo`, `load_telescope_runs_demo` or `reconcile_campaign_runs_demo`.

Other gaps of the same kind:
- Assignments inside an unexecuted `def` or `if False:` body still satisfy
  `node.lineno < setup_line`, because `ast.walk` descends into them.

**Fix:**
```python
# 1. The assigned value must be built from the mkdtemp result, e.g. require the Assign value to
#    reference `scratch_db_path`, and `scratch_db_path` to be assigned from `scratch_db_dir / ...`,
#    and `scratch_db_dir` from the mkdtemp call -- top-level statements only (iterate tree.body,
#    not ast.walk).
# 2. Require an enforcing check, not a read: a top-level `ast.If` whose test compares the resolved
#    name to `scratch_db_path` and whose body is an `ast.Raise`; reject `ast.Assert`.
# 3. Require one fresh run, so the committed output belongs to the current source:
counts = [c.get('execution_count') for c in code_cells]
if counts != list(range(1, len(code_cells) + 1)):
    problems.append(f'code cells were not executed once, top to bottom: {counts}')
# 4. Detect Django use without relying on the literal `django.setup` spelling: treat any notebook
#    whose code imports `django` (ast.Import/ast.ImportFrom with module 'django*') as Django-backed,
#    and require exactly one setup cell in it.
```

### WR-14: The three 37.1-05 notebooks guard the resolved path with `assert`, which `python -O` strips, before running `migrate`

**File:** `docs/notebooks/pre_executed/import_campaign_csv_demo.ipynb` (setup cell, code cell 1), `docs/notebooks/pre_executed/sync_gemini_observation_calendar_demo.ipynb` (setup cell, code cell 1), `docs/notebooks/pre_executed/telescope_runs_demo.ipynb` (setup cell, code cell 1)

**Issue:** Each setup cell checks
`assert resolved_db_name == str(scratch_db_path), (...)` and then immediately runs
`_call_command('migrate', verbosity=0)`.

The assert matters in one realistic case: `settings.py` imports `local_settings.py` last, and
CLAUDE.md says production overrides of `DATABASES` belong there. If that file overrides
`DATABASES`, the resolved name is not the scratch path, and the assert is the only thing that
stops `migrate` (and every later write) running against that database. Under `python -O`, or
any kernel started with `PYTHONOPTIMIZE`, the assert is compiled away.

Phase 34's WR-08 fixed exactly this in `project_observation_calendar_demo`. Its cell says so:
"raise rather than assert, which `python -O` strips". Plan 37.1-06 restated it, but plan
37.1-05 did not carry it into these three notebooks. The plain string comparison also differs
from the projector notebook's `Path.resolve()` comparison.

**Fix:** Use the same shape in all three setup cells, then re-execute and commit them:
```python
if Path(resolved_db_name).resolve() != scratch_db_path.resolve():
    raise RuntimeError(
        'This notebook must never write to the developer or live database -- resolved DB '
        f'{resolved_db_name!r} is not the scratch database {str(scratch_db_path)!r}.'
    )
```
WR-13's item 2 then makes the guard enforce this.

### WR-15: The attribution page still relies on Bootstrap 4 classes that Bootstrap 5.3 ignores; the High-band row marker no longer renders, and the new guard cannot see it

**File:** `src/templates/campaigns/attribution_queue.html:8-9, 63-64, 169-170` (plus `font-weight-bold`/`font-weight-normal` on lines 6, 9, 27, 42, 53, 56, 85-88, 143, 148, 159, 162, 187-190, 229, 249-250, 261-262); `src/templates/campaigns/campaign_list.html:6, 29, 40`

**Issue:** G-37.1-1 was "Bootstrap 4 spelling is inert under the Bootstrap 5 that
`tom_common/base.html` loads". The fix changed only the two collapse data attributes. The same
page still uses Bootstrap 4 utility classes that Bootstrap 5 removed: `border-left`,
`font-weight-bold`, `font-weight-normal`, `mr-2` and `form-inline`. The CSS actually loaded is
Bootstrap 5.3.3 from django-bootstrap5, and no compatibility stylesheet exists in
`tom_common/static` or `src/static`.

The visible effect is on High-band candidate rows:
- They are marked with `class="border-left border-success" style="border-left-width: 4px;"`.
- In Bootstrap 5, `.border-left` does not exist, and `.border-success` sets only
  `border-color`. With no `border-left-style`, the left bar is never drawn.
- So the High-band emphasis that UI-SPEC gives the confirmable rows is gone, and only the
  checkbox and badge remain.

Other effects:
- The band filter loses its inline layout (`form-inline`) and the label's `mr-2` spacing.
- Every `font-weight-bold` label renders at normal weight.

`campaign_list.html` now mixes `me-2` (the new button, line 10) with `mr-2` (lines 29 and 40) in
the same file.

`TestTemplatesUseBootstrap5DataAttributes` scans only `data-*` plugin attributes, so this class
of defect stays invisible to the suite.

**Fix:**
- `class="border-start border-4 border-success"` (drop the inline `border-left-width`)
- `font-weight-bold` → `fw-bold`, `font-weight-normal` → `fw-normal`, `mr-2` → `me-2`
- `<form class="d-flex align-items-center gap-2 mb-4">` in place of `form-inline`
- the `<select>` → `form-select form-select-sm`

Then extend the template guard with a second pattern for removed Bootstrap 4 classes, matched
inside `class="..."` values:
```python
BOOTSTRAP4_CLASS = re.compile(
    r'class="[^"]*\b(?:font-weight-(?:bold|normal|light)|border-(?:left|right)|[mp][lr]-\d|form-inline|text-(?:left|right)|float-(?:left|right))\b'

```

### WR-16: The README misstates how the notebooks isolate themselves; three notebooks still byte-copy the live developer database

**File:** `docs/notebooks/README.md:28-35`

**Issue:** The README says each notebook "either migrates a fresh database ... (most notebooks),
or takes a read-only snapshot of `src/fomo_db.sqlite3` with SQLite's online backup when it needs
the real records (`project_observation_calendar_demo`)".

Of the eight notebooks the README covers (and the guard enforces), four do not match that:
- `campaign_lifecycle_demo`, `load_telescope_runs_demo` and `reconcile_campaign_runs_demo` each
  run `shutil.copy2(dev_db_path, scratch_db_path)`.
- Only four of eight start from a fresh database, so "most notebooks" is also wrong.

The byte copy is the hazard that `project_observation_calendar_demo`'s own prose names: "the
unattended runner may be writing the developer database at the same moment, and the backup API
copies a consistent snapshot where a byte copy could catch it mid-write". The developer database
runs in rollback-journal mode (`journal_mode=delete`). A `copy2` taken during a runner write
transaction can therefore capture a half-written main file without its `-journal`, which is a
corrupt or inconsistent scratch copy. The guard does not check how a copy is made, so it cannot
flag this.

A minor point: line 25 runs straight into the `##` heading on line 26 with no blank line.

**Fix:**
- Make the README accurate: list which notebooks snapshot and which start fresh, and require the
  `mode=ro` + `Connection.backup()` snapshot for any notebook that needs real records.
- Convert the three `shutil.copy2` notebooks to the projector notebook's backup block. They are
  outside this review's file list, so track it as a follow-up if it is not done now.
- Add a guard check:
```python
for call in _calls(tree, 'shutil.copy2') + _calls(tree, 'shutil.copy') + _calls(tree, 'shutil.copyfile'):
    problems.append('the setup cell byte-copies a database; use a mode=ro connection and Connection.backup()')
```

### WR-17: The regenerated `telescope_runs_demo` output reports the horizon dip as "85.2647 arcmin deg"

**File:** `docs/notebooks/pre_executed/telescope_runs_demo.ipynb` (code cell 5, "Horizon dip")

**Issue:** `horizon_dip()` returns an astropy `Quantity` in arcminutes
(`solsys_code/telescope_runs.py:141-180`). The cell formats it with
`f'... {dip:.4f} deg'`, so the committed output reads
`horizon dip at 2347 m: 85.2647 arcmin deg`.

Directly below it, the cell's own comment says the reference is "1.44 deg +/- 0.02", and the
notebook introduction says the helper returns the correction "in degrees". A reader of the paired
doc sees a dip of "85 ... deg", which contradicts the Stage-1 precision constraint the notebook
is meant to demonstrate. Plan 37.1-05 re-executed this cell and committed the mislabelled output
(it changed from "2345 m: 85.2350 arcmin deg"). Nothing asserts the value, so the cell cannot
catch a regression in `horizon_dip()` either.

**Fix:**
```python
import astropy.units as u

dip = horizon_dip(site.altitude)
print(f'horizon dip at {site.altitude:.0f} m: {dip.to(u.deg).value:.4f} deg')
# Reference (EPHEM-03): at Las Campanas (2402 m), dip should be 1.44 deg +/- 0.02.
assert abs(horizon_dip(2402).to(u.deg).value - 1.44) <= 0.02
```

### WR-18: Undo on a Dismissed row folds the section and returns to page 1 every time, so working down the dismissal list needs a re-open and re-page per row

**File:** `src/templates/campaigns/attribution_queue.html:249-259`; the cause is in `solsys_code/campaign_views.py:1386-1393` and `solsys_code/campaign_tables.py:612-645`

**Issue:** The template opens Dismissed only when `dismissed-page` or `dismissed-sort` is in
`request.GET`. Each Undo button posts a form that carries only `action`/`kind`/`orphan_pk`/`run_pk`
(no `band`, no page, no sort). `_redirect()` then sends the browser to the bare
`campaigns:attribution` URL, or to `?band=` when the posted form carried one, which these do not.

So every Undo from Dismissed lands on a page where Dismissed is folded shut, the table is back on
page 1, and the band filter has been dropped. The same happens after Undo from Confirmed: the
undone pair moves into the Dismissed section, which the reload has just folded away.

The runbook text added in this phase says the Dismissed section "stays open while you page
through it" and is where a dismissal is "fully reversible". That is true of paging, but the
action the section exists for (Undo) undoes the open state each time. This is the same
reachability problem G-37.1-1 set out to fix.

**Fix:** Carry the worklist state through the Undo forms, and preserve a whitelist of parameters
in `_redirect()`:
```python
# campaign_tables.py render_actions(): add hidden inputs for the request's band / dismissed-page /
# dismissed-sort / confirmed-page values (format_html-escaped).
# campaign_views.py:
_PRESERVED = ('band', 'dismissed-page', 'dismissed-sort', 'confirmed-page', 'confirmed-sort')

def _redirect(self, request):
    params = {k: request.POST[k] for k in _PRESERVED if request.POST.get(k)}
    if params.get('band') not in _ATTRIBUTION_BANDS:
        params.pop('band', None)
    url = reverse('campaigns:attribution')
    return redirect(f'{url}?{urlencode(params)}' if params else url)
```
Add a render test: POST an undo carrying `dismissed-page=1`, follow the redirect, and assert that
`#attribution-dismissed-section` has `show`.

### IN-14: The notebook guard reads notebook JSON with the locale's default encoding

**File:** `solsys_code/tests/test_pre_executed_notebooks.py:254, 269`

**Issue:** `json.loads(path.read_text())` decodes with the locale's preferred encoding. The
notebooks contain non-ASCII text ("—", "°", "≥", "→"). On a non-UTF-8 locale (for example a

### IN-17: Scratch teardown removes the database file under an open Django connection, and a failed run leaves a full developer-database copy in `/tmp`

**File:** all four notebooks in scope (last code cell); `docs/notebooks/README.md:34-35`

**Issue:** `shutil.rmtree(scratch_db_dir, ignore_errors=True)` runs while Django's
`connections['default']` still holds the SQLite file open. On Linux this works (the inode is
freed later), but `ignore_errors=True` would hide a failure on platforms that lock open files.

If any earlier cell raises, `nbconvert --execute` stops and the teardown never runs. For
`project_observation_calendar_demo` that leaves a full snapshot of the developer database in
`/tmp/fomo-notebook-db-*`: user password hashes, DRF tokens and sessions. `mkdtemp` makes the
directory mode 0700, so only the same user can read it, but nothing tells the operator to clean
it up.

**Fix:** In the teardown, call `from django.db import connections; connections.close_all()`
before `rmtree`. Add a README line telling the operator to remove any leftover
`fomo-notebook-db-*` directories after a failed execution, or register the cleanup with
`atexit` in the setup cell as well.
