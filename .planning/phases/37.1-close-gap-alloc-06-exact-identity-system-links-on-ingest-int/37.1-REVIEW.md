### IN-46: The requirement-to-evidence table cites two sections by names that appear nowhere in the notebook

**File:** `docs/notebooks/pre_executed/project_observation_calendar_demo.ipynb` cell `35debc54` (source lines
1242 and 1245 of the JSON; output lines 1225 and 1227)

**Issue:** The table points the reader at evidence by quoted section name:

- PROJ-01's evidence is `cells under "Per-corpus reconciliation"`.
- PROJ-03's evidence is `"Per-marker tally" cell`.

Neither name exists in the notebook. The PROJ-01 evidence is under the heading "The whole real corpus, not a sample
(ROADMAP criterion 1)" (line 888). The PROJ-03 evidence is the cell that prints "Projected events by stage marker:"
(line 976), which has no heading of its own. "Per-corpus reconciliation" survives only as a step title in
`34-04-PLAN.md:164`, so the table quotes the plan's wording, not the notebook's. Every other row's quoted name ("The
receiver, demonstrated", "The one-time takeover") does match a real heading.

The table has carried this since `a87f5f8` (34-04). The re-run re-committed it as evidence, and no earlier round
raised it. A reader following PROJ-01 or PROJ-03 to its evidence will search for a heading that is not there.

**Fix:** Quote the real headings, then re-run the notebook, or, because the change is to a literal string, edit the
source and the stored output identically:

```python
(
    'PROJ-01',
    'One CalendarEvent per LCO/SOAR record, keyed by the facility URL',
    'cells under "The whole real corpus, not a sample"',
),
...
('PROJ-03', 'Exactly one marker, stage-correct', '"Projected events by stage marker" cell'),
```

### IN-47: The committed run made no observed-telescope lookups and no portal calls, but cell `7e7bd66e` gives those calls as the reason the notebook is pre-executed and points to "the lookup's counts" as what the cells show

**File:** `docs/notebooks/pre_executed/project_observation_calendar_demo.ipynb` cell `7e7bd66e` (JSON lines 33 and
35-36); its outputs in cells `4b61a527`, `65e111fa` and `556d2a9f`

**Issue:** This run reports `site_lookups: 0, site_lookup_failed: 0` for both facilities in the dry run, the first
sweep and the second sweep. The one failed lookup the previous run showed (`4276100`) is gone. Since
`resolve_observed_site()` calls the portal only when it makes a lookup (`project_observation_calendar.py:91-101`), and
no other cell makes a network call, the committed run made **no** LCO portal call.

Cell `7e7bd66e` says two things about this:

- The new sentence says "This notebook's own cells show the lookup's counts, not which block it reads."
- The next paragraph says the notebook "makes **real LCO Observation Portal calls** (the one-time observed-telescope
  lookup, D-07/D-08)" as its reason for living in `pre_executed/`.

Both are true as statements about what a run can do. But the output beside them shows the lookup's counts only as
zeros, which is easy to read as "the lookup ran and found nothing to do". It also shows no portal call at all.
Cell `556d2a9f`'s printed explanation ("The first sweep's `updated` count includes every record whose title gained
its observed-telescope token during that same run ...") likewise describes work this run did not do. That is the
zero-work-evidence class of open IN-16, now extended to the lookup.

Low stakes: nothing here is false, and a future run on a database with a newly observed record will show non-zero
counts again.

**Fix:** Qualify the sentence so it stays true whichever way a run goes. For example: "This notebook's own cells
show only the lookup's counts (`site_lookups`/`site_lookup_failed` in each sweep summary), not which block it reads;
a run on a copy where every observed record already has its telescope makes no lookup and so no portal call, and
those counts are then zero." This is a markdown-only edit, and no re-execution is needed.
