**Reviewed:** 2026-10-02

## Summary

Reviewed the exact-identity system-link matcher (`campaign_system_links.py`), its single writer
(`campaign_utils.create_system_link`), both ingest call sites, the D-09 change to
`orphan_calendar_events()`, the D-05 label surfaces (table, admin inline, model), the runbook and
both re-executed notebooks. I traced each call chain into `allocation_projector`,
`campaign_reconciler`, `campaign_views` and the observation projector.

The locked constraints hold on the main paths:
- The matcher never imports or calls the similarity scorer.
- Only the two ingest commands call `attempt_system_link()`. No view or receiver calls it.
- Only APPROVED runs with both window dates are candidates.
- Containment is inclusive on UTC dates (`coerce_schedule_datetime` normalises to UTC before `.date()`).
- The dismissal veto is applied after the pick, so it never re-routes a link.
- `get_or_create(observation_record=...)` never re-points an existing link.
- Re-runs are idempotent.
- Per-record exceptions write the class name only.

The targeted test modules pass (81 tests, `python manage.py test ... --noinput`), and pinned ruff
is clean. No `./manage.py` invocation was introduced.

Three problems need attention:
- **Lost links reported as written.** A database error inside the post_save receiver chain
  silently rolls back the link row, but the row is still reported and counted as written. I
  reproduced this with a probe test. It breaks the D-08 "a failed write is counted under links
  skipped" contract.
- **Staff undo paths that the next tick reverts.** Several staff undo paths look like they work
  but are reverted by the next unattended tick: admin-inline delete, the Confirmed table's
  event-row Undo (reproduced), and deleting a user account.
- **Gaps left by D-09.** D-09 left the server-side event confirm gate and the calendar pop-up hint
  out of step with the new "a record's own event is never an event orphan" rule.

## Critical Issues

### CR-01: A link rolled back by the post_save receiver is still reported and counted as "System-linked"

**File:** `solsys_code/campaign_utils.py:1036-1040`, `solsys_code/campaign_system_links.py:240-255`, `solsys_code/allocation_projector.py:1648-1658`
**Issue:** `create_system_link()` returns the `created` flag from `get_or_create()`. Django creates
the row inside `get_or_create()`'s own `transaction.atomic()` savepoint, and the
`CampaignRunObservation` post_save receiver runs inside that savepoint.

The receiver catches every exception (`except Exception` at `allocation_projector.py:1652`). But a
failed ORM write inside `reproject_allocation_if_dispatched()` has already set
`connection.needs_rollback` through `Model.save_base()`'s `mark_for_rollback_on_error`. When the
savepoint then exits normally, Django rolls it back without raising. The link `INSERT` is undone,
yet `get_or_create()` still returns `(obj, True)`.

As a result, `attempt_system_link()`:
- prints `System-linked ObservationRecord ...`
- returns `OUTCOME_LINKED`
- is counted under `system links: N`, which reaches `WatchedProposal.last_run_summary` and the log.

No link row exists. If the receiver failure persists, every tick reports the same phantom link
and the record is never linked. This breaks the D-08 contract the phase brief calls out: a
failed per-record write must be counted under `links skipped`.

I reproduced it with a probe `TestCase`. It patched `reproject_allocation_if_dispatched` to perform
one failing save (a duplicate link row), then called `create_system_link(record, run)`. Result:
`created= True row exists= False`, with the receiver logging `receiver_on_run_observation_save
failed ... IntegrityError`.

Three gaps hide this from the existing tests:
- `test_a_failing_write_is_skipped_and_never_leaks_the_message` patches `create_system_link`
  itself to raise.
- `test_a_failing_link_write_is_counted_and_the_sweep_continues` does the same.
- No test covers a failure inside the receiver.

**Fix:** Give the receiver's re-projection its own savepoint, so a projection failure rolls back
only the projection and never the caller's write. Then re-verify in the writer so the reported
outcome is always backed by a row.
```python
# allocation_projector.receiver_on_run_observation_save (and the _delete twin)
try:
    with transaction.atomic():
        reproject_allocation_if_dispatched(run)
except Exception as exc:  # noqa: BLE001
    logger.warning(...)
    return

# campaign_utils.create_system_link
with transaction.atomic():
    link, created = CampaignRunObservation.objects.get_or_create(
        observation_record=record, defaults={'run': run, 'confirmed_at': timezone.now()},
    )
if created and not CampaignRunObservation.objects.filter(pk=link.pk).exists():
    raise IntegrityError('system link rolled back by a post_save receiver failure')
return created
```
Add a regression test that patches `reproject_allocation_if_dispatched` to do a failing save and
asserts `OUTCOME_SKIPPED` (or, with the receiver fix, that the link row exists).

## Warnings

### WR-01: Deleting a system link from the run's admin inline is reverted on the next tick

**File:** `solsys_code/admin.py:134-160`, `solsys_code/admin.py:329-330`; `docs/runbooks/telescope_runs_calendar.rst:640-643`
**Issue:** `CampaignRunObservationInline` keeps Django's default `can_delete=True`.
`save_formset()` deletes the marked rows with a bare `obj.delete()`, which writes no
`ObservationRecordDismissal`. `find_exact_run()`'s only veto is a dismissal row
(`campaign_system_links.py:196-200`). The next discovery tick therefore finds the record unlinked
and undismissed, re-creates the system link and re-retires the allocation night.

A staff member who removes a machine link in the admin, which the runbook now points them to
("and in the run's admin inline the same way"), has a human decision silently overridden. That
contradicts "human outranks machine". The attribution page's Undo writes the dismissal; the admin
does not.
**Fix:** In `save_formset`, when deleting a `CampaignRunObservation` whose `confirmed_by_id is None`,
`get_or_create` an `ObservationRecordDismissal(observation_record=obj.observation_record, run=obj.run,
defaults={'dismissed_by': request.user, 'dismissed_at': now(), 'reason': 'Removed in admin.'})`
inside the same atomic block. Alternatively, set `can_delete = False` on the inline and direct staff
to the attribution page's Undo. Either way, add one sentence to the runbook's "What links by
itself" paragraph.

### WR-02: Each system link appears twice in the Confirmed table, and the event row's Undo is reverted by the next reconcile

**File:** `solsys_code/campaign_views.py:1209-1225`, `solsys_code/campaign_tables.py:693-735`, `solsys_code/allocation_projector.py:984-1000`; `docs/runbooks/telescope_runs_calendar.rst:715-723`
**Issue:** A system link makes `_sync_observation_attribution()` adopt the record's own event, which
sets `CalendarEventMeta.run`. `_confirmed_attribution_rows()` lists `CalendarEventMeta(run__isnull=False)`
and `CampaignRunObservation` side by side, so every system-linked pair produces two Confirmed rows:
- a record row reading "System (exact match)"
- an event row with a blank confirmer

Each row has its own Undo button.

Clicking the event row's Undo calls `unlink_event_from_run()` and writes a `CalendarEventDismissal`.
Two problems follow:
- The `CampaignRunObservation` survives, so the next reconcile re-adopts the event.
  `adopt_event_into_run()` never reads `CalendarEventDismissal`.
- Under D-09 the event is never shown in a worklist, so the dismissal it wrote is dead data.

I reproduced the revert with a probe: Confirmed rows `['CampaignRunObservation', 'CalendarEventMeta']`.
`meta.run` was `None` after the event Undo and back to the run after `reconcile_run(run)`.

The runbook tells staff to "use the same Undo button in the Confirmed table" without saying which
of the two rows to use. The new D-05 docstring on `render_confirmed_by` even acknowledges the
"adopted record event" row. The double listing also cuts against the phase's "count a record and
its event once" goal.
**Fix:** In `_confirmed_attribution_rows()`, exclude event rows that belong to a linked record:
`CalendarEventMeta.objects.filter(run__isnull=False).exclude(observation_record__campaign_run_links__isnull=False)`.
Or render no Undo action for a `CalendarEventMeta` row whose `observation_record_id` is set, with
a note that it follows its record. Add a test asserting one Confirmed row per system-linked pair.

### WR-03: Deleting a staff user turns every link they confirmed into a "System (exact match)" link

**File:** `solsys_code/models.py:620-628`, `solsys_code/models.py:651-661`; `solsys_code/campaign_tables.py:693-703`; `solsys_code/admin.py:154-160`
**Issue:** `CampaignRunObservation.confirmed_by` is `on_delete=SET_NULL`. The phase makes
`confirmed_by IS NULL` the *only* system-link provenance (model docstring: "``confirmed_by`` is the
only provenance"). Removing a departed staff member's account therefore rewrites every link they
confirmed. The table and admin then label those links "System (exact match)", a provenance claim
that is false.

`allocation_projector._sync_observation_attribution()` already keys its machine-vs-human guard on
`confirmed_by__isnull=True`, so those adopted events also lose the human guard. Before 37.1 a null
confirmer only meant "unknown". Now it actively asserts machine provenance.
**Fix:** Switch `confirmed_by` to `on_delete=models.PROTECT`, which forces deactivation rather than
deletion of staff accounts. Otherwise, the phase must accept a small provenance marker after all,
such as a `system_linked` boolean set only by `create_system_link()`, contrary to D-05/D-07's "no
new field". At minimum, document in the runbook that staff accounts must be deactivated, never
deleted.

### WR-04: The admin inline can re-point an existing system link to another record and it still reads as a machine link

**File:** `solsys_code/admin.py:151-152`, `solsys_code/admin.py:305-311`
**Issue:** The inline excludes `confirmed_by` but leaves `observation_record` editable on existing
rows. `save_formset()` stamps `confirmed_by` only when `instance.pk is None`. A staff member who
changes an existing system link's record in the inline therefore produces a human-chosen pair
that keeps `confirmed_by=None`. It renders as "System (exact match)" and is treated as machine
attribution by `_sync_observation_attribution()`'s unlink half. Before this phase, the same edit on
a staff link kept the original confirmer, which was arguably wrong too. Now it also fabricates
machine provenance.
**Fix:** Make `observation_record` read-only for existing rows. Override
`get_readonly_fields(request, obj)` on the inline, or use a formset that disables the field when
`instance.pk` is set, so re-pointing requires delete + add, which stamps the staff user. Or, in
`save_formset`, re-stamp `confirmed_by`/`confirmed_at` whenever `'observation_record' in form.changed_data`.

### WR-05: `is_offered_candidate('event', ...)` still accepts a record's own event, out of step with D-09

**File:** `solsys_code/campaign_attribution.py:877-911`; `solsys_code/campaign_views.py:1386-1406`
**Issue:** D-09 says a record-backed event "is attributed only through its record". However,
`is_offered_candidate('event', pk, run_pk)` (the server-side gate for every confirm POST) only
checks `telescope_label_meta.run_id`. It does not check `observation_record`. Two kinds of POST
still pass:
- a stale page loaded before deploy
- a hand-crafted `action=confirm&kind=event` for a record-backed event

Either one writes `CalendarEventMeta.run` with `confirmed_by=<staff>` directly onto the record's
event. The record itself stays unlinked and remains in the record worklist. If staff then confirm
the record to a different run, `adopt_event_into_run()` refuses the adoption, and the record and
its event disagree permanently. The function's own docstring promises it re-derives "orphan still
unattributed" from the same rules the queue uses, so the gate should apply the same exclusion as
`orphan_calendar_events()`.
**Fix:**
```python
if kind == 'event':
    if not orphan_calendar_events().filter(pk=orphan_pk).exists():
        return None
    event = CalendarEvent.objects.get(pk=orphan_pk)
    candidates = candidates_for_event(event)
```
Add a view test that POSTs an event confirm for a record-backed event and expects "claimed".

### WR-06: The calendar pop-up still shows "Possible campaign run match" for a record's own event and links to a queue that no longer lists it

**File:** `src/templates/tom_calendar/partials/event_form.html:217-245`, `solsys_code/templatetags/attribution_display_extras.py:23-39`; `docs/runbooks/telescope_runs_calendar.rst:745-747`
**Issue:** The hint renders for any staff-viewed event with no `run`, using
`candidates_for_event()` filtered to the High band. It links to `attribution?band=high`. After D-09
a record-backed event is never on that page. Its record is scored separately by
`candidates_for_record()`, where `telescope_code` is always `None`, so the telescope signal falls to
its weaker tiers. The record can therefore sit in Medium, or be absent, while the event shows a
High hint. The link then lands on a High-band page where neither the event nor its record appears.

The runbook's new claim ("still links to the queue, where its record is the row to confirm") is
true only when the record also scores High. The hint also still shows for a record that is already
linked but whose event adoption was blocked.
**Fix:** Have `high_band_attribution_candidates` return `[]` when
`CalendarEventMeta.objects.filter(event=event, observation_record__isnull=False).exists()`.
Alternatively, compute the hint from the record (`candidates_for_record(meta.observation_record)`)
and link without the `band=high` filter. Then align the runbook sentence with the chosen behavior.

### WR-07: The campaign fallback links an observation of a *different moving object* to another object's run

**File:** `solsys_code/campaign_system_links.py:108-143`
**Issue:** Step 2 fires for any record whose target carries no same-proposal run, not only for
field pointings. Consider a campaign holding comets A and B, with exactly one APPROVED dated run
under proposal P, for A. A record of comet B observed under P inside A's window (B is a legitimate
non-sidereal target with no run of its own) is linked to A's run with no human involved. A's
allocation night is retired by an observation of B.

This conforms to D-11 step 2 as written. However, the scenario D-11 targets, the Didymos field
pointings, is distinguishable: those targets are SIDEREAL field targets created by
`--create-missing-targets`. Every other FOMO target is non-sidereal (CLAUDE.md). "Anything partial
or ambiguous stays in the queue" argues against linking a different named object.
**Fix:** Restrict the fallback to field-pointing records, for example:
```python
if record.target.type != Target.SIDEREAL:
    return None
```
If the broader rule is intentional, record that choice in the CONTEXT and runbook, and add a test
showing the different-comet case links.

## Info

### IN-01: The exact-identity rule ignores telescope and instrument

**File:** `solsys_code/campaign_system_links.py:181-192`
**Issue:** Proposal + target + window is the whole key (D-11, locked). Two runs under one proposal,
target and window on different telescope classes (e.g. 1m0 and 2m0) correctly fall to the queue as
ambiguous. But when only one exists, say the 2m0 run, a 1m0 observation of the same target under
the same proposal is linked to it and retires a 2m0 allocation night.
**Fix:** Consider a cheap extra guard when `run.telescope_class` is set and the record's instrument
class is known (`extract_instrument` / aperture class): leave the record in the queue on a mismatch.
Otherwise, note the limitation in the runbook's "What links by itself".

### IN-02: Unterminated sweep lines glue onto the link lines in the unattended log

**File:** `solsys_code/management/commands/backfill_lco_observations.py:633-683,723-727,810`; `solsys_code/campaign_system_links.py:211-213`
**Issue:** The new docstring says every link line ends with `\n` so the runner's
`io.StringIO().splitlines()` gives one log record per line. But the sweep's own
`Would ...`/`Skipping ...`/`Failed to resolve ...` writes have no newline. Under `step_discovery`'s
plain StringIO capture, a dry-run `Would system-link ...` line is appended to the previous
`Would reuse target ...` text and to everything since the last newline. A real-run stderr `System
link check failed ...` line likewise glues onto a preceding `Failed to resolve observed block ...`.
The gluing itself predates this phase, but the new D-04 one-line-per-link promise relies on it not
happening.
**Fix:** Terminate the sweep's own `stdout.write`/`stderr.write` calls with `\n`. `OutputWrapper`
does not double an existing newline.

### IN-03: The outcome tally is copied three times

**File:** `solsys_code/management/commands/backfill_lco_observations.py:748-753,794-798`; `solsys_code/management/commands/backfill_lco_observation_records.py:248-255`
**Issue:** The same `if outcome in (OUTCOME_LINKED, OUTCOME_WOULD_LINK): ... elif outcome ==
OUTCOME_SKIPPED:` block appears in three places, which invites drift if an outcome is added.
**Fix:** Return a small counter object from `campaign_system_links` (e.g. a `SystemLinkTally` with
`.record(outcome)` and `.summary(dry_run)`), or reuse the records command's local
`offer_for_system_link` closure pattern in the sweep.

### IN-04: The runbook's "What links by itself" understates when the Didymos backfill links

**File:** `docs/runbooks/telescope_runs_calendar.rst:618-621`
**Issue:** It says `backfill_lco_observation_records` links "when it is re-run over records it
already created". The command also links every record it newly creates, after the status refresh,
as the section at `:333-344` correctly says.
**Fix:** Reword to "-- and ``backfill_lco_observation_records``, for the records it creates and the
ones it re-encounters on a re-run --".

### IN-05: A dismissal written between the match and the write is not honored

**File:** `solsys_code/campaign_system_links.py:196-200,240-241`; `solsys_code/campaign_utils.py:1036-1040`
**Issue:** The dismissal veto is read in `find_exact_run()`. `create_system_link()` writes later
without re-checking, so a staff dismissal that commits in between is bypassed. The window is
narrow, and the link can be undone.
**Fix:** Inside `create_system_link()`'s atomic block, return False when
`ObservationRecordDismissal.objects.filter(observation_record=record, run=run).exists()`.
