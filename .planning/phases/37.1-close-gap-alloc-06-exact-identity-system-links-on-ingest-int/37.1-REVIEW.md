## Summary

Scope: `git diff fe15b0ca..HEAD` on the 19 listed files. That covers FOMO's own schedule-block rule
(`observation_blocks.py`), the facility subclasses used by both backfill commands and by the
unattended status poll, `--recheck-unscheduled`, the `is_web_url` filter with the event-form
change, and the Bootstrap 5 templates on the attribution tables. I traced each call into the
installed TOM Toolkit code (`tom_observations/facility.py:555-579`, `facilities/ocs.py:180-187` and
`1548-1575`).

What holds up:
- The tier order in `select_schedule_block()` matches the stated rule. All three callers share
  the one function: the embedded path in `_resolve_schedule`, the live path through
  `FomoLCOFacility.get_observation_status`, and `resolve_placement_block`.
- The unattended runner never passes the flag, and a test pins that.
- `is_web_url` handles `javascript:`, `data:`, upper-case schemes, protocol-relative URLs,
  embedded tab/newline characters and leading C0 control characters correctly. Every one is
  either rejected or parsed exactly as a browser would parse it, and Django autoescapes the
  `href`.
- Every new `Target` fixture uses `NonSiderealTargetFactory`.

The main defect: the discovery sweep still writes empty times plus the new failed state when
its live lookup fails. The F2 finished-record skip then freezes that record with no times. The
docstring and runbook text that 37.1-08 rewrote now claim this cannot happen. Smaller problems:
the recheck can blank a partly-filled record, the new FOMO-owned portal method has no timeout and
turns a malformed reply into "no block", the recheck's credential-hygiene rule is not applied to
the line just below it, and the rule treats a FAILED block as one that never ran.

## Critical Issues

### CR-01: A failed live lookup in the discovery sweep erases stored times and writes the failed state, and the F2 skip then never looks at the record again

**File:** `solsys_code/management/commands/backfill_lco_observations.py:694-702` (with `:412-413` and the 37.1-08 docstring at `:372-390`)
**Issue:** `_resolve_schedule()` returns `(None, None, True, embedded)` when the live
`get_observation_status()` call raises. However, `compare_schedule = embedded or (lookup_needed and not dry_run)`
is still True for that request. `_changed_record_fields()` therefore records two changes: the
new portal `status`, and `scheduled_start = scheduled_end = None`. The update branch then saves
both (`:793-799`). On the next tick the record matches its portal state, that state is a failed
state, and it has no times. The gate at `:412-413` returns `recheck_unscheduled or status not in failed_states`,
which is False, so the record is never looked up again.

A concrete path that loses data: a PENDING record holds its block's times, so its allocation
night is retired. Its request moves to WINDOW_EXPIRED after one block was ABORTED. The poll's
per-record call fails for this record (it is skipped and logged, nothing is written), or
the poll step itself fails. Discovery then sees the state change, its lookup also fails (a
transient 5xx or a timeout), and it writes `WINDOW_EXPIRED` with no times. Under D-05 the
allocation night comes back. The F2 skip then hides the record permanently, unless an
operator happens to run `--recheck-unscheduled`. This is exactly the G-37.1-1-alloc symptom
that 37.1-07/08 set out to remove. A brand-new request whose first lookup fails while it is
already in a failed state ends up frozen the same way.

The 37.1-08 docstring ("it was resolved with FOMO's block rule when it reached that state, so
it already holds whatever block the request had") and the runbook sentence "the per-tick skip
stays safe for those records" are false in this case. The runbook even describes the failure
outcome ("updated ... just without resolved schedule times"). No test covers a state-changed
record that already has times when its lookup fails. `test_a_failed_lookup_is_counted_and_never_writes_the_error_text`
starts from a record with no times, so it cannot detect the erasure.
**Fix:** On a failed lookup, never touch the stored schedule, and hold back the state change so
the next tick's "state changed" branch tries again:
```python
compare_schedule = (embedded or (lookup_needed and not dry_run)) and not lookup_failed
...
else:
    changes = _changed_record_fields(record, status, scheduled_start, scheduled_end, parameters,
                                     compare_schedule=compare_schedule)
    if lookup_failed:
        # Keep the stored state so _schedule_lookup_is_needed() sees a state change next tick.
        changes.pop('status', None)
```
For a newly created record whose lookup failed, also store a marker that the gate honours, for
example `parameters['schedule_lookup_failed'] = True`, which the gate treats like "missing
times, not failed". Add a test: an existing PENDING record with times, portal reports
WINDOW_EXPIRED, lookup raises. Expected: times and status unchanged, and the next sweep looks
the record up again.

## Warnings

### WR-01: `--recheck-unscheduled` can write empty times over an existing time (both commands)

**File:** `solsys_code/management/commands/backfill_lco_observation_records.py:292-313`; `solsys_code/management/commands/backfill_lco_observations.py:412-413`
**Issue:** Both recheck gates select a record that is missing either time (`start is None or end is None`).
Neither write path keeps a time that is already stored. The records command calls TOM's
`update_observation_status()` (`tom_observations/facility.py:561-565`), which assigns
`status['scheduled_start']`/`['scheduled_end']` without any check. The sweep compares and
writes both fields because `compare_schedule` is True. Take a record with a start time but no
end time. If the rule now returns no block (because the block became CANCELED or NOT_ATTEMPTED),
or the block carries only one of the two keys, the recheck replaces the stored start with
`None`. In the sweep, a failed lookup does the same (see CR-01). The runbook says a record
"that already has both times is left alone", but a partly filled record gets no such
protection, and no test covers that case (`test_failed_state_missing_one_time_needs_a_lookup_when_rechecking`
tests only the gate).
**Fix:** In the recheck branches, write only the fields the lookup actually filled: skip the
write when both resolved values are `None`, and never replace a non-`None` stored value with
`None`. In the records command this means calling `facility.get_observation_status()` and
setting the fields yourself rather than calling `update_observation_status()`.

### WR-02: FOMO's new portal method makes untimed requests and treats a malformed reply as "no block", which erases times on a write path

**File:** `solsys_code/observation_blocks.py:104-120` (with `:71-72`)
**Issue:** `ScheduleBlockRuleMixin.get_observation_status()` now belongs to FOMO and is called on
every unattended tick. It still calls `make_request()` with no `timeout=` (`ocs.py:180-181` is
just `requests.request(*args, **kwargs)`). A hung portal connection therefore blocks
`step_status_refresh` indefinitely while it holds `command_lock('status_refresh')`.
`calendar_utils.py:97-101` already calls an untimed request in this codebase "a known
anti-pattern", and `resolve_placement_block()` passes `_API_TIMEOUT_SECONDS`.

Separately, `select_schedule_block()` returns `None` for a non-list body. TOM's loop raised on a
malformed body; here `get_observation_status()` returns `{'scheduled_start': None, 'scheduled_end': None}`
instead. `update_observation_status()` then writes `None` over every polled record's times. A
dict body (for example, if the endpoint gains pagination), an error document, or a block
without `start`/`end` would silently remove the placed times from every non-terminal record on
the next tick and bring their nights back, and nothing would report a failure. Leniency is
right for `resolve_placement_block()`, which only reads. It is wrong on a write path.
**Fix:**
```python
from solsys_code.calendar_utils import _API_TIMEOUT_SECONDS  # or move the constant to a shared module
...
response = make_request('GET', ..., headers=self._portal_headers(), timeout=_API_TIMEOUT_SECONDS)
blocks = response.json()
if not isinstance(blocks, list):
    raise ValueError('observations endpoint returned a non-list body')
block = select_schedule_block(blocks)
```
`calendar_utils` imports `observation_blocks`, so put the constant in `solsys_code/constants.py`
to avoid a circular import.

### WR-03: The recheck redacts exception text, but the create-path failure line below it still writes the full exception text

**File:** `solsys_code/management/commands/backfill_lco_observation_records.py:379` (compare `:302-307`)
**Issue:** The new recheck branch writes only `type(exc).__name__`, and its comment explains
why: "a portal exception's text can carry response content". `ImproperCredentialsException`
and `forms.ValidationError` embed `response.content` (`ocs.py:182-185`). Fifteen lines later, in
the same method and on the same `facility.update_observation_status()` call, the create path
still writes `f'... {exc}'` to stderr. The runbook section edited by this phase says a failed
lookup "is logged by the exception's class name only", but that holds for only one of the two
paths. `_resolve_schedule()` at `backfill_lco_observations.py:347` also logs `{exc}` at debug
level.
**Fix:** Use `type(exc).__name__` in both places, as T-37.1-31 and SYNC-09 require, and add a
test that the create path never echoes a marker string placed in the exception.

### WR-04: The rule classes a FAILED block as one that "never ran", although FAILED is a state of an attempted block

**File:** `solsys_code/observation_blocks.py:78-85`; `solsys_code/tests/test_observation_blocks.py:52-54`
**Issue:** The LCO portal's block states include NOT_ATTEMPTED (scheduled, never started) and
FAILED (attempted at the telescope, then failed). Under Phase 35 D-05/D-06 a block that was
placed and started counts as placed-or-observed. That reasoning is what moved ABORTED into the
rule, and it applies to FAILED just as well. The rule silently drops FAILED, and the test that
pins this is named `test_blocks_that_never_ran_give_none`, which is factually wrong for FAILED.
A request whose only attempt FAILED therefore keeps its allocation night, and its calendar
event spans the whole request window. The module docstring, the runbook and 37.1-07's
key decisions never mention FAILED, so the exclusion looks unintended rather than decided.
**Fix:** Either add `FAILED` to the "started" tier (`BlockState.FAILED`) and move the test
assertion, or record the decision to exclude it in the module docstring and the runbook and
rename the test (for example `test_blocks_not_counted_give_none`).

### WR-05: The event form's header comment still says the file below it is an exact upstream copy apart from one block

**File:** `src/templates/tom_calendar/partials/event_form.html:24-25`
**Issue:** The new paragraph at `:19-22` records a second deviation, inside the copied region at
`:57-63`. The sentence just after it still says "Below this point, this file starts as an exact
copy of the upstream partial with one new block inserted after </form>". T-27-20 makes this
comment the upgrade checklist ("diff this file against the upstream path above when
upgrading"). A maintainer who trusts it will re-sync the URL label from upstream and bring back
the `ALLOC:`/`RUN:` dead links and the missing `rel="noopener noreferrer"`.
**Fix:** Reword it to: "...an exact copy of the upstream partial except (1) the URL label block
(G-37.1-1-allocurl) and (2) one new block inserted after </form> (D-08)."

## Info

### IN-01: The bootstrap guard test accepts any Bootstrap version, so it would not catch the mismatch it was written for

**File:** `solsys_code/tests/test_attribution_template.py:184-190`
**Issue:** `startswith('django_tables2/bootstrap')` also passes `bootstrap.html` (Bootstrap 3) and
`bootstrap4*.html`, while the base page is Bootstrap 5. `CampaignRunTable`/`ApprovalQueueTable`
still use `bootstrap4-responsive.html`, which contradicts the new `campaign_tables.py:585/676`
comment that the base page is Bootstrap 5.
**Fix:** Require the `django_tables2/bootstrap5` prefix, with an explicit, commented allow-list
for `CampaignRunTable`, so the exception is visible.

### IN-02: An earlier aborted block hides a request's next placed block, and the aborted night returns once that later block completes

**File:** `solsys_code/observation_blocks.py:56-61`
**Issue:** Take a PENDING request with blocks `[ABORTED night 1, PENDING night 3]`. It is drawn
over night 1, and the night-3 allocation stays even though a block is placed there. When the
night-3 block completes, the COMPLETED tier takes over, the record's times move to night 3, and
night 1 returns as an unused allocation even though data were taken on it. The rule is the
user's decision. But this consequence is not in the runbook, and operators will see it as a
retired night that reappears.
**Fix:** Document the consequence in the runbook section that lists which nights retire (and in
the docstring).

### IN-03: The CLAUDE.md paired-docs map has no entry for the new `observation_blocks.py`

**File:** `solsys_code/observation_blocks.py` (CLAUDE.md "Paired docs" map)
**Issue:** The rule now lives in its own module, which `backfill_lco_observations_demo.ipynb` and
the runbook demonstrate. Without a map entry, a later behaviour change to the tiers will not
trigger the paired-docs requirement (the breach pattern from Phase 35 NF-24).
**Fix:** Add `solsys_code/observation_blocks.py -> backfill_lco_observations_demo.ipynb` plus the
runbook's queue-observation section to the map.

### IN-04: Leftover `refresh_from_db()` with no assertion

**File:** `solsys_code/tests/test_backfill_lco_observation_records.py:811`
**Issue:** `self.record_b.refresh_from_db()` is followed by nothing that reads `record_b`, so the
test never checks that the second record was actually rechecked (it checks only that the URL
was called).
**Fix:** Assert record B's outcome (still no times, status `CANCELED`), or delete the line.

### IN-05: The notebook's PASS checks fail silently

**File:** `docs/notebooks/pre_executed/backfill_lco_observations_demo.ipynb` (cells `b4d47a9b`, `ce089e0c`)
**Issue:** The two new verification cells print `PASS: ...` only when the check holds and print
nothing otherwise. A regenerated notebook whose retire step broke would just be missing a line,
which is easy to miss in review.
**Fix:** Add an `else: print('FAIL: ...')` branch, or use `assert` so execution stops loudly.

### IN-06: Test modules import helpers from other test modules

**File:** `solsys_code/tests/test_unattended.py:45`; `solsys_code/tests/test_backfill_lco_observation_records.py` (imports block)
**Issue:** `portal_side_effect` is imported from `test_observation_blocks`. This works, but it
couples test modules to each other. A rename in one silently breaks collection of the others.
**Fix:** Move shared portal fakes into a non-test helper module (for example
`solsys_code/tests/portal_fakes.py`).
