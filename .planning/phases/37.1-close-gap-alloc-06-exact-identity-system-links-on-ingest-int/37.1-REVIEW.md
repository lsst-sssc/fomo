## Warnings

### WR-19: A FAILED-with-data block now outranks the request's next placed block, so a rescheduled request is drawn as "Scheduled" on a past night, its placed night is not retired, and the failed night's allocation entry comes back once a later block runs

**File:** `solsys_code/observation_blocks.py:151-157`; consequences in
`solsys_code/allocation_projector.py:922-941` (`retired_nights()`), `solsys_code/status_vocabulary.py:263-273`
(`classify_record()`), `solsys_code/unattended.py:308-319` (`step_status_refresh()`)

**Issue:** An LCO request whose block FAILED after taking data usually stays PENDING. The scheduler places a
new block on a later night, until the request completes, its window expires, or it reaches
FAILURE_LIMIT_REACHED (the request state that exists because of repeated FAILED blocks).

For blocks `[FAILED (night 1, time_completed > 0), PENDING (night 3)]`, the new rule returns the night-1
block (`test_failed_with_data_beats_pending_in_either_order` asserts exactly this). Before 37.1-13 the
night-3 PENDING block was returned. The unattended `status_refresh` step runs on every tick for exactly
these non-terminal records. It writes the night-1 times, which has three effects:

1. **The record is drawn as Scheduled on a past night.** `classify_record()` returns `SCHEDULED` for a
   PENDING record with both times, so the calendar shows the record with the `[S]` marker on night 1, a
   block that has already failed. The real upcoming placement on night 3 does not appear anywhere.
2. **The night the scheduler has placed is not retired.** `retired_nights()` retires night 1 only, so
   night 3's `ALLOC:` entry stays drawn as an unused allocation night while the block sits on it. Under
   the old rule, night 3 was retired as soon as it was placed (D-05: "a placed block retires its night").
3. **The failed night's allocation entry returns.** When the night-3 block runs, it becomes COMPLETED (the
   first COMPLETED block wins) or a later started-tier block (the last one wins). Either way the record's
   times move to night 3. `retired_nights()` is recomputed from the record's current times only, so
   `project_allocation()` mints night 1's `ALLOC:` entry again (`allocation_projector.py:1176-1193`), for
   a night on which data was taken. Phase 35 D-06 says "A placed-then-cancelled/failed block keeps its
   night retired". That holds only while the failed block is the record's chosen block.

ABORTED blocks already behaved this way since 37.1-07. 37.1-13's own finding is that the portal reports
every such early stop as FAILED, which moves this from a rare path to the common rescheduling path. The
plan's tests and the Didymos tracer use single-block requests only, so nothing exercises it.

The runbook (`telescope_runs_calendar.rst:142-144`) states the ranking ("outranks a later pending block").
It does not state effect 1 or effect 3.

**Fix:** This needs a decision from the developer, because the ranking was the developer's own choice
(2026-10-04 and 2026-10-05). Either option fixes it:

- **(a) Rank by request state.** While the request is still PENDING, prefer the last PENDING block over an
  earlier started-tier block, and let the started-tier block win only once no PENDING block remains:

  ```python
  # in select_schedule_block(): a placed future block is the request's live schedule
  return last_pending if last_pending is not None else last_started
  ```

  This rewrites the 2026-10-04 ranking and the tests that pin it.
- **(b) Keep the ranking and document both effects.** In the runbook's "How do LCO/SOAR queue observations
  get onto the calendar?" and in the `retired_nights` paragraph near `:1391-1397`, state that a record
  carries one block. A request that is rescheduled after a failed or aborted block is shown on the earlier
  block until a later block runs, and the earlier night's allocation entry comes back at that point. Add a
  multi-block test that pins the behaviour.

### IN-24: A third dry-run/real-run difference: a marked record whose lookup now succeeds without moving its times

**File:** `docs/runbooks/telescope_runs_calendar.rst:504-515`;
`solsys_code/management/commands/backfill_lco_observations.py:1093-1103`, `:809` (`compare_schedule`),
`:586-587` (marker carried only when `compare_schedule` is False)

**Issue:** Both texts now say a dry run's counts match the real pass "with two caveats". There is a third
case. Take a record carrying `schedule_lookup_failed` whose next lookup succeeds and leaves its times
unchanged. For example, a new request created while the portal was down, whose request still has no
counting block: no block, a PENDING request without a block yet, or a FAILED block with nothing
completed.

- **Real pass:** `compare_schedule` is True, so the marker is not carried. The rebuilt parameters lack it,
  so the record is reported `updated` (the mark is removed).
- **Dry run:** `compare_schedule` is False, the marker is carried, and the record is reported `unchanged`.

The first caveat covers only "when only its schedule times would actually move", and here they do not.
The runbook says elsewhere (`:557-558`) that a dry run "leaves the mark alone", but the enumerated caveats
read as complete.

**Fix:** Extend the first caveat: "...when only its schedule times, or a `schedule_lookup_failed` mark that
a successful lookup would remove, would actually change."

### IN-25: `_resolve_schedule()` says an embedded FAILED block with no statuses "gives no times"; for an existing record it erases stored times

**File:** `solsys_code/management/commands/backfill_lco_observations.py:320-321`, `:349-354`, `:809`

**Issue:** For any embedded list, `compare_schedule` is `embedded and not lookup_failed`, which is True. Take
a record that holds times from an earlier live lookup that found a FAILED-with-data block, and a later
listing that embeds that block without `configuration_statuses`, as the test fixtures' bare
`{'state','start','end'}` blocks do. The comparison then writes None over both stored times, and the
night's allocation entry comes back.

The plan's A-18 accepted only "gives no times and triggers no live lookup", not erasure. The path is
dormant: the portal embeds no blocks today. This is related to open IN-01 (a non-list embedded value) but
is a different case: a list whose only block cannot count.

**Fix:** Say "gives no times (and, for an existing record, replaces its stored times with none)" in the
docstring. Or treat an embedded list in which no block counts but a FAILED block lacks
`configuration_statuses` as "not resolved": return `embedded=False` so that the gate's live lookup runs.
