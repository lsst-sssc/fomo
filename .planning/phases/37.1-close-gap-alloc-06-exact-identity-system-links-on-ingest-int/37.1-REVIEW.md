### IN-01: An embedded `observations` value that is not a list is still read as "no block" on the discovery sweep (carried from round 4, accepted as A-5)

**File:** `solsys_code/management/commands/backfill_lco_observations.py:345-351`, `:789-790`, `:805`

**Issue:** The code is unchanged. `embedded = blocks is not None` treats any non-None `observations` value as
an embedded block list, including a dict, a string or an envelope. `select_schedule_block` then returns None,
and `_resolve_schedule` returns `(None, None, False, True)`. Because `compare_schedule` is True and
`lookup_failed` is False, three things happen:
- an existing record's stored times are overwritten with None;
- a held-back status change is committed;
- the `schedule_lookup_failed` mark is dropped.

The embedded branch runs before the F2 skip, so this also hits a record the skip would otherwise leave alone.
The listing carries no embedded blocks today, so there is no live exposure.

**Fix:** `embedded = isinstance(blocks, list)`. A non-list value then falls through to the gated live lookup,
which already raises `UnexpectedBlockPayloadError` for a bad body.

### IN-02: `sweep_watched_rows()`'s per-proposal failure line still has no newline (carried from round 4, A-9)

**File:** `solsys_code/management/commands/backfill_lco_observations.py:1058`, together with
`solsys_code/unattended.py:457-470`

**Issue:** The code is unchanged. `stderr.write(f'Proposal {row.proposal_code!r}: {summary}')` writes no
`\n` into the raw `io.StringIO` that `step_discovery` splits with `splitlines()`. Suppose proposal A's sweep
raises and proposal B's sweep then writes `Failed to resolve observed block ...`. The two lines merge into one
log record:

```
discovery stderr: Proposal 'A': failed: HTTPErrorFailed to resolve observed block for observation_id='30'.
```

Under `call_command` the bug does not show, because Django's `OutputWrapper` adds the newline.

**Fix:** `stderr.write(f'Proposal {row.proposal_code!r}: {summary}\n')`. Add a two-row test in which the first
row raises and the second has a failed lookup, and assert that `splitlines()` returns them as separate
entries.

### IN-03: The recheck mark turns a one-time recheck failure into an unlimited per-tick retry (carried from round 4)

**File:** `solsys_code/management/commands/backfill_lco_observations.py:455-487`, `:820-822`, `:910-912`

**Issue:** The code is unchanged. Suppose an operator runs `--recheck-unscheduled` during a partial portal
outage, for example while `/observations/` returns 5xx or a non-list body. Every legacy failed-state record in
the proposal gets marked. If the proposal is watched, every later tick then makes two GETs per marked record
until each lookup succeeds.

For a transient outage this heals itself. For a request whose lookup fails every time, nothing limits the
retries and nothing escalates. These records are finished, so the status_refresh failure email does not
cover them either.

**Fix:** Store an attempt count in the marker (`parameters['schedule_lookup_failed'] = n`), and stop or log
at WARNING past a threshold. At minimum, add a runbook note that a recheck run during a portal incident marks
every record it touches.

### IN-05: The `UnexpectedBlockPayloadError` docstring makes a wrong claim about `calendar_utils` (carried from round 4; file outside this round's scope)

**File:** `solsys_code/observation_blocks.py:64-66`

**Issue:** The docstring is unchanged. It says the class subclasses `ValueError` "so the handlers that already
catch it (and `calendar_utils`'s own `ValueError` catch) keep working". But
`calendar_utils.resolve_placement_block` never calls `get_observation_status`, so it never sees this
exception. Every real caller catches `Exception`.

**Fix:** "It subclasses `ValueError` because the body is a bad value; every caller catches `Exception`, so the
class only names the failure."

### IN-06: Facility tests and notebook cell 42 check the exception class by name string (carried from round 4)

**File:** `solsys_code/tests/test_observation_blocks.py:154`, `:169` (outside this round's scope);
`docs/notebooks/pre_executed/backfill_lco_observations_demo.ipynb` cell 42 (`except ValueError` followed by
`raised_name == 'UnexpectedBlockPayloadError'`)

### IN-07: The `mark_lookup_failed` / `lookup_failed` pairing is documented but not enforced (carried from round 4)

**File:** `solsys_code/management/commands/backfill_lco_observations.py:567-569`, `:584-585`

**Issue:** The code is unchanged. The argument doc says "pass True only together with `lookup_failed`", but
nothing checks it. If a caller passed `mark_lookup_failed=True` after a successful lookup, the mark would be
written together with the resolved times. Both current call sites are correct.

**Fix:** Change the test at `:584` to `if mark_lookup_failed and lookup_failed:`, or raise `ValueError` when
`mark_lookup_failed` is passed without `lookup_failed`.

### IN-08: The runbook still says dry-run and real-run counts match, and a failed lookup breaks that (the half of round-4 IN-04 that was not fixed)

**File:** `docs/runbooks/telescope_runs_calendar.rst:496-503`; code at
`solsys_code/management/commands/backfill_lco_observations.py:578-585`, `:353-354`

**Issue:** The runbook says "A dry run's counts are what the following real pass over the same portal payload
will report -- the one honest caveat being" the schedule-only case. A failed real-pass lookup now gives a
second, systematic difference in both directions:
- **A failed recheck lookup.** The real pass marks the record and reports `updated: 1`, as the new paragraph at
  `:603-605` says. A dry run never fails a lookup, so it marks nothing and reports `unchanged`.
- **A state change whose lookup fails.** The dry run reports `would update` for the status change. The real
  pass holds the status back (`:578-579`) and reports `unchanged`. Notebook cell 37 shows this: request
  `900603` goes from PENDING to WINDOW_EXPIRED and its lookup times out, and the summary reads
  `updated: 0, unchanged: 1`.

Round 4 raised this ("A dry run of the same command reports it `unchanged`"). 37.1-12 added only the
`updated` sentence. An operator who compares a dry run with the real run, as `:492-497` tells them to, will
see counts that do not match.

**Fix:** Add a second caveat after `:503`: "A real pass whose block lookup fails also differs: a held-back
state change is reported `unchanged` instead of `updated`, and a record a failed recheck lookup marks is
reported `updated` instead of `unchanged`. `block lookups failed` counts these."

### IN-09: "re-run the command (no flag needed)" in the `--recheck-unscheduled` help can be read as "run it with no flags at all"

**File:** `solsys_code/management/commands/backfill_lco_observations.py:1217-1221`; related:
`:1066-1069`, `:1314`

**Issue:** The help text says: "for any other --proposal code re-run the command (no flag needed) until block
lookups failed is 0". "No flag" is meant to mean "no `--recheck-unscheduled`", but read literally it describes
the bare invocation. The bare invocation is exactly the run that never sweeps an unwatched code. It also
prints only `Swept N watched proposal(s), failed: M` (`:1314`), because `sweep_watched_rows()` puts each
proposal's summary only into `WatchedProposal.last_run_summary` (`:1066-1069`). So the operator would never
see a `block lookups failed` count to stop on.

The runbook (`:609-611`), the `Command` docstring (`:1116`) and notebook cell 39 all spell out
`--proposal <code>`. Only the `--help` text is ambiguous.

**Fix:** "...so for any other code re-run `--proposal <code>` without `--recheck-unscheduled` until block
lookups failed is 0."

### IN-10: The "until `block lookups failed` is 0" stopping rule counts every failed lookup in the proposal, not just the marked record

**File:** `docs/runbooks/telescope_runs_calendar.rst:609-611`;
`solsys_code/management/commands/backfill_lco_observations.py:1116-1117`, `:1220`, `:795-797`; notebook cell 39

**Issue:** `block_lookups_failed` counts every live lookup that raised in the sweep (`:795-797`). That includes
new requests, non-terminal requests, held-back state changes, and any request whose lookup fails every time
(see IN-03). If one unrelated request in an unwatched proposal fails persistently, the count never reaches 0,
even after the marked record has been resolved. The operator following the instruction then re-runs
indefinitely and has no documented way to tell that the marked record is done. The rule is sufficient but not
necessary, so the wording overstates what the operator must reach.

**Fix:** Tie the stopping rule to the record. For example: "...until the record's `Failed to resolve observed
block for observation_id=...` line no longer appears on stderr (or `block lookups failed` is 0)." Each failed
lookup already names its `observation_id` on stderr (`:797`), so the operator can check the record directly.

### IN-11: "an expired or cancelled record" leaves out the other two failed states the skip applies to

**File:** `docs/runbooks/telescope_runs_calendar.rst:596-598`

**Issue:** The skip at `backfill_lco_observations.py:451` applies to every state in
`get_failed_observing_states()`. For LCO those are `WINDOW_EXPIRED`, `CANCELED`, `FAILURE_LIMIT_REACHED` and
`NOT_ATTEMPTED` (`tom_observations/facilities/ocs.py:118-119`). The new sentence names only expired and
cancelled, and the next clause covers only completed records. A `FAILURE_LIMIT_REACHED` or `NOT_ATTEMPTED`
record therefore matches neither clause, although it behaves exactly like an expired one. The same shorthand
appears at `:556-557`. This is not false, but it is incomplete exactly where an operator would compare
summary counts.

**Fix:** "an expired, cancelled or otherwise failed record (any of the facility's failed states) whose recheck
lookup succeeded is back under `fallback lookups skipped`..."
