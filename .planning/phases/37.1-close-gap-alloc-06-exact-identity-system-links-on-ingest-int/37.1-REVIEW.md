## Summary

This is an incremental review of the four files changed since `ac3e959`. Those changes are gap-closure plan
37.1-10, which closes the previous round's CR-01: a live block lookup that raised used to erase stored times
and commit the new status. I traced the change across module boundaries into `observation_blocks.py`
(`ScheduleBlockRuleMixin.get_observation_status`, `select_schedule_block`), TOM's `make_request` /
`update_observation_status` / `update_all_observation_statuses`, `unattended.py` (`step_discovery`,
`_refresh_one_facility`), `project_observation_calendar.py` (the other writer of `parameters`) and
`backfill_lco_observation_records.py`.

Checks run:
- `python manage.py test solsys_code.tests.test_backfill_lco_observations`: 117 tests, all pass.
- `pre-commit run ruff` and `pre-commit run ruff-format` on both Python files: both clean.

### (a) Is CR-01 closed? Yes, on every path.

- **Existing record, real run (`backfill_lco_observations.py:751`, `:845-853`, `:527-544`).** A raised lookup
  sets `lookup_failed`. That forces `compare_schedule` to False, both at the call site and inside
  `_changed_record_fields`, and the `status` comparison is skipped. Only `parameters` can change, and an
  existing marker is carried along. The stored `scheduled_start`/`scheduled_end` and the stored status
  survive. Because the status change is held back, the next tick's `existing_record.status != portal_state`
  branch (`:437`) looks the request up again. TOM's `update_observation_status` raises before any write when
  either GET fails, so the unattended `status_refresh` step cannot reopen the hole either.
- **Brand-new record (`:829-840`).** The record is created with the listing's status, no times, and
  `parameters['schedule_lookup_failed'] = True`. `_schedule_lookup_is_needed` (`:435`) checks the marker
  before the state or terminal checks, so a finished, same-state, marked record is looked up on every
  later run. The save that writes a resolved schedule uses the freshly built `parameters`, which never
  contain the key, so the marker is dropped in that same save. I checked the one other place that writes
  `parameters`, `project_observation_calendar.py:93-103`. It changes the loaded dict in place, so it keeps
  the marker.
- **Concurrent create.** If `existing_record` was None but `get_or_create` finds a row, the `else` branch
  still passes `lookup_failed`, so that path is safe too.
- **Dry-run branch (`:756-772`).** A dry run never makes a live lookup, so `lookup_failed` is always False
  there. A marked record gets `compare_schedule=False`, so the marker is carried and the record is not
  reported as drift (covered by `test_a_dry_run_over_a_marked_record_makes_no_lookup_and_keeps_the_marker`).
- **Embedded-block branch.** `_resolve_schedule` returns `lookup_failed=False` whenever `observations` is
  present, so this branch cannot reach the failed-lookup path. It compares the schedule and clears the
  marker, the same in both modes.
- **T-ik7-02.** Both the dry-run and real-update branches call the single `_changed_record_fields` with
  identical arguments, including `lookup_failed=`. Any remaining dry-run versus real difference comes only
  from data a dry run cannot know (the live lookup's outcome), not from two diverging comparisons.

### (b) New ways a lookup could still erase, disarm or grow

I found no new path that erases stored times after a *raised* lookup. Two weaker spots remain:

- A *non-raising* malformed reply is still read as "no block". This is the previous round's WR-02, still
  open and pre-existing. It now also clears the new marker (WR-01).
- A failed lookup during an operator `--recheck-unscheduled` run is neither marked nor retried (WR-02).

Per-tick lookups stay bounded by the number of requests in the listing. Each held-back or marked record adds
at most one lookup per tick. There is, however, no limit on how many ticks a deterministically failing
request is retried, and its status change stays held back for the whole time (IN-01).

### (c) Docs

The notebook's failed-lookup cells (cells 36-38) were re-executed in order (execution counts 1-24 are
monotonic). Their outputs match the implemented behaviour: two lookups attempted in sweep 1, the marker set
only on `900604`, four lookups in sweep 2, zero in sweep 3, and the retired night unchanged throughout. The
cleanup cell removes `900603`/`900604` and their group.

The runbook's new "Scheduled times" paragraph is accurate. One earlier bullet in the same section is now
stale (WR-03).

## Warnings

### WR-01: A malformed but non-raising block reply still reads as "no block", and now also clears the failed-lookup marker (pre-existing, previous review's WR-02, still open)

**File:** `solsys_code/observation_blocks.py:117` (via `select_schedule_block`, `:71`); consumed at
`solsys_code/management/commands/backfill_lco_observations.py:357` and `:751`

**Issue:** This is the WR-02 that plan 37.1-10 deliberately left out of scope (assumption A-2). It still
applies. `select_schedule_block()` returns None for any `/observations/` body that is not a list, and
`get_observation_status()` then returns `{'scheduled_start': None, 'scheduled_end': None}` without raising.
Examples are a 200 reply with a dict error payload, or a paginated `{'results': [...]}` envelope.

The sweep treats that as a successful lookup: `lookup_failed` is False and `compare_schedule` is True.
Three things follow:
1. An existing record's stored times are overwritten with None and the new status is committed. This
   brings back the retired allocation night, exactly as CR-01 did for a raised lookup.
2. **New in this round:** a record carrying `schedule_lookup_failed` has the marker dropped in that same
   save. This disarms the retry that 37.1-10 added.
3. A failed-state record then falls under the F2 skip and is never looked up again.

The same malformed reply also erases times on the unattended `status_refresh` path, since TOM's
`update_observation_status` writes whatever `get_observation_status` returns. TOM's own implementation
would have raised a `TypeError` on such a body (`block['state']` on a str key). FOMO's `isinstance` guard
turns a failure into a silent "no block".

**Fix:** Make a non-list body a failure in `ScheduleBlockRuleMixin.get_observation_status`, so every
caller's existing failed-lookup handling applies:

```python
blocks = response.json()
if not isinstance(blocks, list):
    raise ValueError(f'unexpected observations payload type for request {observation_id}: {type(blocks).__name__}')
block = select_schedule_block(blocks)
```

Keep `select_schedule_block()`'s tolerant contract for the embedded-list caller, or give it the same strict
check behind a flag.

### WR-02: A failed lookup during `--recheck-unscheduled` is neither marked nor retried, so the operator's one-time catch-up is silently lost for that record

**File:** `solsys_code/management/commands/backfill_lco_observations.py:441-442`, `:527-544`, `:741-743`

**Issue:** Take a failed-state record (`WINDOW_EXPIRED`/`CANCELED`) at the same portal state with no times.
It is looked up only when `recheck_unscheduled=True` (`:442`). If that lookup raises, the sequence is:
1. `_changed_record_fields(..., lookup_failed=True)` returns no change, and no marker is added. The marker
   is written only on the brand-new-record branch (`:837`).
2. The record is counted `unchanged`.
3. The next ordinary tick reaches `return recheck_unscheduled or existing_record.status not in failed_states`
   with `recheck_unscheduled=False` and skips it forever.

The aborted block's times are never picked up and the run's allocation night stays on the calendar. The
only trace is `block lookups failed: N` and one stderr line. The runbook (`telescope_runs_calendar.rst`
around line 589: "A failed lookup is counted under `block lookups failed` and never stops the sweep") does
not tell the operator to re-run the recheck. This is the same kind of "lookup failed, retry disarmed" hole
CR-01 closed for the ordinary path, now on the operator path.

**Fix:** Either:
- mark an existing record when its lookup fails while it would otherwise be skipped, so the unattended
  runner retries it until a lookup succeeds; or
- at minimum, document the re-run.

To mark the record, add something like this after `changes` is computed in the real-run `else` branch:

```python
if lookup_failed and not _schedule_lookup_is_needed(
    record, status, terminal_states, failed_states, recheck_unscheduled=False
):
    marked = dict(changes.get('parameters', record.parameters) or {})
    marked[SCHEDULE_LOOKUP_FAILED_KEY] = True
    changes['parameters'] = marked
```

If you only change the docs, add to the runbook's recheck paragraph: "If `block lookups failed` is not 0,
run the same command again; a record whose recheck lookup failed is not retried by the unattended runner."

### WR-03: Runbook "Re-running updates in place" bullet contradicts the new failed-lookup and marker behaviour (paired-doc staleness)

**File:** `docs/runbooks/telescope_runs_calendar.rst:415-427`

**Issue:** The bullet still says, without qualification, that an existing record "has its `status`,
`scheduled_start`, `scheduled_end` and `parameters` refreshed from the portal". It also says that for a
finished same-state record "no per-request lookup is made for it". After 37.1-10 both statements are wrong
in specific cases:
- a failed lookup holds the status change back and writes neither time;
- a finished, same-state record carrying `schedule_lookup_failed` *is* looked up on every run.

The "Scheduled times" paragraph 100 lines later now says the opposite. The CLAUDE.md paired-docs rule treats
a stale runbook statement about changed behaviour as a must-have gap.

**Fix:** Qualify the bullet, for example: "...refreshed from the portal (except after a failed block lookup,
which keeps the stored status and times; see **Scheduled times** below)". In the finished-record sentence,
also add: "...no per-request lookup is made for it unless it carries the `schedule_lookup_failed` mark."

## Info

### IN-01: A request whose lookup fails every time has its status change held back forever, with no attempt limit and no escalation

**File:** `solsys_code/management/commands/backfill_lco_observations.py:530-533`, `:435-437`, `:837`

**Issue:** Before 37.1-10, an existing record moving to a terminal state stopped being looked up after one
failed tick (by committing the wrong data, which was CR-01). Now a request whose lookup fails every time is
retried on every tick indefinitely, and its stored status never advances. Examples of a deterministic
failure are a `KeyError` on a response without `'state'`, or a persistent per-request 4xx or 5xx. The
change is counted `unchanged`, not `updated`, so the summary shows the problem only through
`block lookups failed`. The per-tick cost is bounded (at most two GETs per such request), but the duration
is not. This is a reasonable trade-off, but it should be a conscious one.

**Fix:** Optionally store a failure count in the marker (`{'schedule_lookup_failed': n}`). Log at WARNING,
or add a summary counter such as `state changes held back: N`, once `n` passes a threshold, so a stuck
request becomes visible to an operator.

### IN-02: In the unattended runner, the sweep's per-request failure lines merge into one log record (pre-existing, cross-file)

**File:** `solsys_code/management/commands/backfill_lco_observations.py:743` together with
`solsys_code/unattended.py:457-470`

**Issue:** `sweep_proposal()` writes `stderr.write(f'Failed to resolve observed block ...')` with no
trailing newline. Under `call_command`, Django's `OutputWrapper` appends one, which is why the notebook
shows separate lines. `step_discovery` instead passes a raw `io.StringIO()`, so every
`Failed to resolve ...` line from a tick runs together, and `splitlines()` (IN-38) produces one huge log
record. Now that failed lookups are retried on every tick, this stderr output is the only place an operator
can find *which* observation ids are stuck.

**Fix:** End each `stderr.write`/`stdout.write` in `sweep_proposal()` with `'\n'`, or wrap the sinks in
`unattended.step_discovery` with `django.core.management.base.OutputWrapper`.

### IN-03: The Didymos backfill still creates records whose failed lookup is never retried, and prints the raw exception text (pre-existing, documented)

**File:** `solsys_code/management/commands/backfill_lco_observation_records.py:376-380` (out of file scope;
referenced by the new text at `backfill_lco_observations.py:411-413` and `telescope_runs_calendar.rst:555-559`)

**Issue:** The new docstring and runbook text correctly say that a Didymos-backfill record created during a
failed lookup is recovered only by a manual `--recheck-unscheduled`. That command does not reuse
`SCHEDULE_LOOKUP_FAILED_KEY`, so if the listing state is a failed state, the discovery sweep's F2 skip
leaves the record frozen without its times. Separately, its create path writes
`f'Failed to refresh status ...: {exc}'`, the raw exception text. An `ImproperCredentialsException` carries
the portal response body. Its own recheck path at `:302-307` deliberately prints the class name only.

**Fix:** Set `parameters[SCHEDULE_LOOKUP_FAILED_KEY] = True` (imported from `backfill_lco_observations`) when
`update_observation_status` raises on create, and print `type(exc).__name__` instead of `exc`.

### IN-04: Test coverage gaps around the new marker and held-back status

**File:** `solsys_code/tests/test_backfill_lco_observations.py:2488-2820`

**Issue:** The `_changed_record_fields` unit tests cover the logic, but no sweep-level test exercises:
- an *existing marked* record whose lookup fails again. The marker should survive a real save and the
  record should be counted `unchanged`; this is only unit-tested.
- a failed lookup combined with `parameters` drift. `parameters` should be saved while status and times
  are held.
- a successful lookup that returns no block for a marked record. The marker should be dropped, then the F2
  skip should apply.
- the `--recheck-unscheduled` failed-lookup path described in WR-02.

**Fix:** Add three or four `sweep_proposal` cases to `TestFailedLookupOnANewRecord` /
`TestFailedLookupKeepsTheStoredSchedule` using the existing `_PORTAL`/`_LISTING` patches.

### IN-05: Minor doc wording and wrapping issues in the new text

**File:** `solsys_code/management/commands/backfill_lco_observations.py:413-415`;
`docs/runbooks/telescope_runs_calendar.rst:539-541`, `:556-565`;
`docs/notebooks/pre_executed/backfill_lco_observations_demo.ipynb` (cell 0 overview bullet)

**Issue:**
- In `_schedule_lookup_is_needed`, the docstring sentence "Both kinds are / brought up to date by an
  operator / run with" is wrapped raggedly, apparently left over from an insertion.
- The same docstring says "no FOMO path stores a state change without its block" and then, a paragraph
  later, describes the Didymos backfill doing exactly that.
- The runbook's "Every later run looks a marked record up ... and that lookup removes the mark" is
  imprecise in two ways: a dry run makes no lookup, and an embedded block also removes the mark with no
  lookup at all.
- Runbook lines 559 and 565 are much longer than the surrounding wrap.
- The notebook overview says the next sweep "looks both up again and clears the mark", but only `900604`
  ever had a mark.

**Fix:** Re-wrap the docstring and runbook lines. Reword the docstring premise to "no FOMO path that
updates an existing record stores a state change without its block". In the runbook, write "every later
real run ... until a lookup (or an embedded block) resolves it". In the notebook overview, write "...and
clears the new request's mark".
