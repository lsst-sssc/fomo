## Warnings

### WR-21: The observed-telescope lookup decides "finished" from the record's status, not from the block its times came from, so TOM-route and pre-fix records can get a telescope that does not match their times

**File:** `solsys_code/management/commands/project_observation_calendar.py:64-67, 90-92`; `solsys_code/calendar_utils.py:300-305`; `docs/runbooks/telescope_runs_calendar.rst:296-300`; `docs/notebooks/pre_executed/project_observation_calendar_demo.ipynb` cell `7e7bd66e`

**Issue:** `resolve_observed_site()` passes `request_finished=is_request_finished(record.status, facility)`. That
is True for every record that reaches the lookup, because COMPLETED is the only observed state. The rule
therefore picks the last started block over a leftover PENDING block. The docstrings, the runbook (line 298:
"so the telescope it names is the one the record's times came from") and projector notebook cell `7e7bd66e`
all state this as unconditional.

It holds only when the record's times were chosen by this round's rule. It fails for two kinds of COMPLETED
record with no COMPLETED block whose list is, for example, `[FAILED with data, PENDING]`. That is the shape of
the real request 4276100 plus a placed block.

- **Finished through one of TOM Toolkit's own routes:** `updatestatus`, the "Update status" button, the
  Cancel view, or the REST cancel route (module docstring lines 43-52; plan A-37). TOM's
  `OCSFacility.get_observation_status()` stores the last PENDING block's times (`ocs.py:1563-1568`).
- **Stored under 37.1-14's rule with the observed site still unresolved:** for example, every earlier lookup
  hit `site_lookup_failed`, and those records are retried each sweep. Plan A-42 covers these.

For either kind, the next `project_sweep` now stores the FAILED block's site and telescope (`coj`/FTS). The
event is still drawn over the stored PENDING block's night, so the `[O]` title and `event.telescope` name a
telescope and night that do not belong together. This breaks Pitfall 3 ("telescope resolution and timing always
come from the same block"), which this change was meant to protect.

Before 37.1-15 both TOM's rule and `resolve_placement_block()`'s default picked the PENDING block, so these
records were consistent. This round introduced the mismatch for them. No test covers it.
`test_the_observed_site_of_a_completed_request_comes_from_the_block_that_took_data` uses a record whose stored
times (2026-09-06) match neither block (see IN-33).

**Fix:** Choose the block that matches the record's stored times, and fall back to the rule only when nothing
matches. That makes Pitfall 3 hold whatever path wrote the times:

```python
# calendar_utils.resolve_placement_block(observation_id, facility, *, request_finished=False, stored_start=None)
if stored_start is not None:
    for block in blocks:
        if isinstance(block, dict) and coerce_schedule_datetime(block.get('start')) == stored_start:
            return block
return select_schedule_block(blocks, request_finished=request_finished)

# project_observation_calendar.resolve_observed_site()
block = resolve_placement_block(
    record.observation_id,
    facility,
    request_finished=is_request_finished(record.status, facility),
    stored_start=record.scheduled_start,
)
```

If you keep the current code, change the three statements so they say the lookup reads the block this round's
rule would choose, which can differ from the stored block for a record finished through TOM's routes or stored
before 37.1-15. Then add a test with a record whose stored times are the PENDING block's.

### WR-22: Docs and both `--recheck-unscheduled` help strings say records stored before the rule are recovered, but a record holding a leftover pending block's times is never rechecked

**File:** `solsys_code/management/commands/backfill_lco_observations.py:1240-1245` (help), `:427-439` (`_schedule_lookup_is_needed` docstring); `solsys_code/management/commands/backfill_lco_observation_records.py:225-232` (help); `solsys_code/observation_blocks.py:49-52`; `docs/runbooks/telescope_runs_calendar.rst:626-631, 637-640`

**Issue:** Both help strings now read: "using the block rule FOMO applies (..., and on a finished request even
beside a leftover pending block), so records stored before that rule pick up their block times". The rule they
describe now includes the WR-20 part.

`--recheck-unscheduled` only reaches records missing a scheduled time:

- `_schedule_lookup_is_needed()` returns `recheck_unscheduled or ...` only inside the
  `scheduled_start is None or scheduled_end is None` branch
- the Didymos command checks
  `existing.scheduled_start is None or existing.scheduled_end is None` (line 296)

A finished record holding a leftover PENDING block's times has both times set, so the flag never looks at it.
Such a record can come from TOM's routes, from 37.1-14's rule, or from 37.1-07 to -12 for a FAILED block. The
operator is told the flag brings it up to date, and it does not.

Two more statements say TOM's routes leave a record "without times" and that `--recheck-unscheduled` recovers
it:

- the module docstring, lines 49-52: "An operator recovers an LCO record by re-running the backfill command for
  its proposal with --recheck-unscheduled"
- the runbook, lines 626-631 and 637-640: "still uses TOM's rule and leaves such a record without times";
  "Records stored before this release, and any finished through one of TOM's own routes, are brought up to
  date with --recheck-unscheduled"

That is true only when the list has no PENDING block. With a leftover PENDING block, TOM stores that block's
times. Before this round FOMO's rule would have picked the same block, so it did not matter. Now FOMO's rule
picks a different block and there is no documented recovery. The plan routes this to human item 4 (A-42),
which names `FomoLCOFacility().update_observation_status(id)` as the per-record correction. None of the
operator-facing text says so.

**Fix:** Narrow the help strings to what the flag does, for example: "...so records missing a scheduled time
pick up their block times. A finished record that already holds a leftover pending block's times is not
looked up; correct it with `FomoLCOFacility().update_observation_status(<id>)`." In the module docstring and
the runbook's TOM-routes sentences, add that when the portal lists a pending block, TOM's rule stores that
block's times instead of none, that `--recheck-unscheduled` does not revisit such a record, and how to
correct it. A better fix is a recheck mode that also looks at finished records with both times set, but that
changes behaviour and is the developer's call.

### WR-23: The runbook's `[X]` legend row misstates A-33

**File:** `docs/runbooks/telescope_runs_calendar.rst:208-211`

**Issue:** The legend says `[X]` is "drawn over the whole request window when no block counts, or over the
block when one started and was aborted or failed after taking data". Under A-33, a WINDOW_EXPIRED request
whose only timed block is a leftover PENDING block keeps that block's times, so its `[X]` is drawn over a
night where nothing ran. The rule paragraph at lines 179-183 says this and the A-33 test pins it, but the
legend gives a reader no case that matches. The plan left the row as 37.1-14 wrote it. It was already
incomplete then, and the orchestrator asked for any misstatement of A-33 to be flagged.

**Fix:** Extend the row: "...or over the block when one started and was aborted or failed after taking data,
or, when no block took data, over a placed block that never ran (see the one-block paragraph above)."

### IN-31: On the embedded-list path a finished record is re-read on every sweep, so A-33 and "the finishing tick is the last one that reads it" do not hold there

**File:** `solsys_code/management/commands/backfill_lco_observations.py:351-359, 816`; `solsys_code/observation_blocks.py:28-29, 35-36, 171-173`

**Issue:** `_resolve_schedule()` reads an embedded block list even when `skip_live_lookup` is True. With
`embedded` True, `compare_schedule` is True on every sweep. Take a WINDOW_EXPIRED request whose embedded list
later changes from `[PENDING]` to `[NOT_ATTEMPTED]`. The rule returns None, and `_changed_record_fields()`
writes `scheduled_start=None`/`scheduled_end=None`, so the A-33 times are erased and the night comes back. The
live path keeps them forever. The docstrings state A-33 and "the tick at which the request finishes is the
last one that reads its record" without exception. The listing carries no embedded blocks today (documented),
so this is a latent divergence, not a live bug.

**Fix:** Add one clause to the module docstring, "on the live lookup path; an embedded block list is re-read
on every sweep", or skip the schedule comparison for an embedded finished record at the same state, as the
live path does.

### IN-32: The runbook's status_refresh step says a tick "never erases the times of an in-progress or aborted block", and the next sentence says it replaces them

**File:** `docs/runbooks/telescope_runs_calendar.rst:1778-1784`

**Issue:** Line 1779 says a tick "never erases the times of an in-progress or aborted block, or of a block that
failed after taking data". The next sentence says that while a pending block exists "the tick stores that
placed block's times instead". The wording predates this round, but this round reflowed and extended the

(TOM's rule would)."

### IN-33: Three new tests claim more than they check

**File:** `solsys_code/tests/test_observation_blocks.py:560-575, 331-334`; `solsys_code/tests/test_project_observation_calendar.py:489-516`

**Issue:**

1. `test_status_on_a_completed_request_still_reads_its_completed_block` says "in either order". Both subtests
   put the COMPLETED block last; `[completed, pending]` is never tested.
2. `test_the_observed_site_of_a_completed_request_comes_from_the_block_that_took_data` names Pitfall 3. Its
   record's stored times (`_make_observed_record`, 2026-09-06 10:00) match neither the FAILED block (07-12)
   nor the PENDING block (09-07), so it never checks "the block the record's times came from" (see WR-21).
3. In the finished pair table, the second assertion compares `request_finished=False` with the default call.
   Both resolve to the same parameter value, so it can never fail. 37.1-14's table is what actually pins that
   order.

**Fix:** (1) Add a `[completed, pending]` subtest. (2) Give the record the FAILED block's stored times, and add
the contrasting record with the PENDING block's times from WR-21. (3) Drop the tautological assertion, or
replace it with an explicit check against the can-still-run oracle.

### IN-34: The claim that `is_request_finished()` never raises depends on the facility returning a list

**File:** `solsys_code/observation_blocks.py:140-150`

**Issue:** The docstring says it works for "any facility instance that has `get_terminal_observing_states()`",
and that "List membership never hashes, so an odd state value never raises". That is true for TOM's OCS
facilities, which return a list. A facility returning a `set` or `frozenset` would raise `TypeError` for an
unhashable state. `status_vocabulary` itself wraps these lists in `frozenset`.

**Fix:** `return state in list(facility.get_terminal_observing_states())`, or say in the docstring that it
relies on the list.
