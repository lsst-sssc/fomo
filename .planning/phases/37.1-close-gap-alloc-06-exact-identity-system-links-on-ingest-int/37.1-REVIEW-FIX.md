## Fixed Issues

### WR-12: `ProtectedUserDeleteView` catches `ProtectedError` only in `form_valid()`, so an HTTP `DELETE` to the same URL still returns a 500

**Files modified:** `solsys_code/views.py`, `solsys_code/tests/test_campaign_run_observation.py`
**Commit:** a84f87c
**Applied fix:** `ProtectedUserDeleteView` now overrides `delete()` to set `self.object = self.get_object()` and
call `self.form_valid(self.get_form())`, so an HTTP `DELETE` goes through the same `ProtectedError` guard as
`POST` (redirect to the user list with an error message, account left in place). `HttpRequest` was added to the
`django.http` import for the type hint.

This is a variation on the review's second suggestion, which was to have `delete()` call `post()`. Django's
`BaseDeleteView.post()` validates a form bound to `request.POST`, and a `DELETE` request does not populate that,
so the form would be unbound, `is_valid()` would be False, and the view would re-render the confirmation page
(HTTP 200) without deleting anything. Calling `form_valid()` directly avoids that. Keeping `DELETE` working
(rather than the review's first option of removing it from `http_method_names`) preserves HTMX `hx-delete`
clients for unprotected accounts.

Tests added next to the WR-10 tests in `TestUserDeleteView`:
- `test_http_delete_for_a_protected_user_redirects_with_a_message_instead_of_a_500`: `client.delete(...)` for a
  link-confirming user redirects to `user-list`, the user and link still exist, and the message says
  "cannot be deleted".
- `test_http_delete_for_an_unprotected_user_still_deletes_it`: `client.delete(...)` for a bystander redirects and
  deletes the account.
