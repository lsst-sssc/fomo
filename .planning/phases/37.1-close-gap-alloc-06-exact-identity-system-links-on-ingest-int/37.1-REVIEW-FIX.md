### WR-09: `receiver_on_record_save` re-projection had no savepoint

**Status:** fixed (logic change; requires human verification)
**Commit:** 8ade361
**Files modified:** `solsys_code/observation_projector.py`, `solsys_code/tests/test_observation_projector_signals.py`
**Applied fix:** the per-link `reproject_allocation_if_dispatched(link.run)` call is now wrapped in
`with transaction.atomic():` inside the existing per-link `try`, the same pattern the CR-01 fix used at
`allocation_projector.py` ~1655 and ~1744. A failed projection write now rolls back only the projection, not the
caller's atomic block, so the record's own save survives and later links are not poisoned with
`TransactionManagementError`. Regression test
`TestLinkedRunReproject.test_a_failing_linked_run_write_does_not_roll_back_the_records_own_save` (mirrors
`test_a_failing_receiver_write_does_not_roll_back_the_link`): inside `transaction.atomic()` it saves a status change
while the projection performs a unique-constraint-violating write, then asserts the status persisted and the warning
was logged. Confirmed it fails without the fix (`'PENDING' != 'CANCELED'`) and passes with it.
**Paired notebook:** `docs/notebooks/pre_executed/project_observation_calendar_demo.ipynb` was deliberately NOT
regenerated. This is an error-path robustness change with no visible demo behavior (a failing re-projection never
occurs in the demo), so there is nothing new for real executed output to show.
**Test run:** `python manage.py test solsys_code.tests.test_observation_projector_signals --noinput` -- 33 tests, OK.

### WR-10: `PROTECT` turned TOM's user-delete page into an HTTP 500

**Status:** fixed
**Commit:** ddace32
**Files modified:** `solsys_code/views.py`, `src/fomo/urls.py`, `solsys_code/tests/test_campaign_run_observation.py`, `docs/runbooks/telescope_runs_calendar.rst`
**Applied fix:** added `ProtectedUserDeleteView(tom_common.views.UserDeleteView)` in `solsys_code/views.py`. It
overrides only `form_valid()`: it calls the parent, and on `ProtectedError` leaves the account in place, shows an error
message ("<user> cannot be deleted: the account confirmed N campaign link(s) or calendar event attribution(s) ...
Deactivate the account instead") and redirects to `user-list`. TOM's `dispatch()` permission logic and its behavior for
every unprotected account are inherited unchanged. Registered in `src/fomo/urls.py` as
`users/<int:pk>/delete/` (name `user-delete`) ahead of `include('tom_common.urls')`, the same shadowing technique the
project already uses for the `calendar` namespace. The runbook sentence now names the Users page Delete button and
says clearing **Active** on the admin page locks the account out.
Decision note: the review's first option is "catch `ProtectedError` at the view layer", which the instructions say to
implement; the thin subclass is the smallest way to do that. It needed neither reverting to `SET_NULL` nor editing a
TOM template. If the operator prefers hiding the button instead, the subclass can be removed without touching the
model.
**Tests:** new `TestUserDeleteView` class: a confirming user's POST redirects to `user-list` with a "cannot be deleted"
message and the user and link survive (no 500); an unprotected user is still deleted. Confirmed the first test fails
with a raised `ProtectedError` when the URL override is removed.
**Test run:** `python manage.py test solsys_code.tests.test_campaign_run_observation --noinput` -- 9 tests, OK (at the
time of this commit).

**Files modified:** `solsys_code/models.py`, `solsys_code/migrations/0025_calendareventmeta_confirmed_by_protect.py` (new), `solsys_code/tests/test_campaign_run_observation.py`, `docs/runbooks/telescope_runs_calendar.rst`
**Applied fix:** `CalendarEventMeta.confirmed_by` is now `on_delete=models.PROTECT`, with a comment explaining the

legacy rows are unaffected by this change; only accounts that currently own a confirmation become protected.
