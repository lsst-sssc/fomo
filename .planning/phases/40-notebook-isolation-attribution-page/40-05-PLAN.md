The defect (40-VERIFICATION.md gap 1, reproduced by the reviewer and the verifier):
`setup_scratch_django()` in docs/notebooks/fomo_nb_utils.py calls `django.setup()` (line 201) before
`check_resolved_database()` (lines 206-207). When the check refuses a database that a `local_settings.py`
or `DJANGO_SETTINGS_MODULE` override chose, the `except` block only removes the scratch directory.
`apps.ready` stays True and `connections['default']` still points at the refused database, so the next
notebook cell writes there. 40-01-PLAN.md specified that order (interfaces, steps 5-6), so the executor
followed the plan; this plan corrects it.

The fix, per the VERIFICATION `missing` list and the review's suggested fix:
1. Read `django.conf.settings` (which loads the settings module without populating the app registry or
   opening a connection) and check it **before** `django.setup()`.
2. On any failure once settings are loaded (the refusal itself, or later, for example in `migrate`), close
   every connection and leave the ORM unable to reach any database before re-raising. This plan does that by
   switching every alias to Django's `django.db.backends.dummy` engine in place, which raises
   `ImproperlyConfigured` on any query. The in-place change works because Django's connection handler holds
   the same dict object as `settings.DATABASES`.
   Planning-time grounding (2026-10-09, venv devel_fomo311_venv, Django 5.2.17): a scratch copy of the helper,
   outside the repo, implemented this plan's target order. The planned child probes were run against it and
   against the current helper:
   - Default-override refusal, second-alias refusal and router refusal: the prototype printed `APPS_READY False`,
     `WRITE_REFUSED <alias> ImproperlyConfigured` for every alias, both routing variables `None` and a
     restart-the-kernel second refusal, and the other file was never created. The current helper printed
     `APPS_READY True` and `WRITE_SUCCEEDED default`, and created the other file (the RED this plan expects).
   - Forced migrate failure: the prototype printed `ImproperlyConfigured` for both the cursor and the ORM; the
     current helper printed `OperationalError` (from the deleted directory, safe only by accident).
   - Environment restore (`DURING True 'true'`, `AFTER_FOMO True`, `AFTER_ASYNC None`) and the snapshot run
     (marker row present, 175 migration rows, source sha256 unchanged, no directory left) both behaved as
     specified.
   The same scratch prototype also confirmed the pre-settings-read case: `settings.configure()` with a dummy
   default makes a later raw `cursor()` raise `ImproperlyConfigured`.
3. A child-process test catches the refusal and asserts `apps.ready is False` and that a raw
