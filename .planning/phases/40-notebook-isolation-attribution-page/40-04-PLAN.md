Planner decisions recorded here:
- **Where the whitelist lives:** `attribution_return_state()` is a module-level function in
  `campaign_views.py` next to `_ATTRIBUTION_BANDS`; the tables receive the already-validated state from
  the view (`return_state=` constructor keyword), so `campaign_tables.py` never imports the view module
  (no import cycle) and never validates on its own.
- **Key names:** the four page/sort keys are built from the two table prefixes (constants
  `_DISMISSED_TABLE_PREFIX`, `_CONFIRMED_TABLE_PREFIX`, also used to construct the tables) and
  django-tables2's default `page` / `sort` field names; a test pins them to the constructed tables'
  `prefixed_page_field` / `prefixed_order_by_field`.
- **Validation** (V5): page = 1-6 ASCII digits with no leading zero (no unbounded `int()` on input);
  sort = `-?[a-z_]{1,40}` (django-tables2 ignores unknown column names itself); `*-per_page` is not
  carried (D-22 names five keys).
- **Fragments** (D-25, RESEARCH A4): `undo_dismissal` -> `#attribution-dismissed-section`,
  `undo_confirmation` -> `#attribution-confirmed-section`, every worklist action -> none; the fragment
  comes from a constant map keyed by the validated action, never from input.
- **Clamp** (D-27): no clamping arithmetic -- the redirect keeps a valid posted page and django-tables2's
  `RequestConfig` silently renders the last page for an out-of-range one (RESEARCH, library source).
- **Open/closed state** (IN-15): the Dismissed section opens when its page or sort key is in the
  validated GET state; carrying Dismissed's state through the Confirmed table's links and forms is the
  D-26 behavior ("Dismissed keeps whatever state it had") and stays.
- **Browser proof** of success criterion 5 is added (RESEARCH: optional but cheap) because the real flow
  includes the Undo button's `confirm()` dialog, which a server test cannot see.
