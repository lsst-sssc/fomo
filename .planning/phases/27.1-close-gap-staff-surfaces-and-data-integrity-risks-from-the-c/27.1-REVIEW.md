## Summary

Four plans landed: a template-comment fix (27.1-01), admin label/lock work (27.1-02), a shared
site-review queryset helper (27.1-03), and a re-import site-preservation guard (27.1-04). The
quality gates are genuinely clean (`ruff check` and `ruff format --check` pass on all changed
Python; all 181 tests in the four affected modules pass), and the two template edits are
structurally correct.

That is where the good news stops. Three defects were reproduced empirically during this review
using throwaway probe tests (since removed; the repo tree is unmodified):

1. The new site-preservation guard in `import_campaign_csv.py` writes a **`telescope_class` onto a
   run whose resolved site it just preserved** — proven output: `site = 705: SOAR`,
   `telescope_class = '1m0'`, `site_needs_review = True`. That triple violates three separate
   invariants the codebase states in prose, and `telescope_class` is by design never cleared by any
   writer, so the wrong value is permanent. The new tests deliberately dodge this interaction
   (case 4's own comment says it picks an instrument with "no aperture-class-matching phrase").
2. `CalendarEventMetaAdmin`'s standalone change form still exposes the `event` **primary key** as an
   editable select. Repointing it via an admin POST produced two `CalendarEventMeta` rows where
   there was one — exactly the duplicate/orphaned-history failure `CalendarEventMetaInlineFormSet`
   and migration 0008 exist to prevent. This phase made that admin materially more reachable
   (autocomplete, `event_start` column, `run` in `list_display`, `list_select_related`) without
   extending the freeze to it, while `admin.py:80-82` asserts the freeze is comprehensive.
3. The paired pre-executed notebook — a stated deliverable under CLAUDE.md — carries committed
   outputs that **contradict its own prose** and the phase's claims, as a direct consequence of the
   new guard making the notebook non-idempotent.

Answering the four questions posed in the phase context directly:

1. **`source` lock:** it holds on the standard change form (GET render and POST bind, verified), and
   the add form / bulk paths are not exploitable because `approval_status` is class-level readonly.
   But the lock is state-dependent and bypassable in two steps by the same actor — see WR-03.
2. **Site-preservation guard:** the core condition is right for the case it targets, but it has
   three problems: the `telescope_class` interaction (CR-01), silent discard of a legitimately
   corrected `Site Code` with no operator signal (WR-01), and orphan placeholder `Observatory` rows
   left behind (WR-02, reproduced).
3. **`runs_needing_site_review()`:** the queryset is byte-equivalent to the two filters it replaced,
   and the widened banner introduces exactly one extra `COUNT(*)` per campaign-list request — no
   N+1. This is the cleanest of the four plans. Only nits (IN-01, IN-02).
4. **Templates:** both are correct. Tag nesting balances, `{% comment %}` blocks containing literal
   `{% if %}` text are safely skipped by `Parser.skip_past('endcomment')`, and `{% if run.window_start %}`
   is a sound TBD gate (a `date` is always truthy; a missing reverse-one-to-one yields `''`).

## Critical Issues

### CR-01: Re-import writes `telescope_class` onto a run whose resolved site was just preserved

**File:** `solsys_code/management/commands/import_campaign_csv.py:202-206, 296-308`

**Issue:** `telescope_class` is computed from the CSV's *fresh* resolution result
(`... if site is None else ''`) at line 202-206, but the site-preservation guard at line 296 runs
*afterwards* and can decide the run keeps its existing resolved site. Nothing re-reconciles the two.
The `telescope_class` pop at line 307 only guards the reverse direction (`existing.telescope_class`
truthy and new value blank); it does not guard the case where `existing.telescope_class` is blank and
a class is newly derived for a row whose site is preserved.

Reproduced (probe test, since deleted). Existing row: `site=<Observatory 705 SOAR>`, `site_raw='705'`,
`site_needs_review=True` (the documented projection-failed retry state), `telescope_class=''`. CSV
row: `Telescope / Instrument = 'LCO 1m network'`, `Site Code = ''`. After re-import:

```
PROBE site = 705: SOAR | telescope_class = '1m0'
PROBE site_needs_review = True
PROBE __str__ = #1 Probe Campaign | LCO 1m network | 2025-07-04 | 705
```

Three stated invariants are violated at once:

* `solsys_code/models.py:227-229` — "telescope_class is never inferred for a run whose site DID
  resolve." It just was.
* `solsys_code/models.py:223-225` — the value "is NEVER cleared by any writer once a site later
  resolves." So this wrong value is **permanent** and unrecoverable except via the Django admin or a
  shell.
* `solsys_code/campaign_views.py:686-691` (`_resolve_site` docstring) — "a classed run can no longer
  carry `site_needs_review=True` at all (every writer now honours `telescope_class`), so it is
  already ineligible here via this same guard — no separate `telescope_class` check is needed." The
  importer just produced exactly that state, so the reasoning that justified omitting a
  `telescope_class` check in `_resolve_site()` no longer holds.

This is not an edge case — it is the guard's **primary intended scenario**. The guard exists for rows
`repair_stale_campaign_run_sites` fixed, and that command only ever runs against rows whose CSV
`Site Code` failed to resolve (see its module docstring). `derive_telescope_class` fires purely on
`telescope_instrument` text (`'LCO 1m network' -> '1m0'`, `'2m0 Faulkes' -> '2m0'`,
`'JUICE/JANUS' -> 'SPACE'`) or on a `500@-<naif>` `site_raw`, so the collision is common in the real
3I/ATLAS sheet shape. `telescope_class` is also in `ALLOWED_FIELDS_FOR_NON_STAFF`
(`campaign_views.py:83`), so a bogus "1m0 class allocation" is rendered publicly on a run pinned to a
single site.

**Fix:** gate derivation on the *effective* post-guard site, not the CSV's fresh result. Compute the
guard decision first, then derive:

```python
site, site_resolution_failed = resolve_site(site_raw)
existing = CampaignRun.objects.filter(**lookup).first()
preserve_site = existing is not None and existing.site_id is not None and (site is None or site_resolution_failed)

# D-06/D-13: only ever derive a class for a row that will actually end up site-less.
# `preserve_site` means the row keeps its already-resolved site, so there is no
# "why is there no site" question for a class to answer.
telescope_class = (
    derive_telescope_class(site_raw=site_raw, telescope_instrument=telescope_instrument)
    if site is None and not preserve_site
    else ''
)
needs_review = site_resolution_failed and not telescope_class
...
if preserve_site:
    fields.pop('site', None)
    fields.pop('site_raw', None)
    fields.pop('site_needs_review', None)
```

Add a regression test that is the mirror image of `test_telescope_class_never_blanked_by_reimport`:
existing row with a resolved site and blank `telescope_class`, CSV row with a class-bearing
instrument and a non-resolving `Site Code`; assert `run.telescope_class == ''` after re-import.

### CR-02: `CalendarEventMetaAdmin`'s change form lets staff repoint the primary key, duplicating the row

**File:** `solsys_code/admin.py:202-217` (and the freeze claim at `solsys_code/admin.py:10-32, 80-82`)

**Issue:** `CalendarEventMeta.event` is an explicitly declared `OneToOneField(primary_key=True)`, which
Django treats as editable, so it appears in the generated `ModelForm` for the standalone
`CalendarEventMetaAdmin` change view. `CalendarEventMetaInlineFormSet` was written in Phase 27
specifically to stop this pk from being repointed — but that hardening lives only on the *inline*.
The standalone admin has no equivalent guard, and this phase made that admin the primary staff
surface (added `autocomplete_fields = ['run']`, `event_start`, `run` in `list_display`,
`list_select_related`) without extending the freeze.

Reproduced (probe test, since deleted) via a real admin POST as a superuser:

```
PROBE GET status 200
PROBE change form has name="event": True
PROBE POST status 200
PROBE meta rows now: [(1, False), (2, False)]     # one row in, TWO rows out
```

This is precisely the failure `admin.py:15-19` describes: "`instance.save()` would issue an UPDATE
matching 0 rows and fall back to an INSERT -- leaving the original row behind as a duplicate with an
orphaned `is_verified`/run history, which is exactly what migration 0008's header comment was written
to protect." If the target event already has its own companion row, `Model._do_update()` matches that
row instead and **silently clobbers** its `is_verified`/`run` values.

`admin.py:80-82`'s claim — "add and delete are the only operations on the link itself" — is therefore
false as written; it is true only of the inline.

**Fix:** freeze the pk on the standalone admin too, and keep it re-pointable only by delete + re-add:

```python
class CalendarEventMetaAdmin(admin.ModelAdmin):
    ...
    def get_readonly_fields(self, request, obj=None):
        """WR-08 parity with CalendarEventMetaInlineFormSet: `event` is this model's primary
        key, so repointing it on an existing row duplicates (or clobbers) rather than moves.
        Editable on add, frozen on change.
        """
        readonly = list(super().get_readonly_fields(request, obj))
        if obj is not None:
            readonly.append('event')
        return readonly
```

Add a test that POSTs a different `event` pk to
`admin:solsys_code_calendareventmeta_change` and asserts `CalendarEventMeta.objects.count()` is
unchanged and `event_id` is unchanged. The same probe used above is a ready-made regression test.

## Warnings

### WR-01: Site-preservation guard silently discards a legitimately corrected `Site Code`

**File:** `solsys_code/management/commands/import_campaign_csv.py:296-299`

**Issue:** The guard fires whenever `site is None or site_resolution_failed`, which includes the case
where the operator *corrected* the sheet's `Site Code` to a genuinely new code that MPC does not know
(tier-3 placeholder) or that exceeds `_MAX_OBSCODE_LEN`. In that case the run keeps its old `site`
**and** its old `site_raw`, and the operator's correction is thrown away with **no stderr line, no
log call, and no summary counter**. The command prints `updated`/`unchanged` exactly as if the write
had landed. The comment at line 293-295 asserts "A CSV cell that DOES genuinely resolve still wins",
which is true, but says nothing about the operator being unable to tell which case they got. The
runbook change at `docs/runbooks/telescope_runs_calendar.rst:234-250` has the same blind spot.

**Fix:** emit a diagnostic when the guard fires, and add a counter to the summary line:

```python
if preserve_site:
    fields.pop('site', None)
    fields.pop('site_raw', None)
    fields.pop('site_needs_review', None)
    site_preserved_count += 1
    self.stderr.write(
        f'Row {row_num}: kept existing resolved site {existing.site_id} '
        f'(Site Code={site_raw!r} did not resolve); CSV site/site_raw discarded'
    )
```

and append `site_preserved: {site_preserved_count}` to the `Done.` line, so a discarded correction is
visible rather than silent.

### WR-02: Orphan placeholder `Observatory` rows accumulate on every re-import

**File:** `solsys_code/management/commands/import_campaign_csv.py:194, 296-299`

**Issue:** `resolve_site(site_raw)` is called unconditionally at line 194 with the default
`create_placeholder=True`, so an unresolvable `Site Code` creates a tier-3 placeholder `Observatory`
(`campaign_utils.py:260-272`). The new guard then pops `site` from `fields`, so the placeholder is
never linked to anything. Reproduced (probe test, since deleted):

```
PROBE observatories = [('F65', 'FTN'), ('Z99', 'NEEDS REVIEW: Z99')]
PROBE runs referencing Z99 = 0
```

Before this phase the placeholder was at least attached to the run. Now it is a pure orphan. It
still satisfies `is_placeholder_observatory()`, still enters `build_site_candidates()`, and still
wins tier 1 for that obscode on every future resolution — which is the exact pollution
`CampaignRunDecisionView._resolve_site()`'s WR-03 cleanup (`campaign_views.py:764-774`) was written
to prevent, except that cleanup only deletes a placeholder it *replaces* on a run.

**Fix:** either short-circuit before creating the placeholder when the row will be preserved (fetch
`existing` before calling `resolve_site`, and pass `create_placeholder=False` when
`existing.site_id is not None`), or delete the just-created orphan when the guard fires, reusing
`_resolve_site()`'s "no other CampaignRun still references it" guard.

### WR-03: The `source` provenance lock is bypassable in two steps and untested against that bypass

**File:** `solsys_code/admin.py:141-155`

**Issue:** The lock keys on the *current* row state (`WEB` **and** `APPROVED`). Because `source`
stays editable while the run is `PENDING_REVIEW` (deliberately, per D-19 — and
`test_submitted_source_value_does_bind_on_pending_web` proves it works), a staff user can:

1. Open a `WEB` + `PENDING_REVIEW` run in the admin and set `source = csv_import`.
2. Approve it through `CampaignRunDecisionView` (which only requires `approval_status == PENDING_REVIEW`,
   `campaign_views.py:558-560`).

The result is `APPROVED` + `csv_import`, which under CANON-01's derivation rule reads as "no approval
was required" — the exact provenance destruction the lock exists to prevent, reached without ever
touching a locked row. It also removes the run from the importer's WEB carve-out
(`import_campaign_csv.py:277`), so a later CSV re-import will now overwrite it.

The seven `SourceProvenanceLockTests` cover the change form thoroughly but none covers this sequence,
so the lock reads as stronger than it is. The class docstring at `admin.py:129-138` should not claim
more than the lock delivers.

**Fix:** lock on `source == WEB` alone (any approval status), which costs only the ability to relabel a
pending WEB row — a case D-19's "correction use case" does not actually need, since a WEB row's source
is not a guess. If the pending-editable behaviour is genuinely wanted, add a test asserting the
two-step sequence and document the residual gap explicitly in the docstring rather than leaving it
implied-closed.

### WR-04: `site_needs_review` summary counter now under-reports genuine queue members

**File:** `solsys_code/management/commands/import_campaign_csv.py:315-316`

**Issue:** The counter is gated on `'site_needs_review' in fields`, so when the preservation guard
pops the key the row is never counted — including when the row's *existing* flag is `True` (the
projection-failed retry state, which `runs_needing_site_review()` explicitly includes,
`campaign_views.py:199-200`). The row really is in the staff queue; the summary says otherwise. The
runbook's "so a preserved row no longer inflates it"
(`docs/runbooks/telescope_runs_calendar.rst:249-250`) states only the half of the change that reads
as an improvement.

**Fix:** count the flag's *resulting* value, not the written one:

```python
resulting_needs_review = needs_review if 'site_needs_review' in fields else existing.site_needs_review
if resulting_needs_review:
    site_needs_review_count += 1
```

and reword the runbook line to say the counter reports the number of rows that end up flagged, not
the number of flags written.

### WR-05: The repo-wide template-comment sweep stops scanning a file after the first unterminated `{#`

**File:** `solsys_code/tests/test_calendar_template.py:588-596`

**Issue:** When `content.find('#}', start + 2)` returns `-1`, the loop records the failure and
`break`s out of the *whole file*, so any further multi-line `{# ... #}` blocks later in that same file
are never examined. A single stray `{#` (for example inside a JS object literal or a CSS selector)
therefore silently disables the guard for the rest of that template — and a stray `{#` is exactly the
kind of thing that makes the sweep's own heuristic fire. The scan also has no awareness of
`{% comment %}`/`{% verbatim %}` regions or `<script>` blocks, so it can report a false positive that
cannot be silenced except by changing the content.

**Fix:** on an unterminated `{#`, record the failure and `search_from = start + 2; continue` instead of
`break`, so scanning continues; and either skip `<script>`/`{% verbatim %}` regions or require the
opening `{#` to be at the start of a (possibly indented) line, matching how the real defect appeared.
