## Findings addressed

### CR-01 — `telescope_class` derived from a site the guard then discards

**Commit:** `ec931d3` (merged via `d4bf04d`)
**Files:** `solsys_code/management/commands/import_campaign_csv.py`,
`solsys_code/tests/test_import_campaign_csv.py`

`telescope_class` was derived from the CSV's *fresh* resolution result, while the new
site-preservation guard ran afterwards and could keep the row's *existing* site. Nothing
reconciled the two, so a re-import produced the contradictory triple
`site=705 / telescope_class='1m0' / site_needs_review=True`. Because no writer ever clears
`telescope_class`, the wrong value was permanent.

The fix computes the natural-key lookup and the `preserve_site` decision *before* deriving
`telescope_class`, and gates derivation on `site is None and not preserve_site`, so a class is
only ever inferred for a row that actually ends up site-less. This upholds `models.py`'s
invariant that `telescope_class` is never inferred for a run whose site did resolve, and never
clears an existing class — the permanence invariant is preserved.

Regression test case 9 was added as the mirror image of
`test_telescope_class_never_blanked_by_reimport`. The original 27.1-04 tests did not catch this
because case 4 deliberately picks an instrument with no aperture-class-matching phrase.

**Verified:** `test_import_campaign_csv` — 69 tests, OK.

### CR-02 — standalone admin let staff repoint the primary key, duplicating the row

**Commit:** `efe7240`
**Files:** `solsys_code/admin.py`, `solsys_code/tests/test_admin.py`

`CalendarEventMetaInlineFormSet` froze `event` only on the inline. `CalendarEventMetaAdmin` is
a second, independent write path onto the same row, and 27.1-02 made it the primary staff
surface for hand-linking a run to an event. Because `CalendarEventMeta.event` is an explicitly
declared `OneToOneField(primary_key=True)`, Django treats it as editable and rendered it as a
live `<select>` there too. A real admin POST turned one row into two: `save()`'s UPDATE matched
0 rows and fell back to an INSERT, leaving the original behind as a duplicate with orphaned
`is_verified`/`run` history — the failure migration 0008's header comment exists to prevent.

`get_readonly_fields()` now returns `event` as readonly on change (`obj is not None`), which
drops the field from the form so a submitted value is never bound; the instance keeps resolving
from the URL pk. Add stays editable, so re-pointing remains available as delete + re-add —
matching the inline's add-and-delete-only contract rather than being stricter than it.

**Reproduced first:** the new `CalendarEventMetaStandaloneAdminPkFreezeTests` failed 2 of 3
tests against the unfixed admin, including the duplication case.
**Verified:** `test_admin` — 35 tests, OK.

### CR-03 — pre-executed notebook outputs contradicted its own prose

**Commit:** `b970fc9`
**File:** `docs/notebooks/pre_executed/import_campaign_csv_demo.ipynb`

This was collateral damage from 27.1-04's own guard. Cell 21 resolves `Uma Unresolved`'s site by
hand to demonstrate the guard; before the guard existed, the subsequent re-import reverted that
mutation, so the next execution started from a clean row. The guard correctly preserves it,
which left the row resolved in the persistent dev DB — so cells 9–11 reported the *previous*
run's leftover state. Cell 11 printed `site=705 / site_needs_review=False` directly beneath cell
10's prose saying Uma "IS flagged via `site_needs_review`", and cell 9's table showed `False`
where cell 22's summary claimed `True`.

Added an explicit teardown restoring the unresolved starting state after the guard has been
demonstrated, so the notebook leaves the database as it found it and is re-executable. The
notebook was regenerated with `jupyter nbconvert --to notebook --execute --inplace` and
committed with output per the `pre_executed/` convention.

**Verified after regeneration:** cell 9's table shows `True` for `Unassigned facility`; cell 11
shows `site=None / site_needs_review=True`; cell 21 still shows the repaired site surviving the
re-import; every code cell carries output.

## Not addressed in this pass

are related to the fixed blockers but are genuinely separate defects:

- **WR-03** — the `source` lock holds on the change form but is bypassable in two steps (edit
  while `PENDING_REVIEW`, then approve).
- **WR-01 / WR-02** — the site guard also silently discards legitimate corrections, and leaks
  orphan placeholder `Observatory` rows (reproduced by the reviewer).

These do not have reproduced data-corruption consequences of the same severity as CR-01/CR-02,
but WR-03 undercuts the CANON-01 provenance guarantee that 27.1-02 criterion 6 exists to
protect, so it should not be deferred indefinitely.
