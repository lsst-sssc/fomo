<objective>
Close the one open gap in Phase 27.1: success criterion 6. Widen `CampaignRunAdmin`'s `source`
provenance lock from the `(APPROVED, WEB)` combination it shipped with to every `source == WEB`
row, at any approval status — this is **Option A** from `27.1-VERIFICATION.md`'s `missing:` field
and the fix `27.1-REVIEW.md` WR-03 itself proposed.

Purpose: the shipped lock protects exactly the state it checks, but a legal two-step sequence any
staff user can perform reaches the identical outcome without ever touching a protected row — edit
`source` while the run is still `PENDING_REVIEW` (editable by design per D-19), then approve it via
`CampaignRunDecisionView`, which only requires `approval_status == PENDING_REVIEW`. The row lands
on `APPROVED` + non-WEB, which under CANON-01's derivation rule reads as "no approval was
required": the exact provenance loss the lock exists to prevent.

Output: a one-term change to `get_readonly_fields`, an inverted-and-extended
`SourceProvenanceLockTests`, a new regression test that drives the whole two-step sequence
end-to-end, and an operator-facing runbook section stating the rule, its cost, and what stays open.

## Why Option A (close the hole), not Option B (record the consequence)

The user delegated this choice to the planner. Four pieces of evidence in the codebase decide it,
and none of them is a judgement call about difficulty:

**1. A WEB label is never a guess, so D-19's correction use case cannot apply to it.**
`source = WEB` is written by exactly one code path in the whole repository:
`campaign_views.py:283`, the public submission view. No importer, adapter, backfill, migration or
management command produces it. D-19 kept `source` editable so staff could correct a *mislabelled*
ingest source — a real need for `legacy` (a bulk backfill value applied to every pre-v2.2 row, i.e.
a genuine guess) and for `csv_import`. There is no mechanism by which a row wrongly becomes WEB, so
the editability being removed here has no correction use case behind it. Option A costs an ability
that exists only in principle.

**2. The codebase already enforces Option A's rule on the other write path.**
`import_campaign_csv.py:308` refuses to rewrite `source` whenever `existing.source == WEB`, with
**no approval-status condition at all**, and the comment above it gives CANON-01's derivation rule
as the reason. FOMO therefore already applies one rule to the CSV write path ("a WEB row's `source`
is never rewritten") and a strictly weaker rule to the admin write path ("...but only once it is
approved"). The gap is precisely the difference between the two. Option A makes both write paths
enforce one rule; Option B would leave FOMO documenting two different rules for one field — the
harder thing to keep true as Phases 28 and 29 add more writers.

**3. The runbook already states the rule in Option A's form.** Lines 220-226 already tell operators
that a `source = web` row "keeps its own ``source`` **and** ``approval_status``", unconditionally.
Under Option B that paragraph would need walking back with an admin-specific exception. Under
Option A it is extended, not contradicted.

**4. Option B cannot close the criterion, only annotate it — and the loss it would annotate is
permanent.** There is no audit field on `CampaignRun` from which a former `source` can be
reconstructed, and both Phase 28's attribution queue and Phase 29's reconciler read
`source`/`approval_status` as provenance input. A documented hole is a hole every later phase has
to route around.

**Cost of Option A, measured before choosing it.** Staff lose the ability to relabel a *pending*
WEB row through the admin change form. A repository-wide search for consumers of that ability found
exactly one: the test `test_submitted_source_value_does_bind_on_pending_web`
(`test_admin.py:670-681`), written by 27.1-02 to demonstrate that the lock was narrow — a
characterisation test, not a product requirement. No view, form, template, management command,
notebook or runbook procedure relabels a WEB row. The same correction friction already exists on
the CSV path, where 27.1-04 accepted it deliberately. The escape hatch stays what it already is
there: a shell or a data migration.

**What Option A does NOT close, and is therefore recorded rather than fixed.** The lock keys on the
row's *current* `source`, so it is a one-way ratchet: a non-WEB row can still be relabelled *to*
`web`, after which it locks. That direction fabricates provenance rather than destroying it, it
requires a deliberate staff act, and Django's admin `LogEntry` records the field change with actor
and timestamp — unlike the destructive direction, which leaves nothing behind. Locking it too would
re-open D-19 for the sources D-19 legitimately covers. This residual is accepted, and the plan
requires it to be written into both the docstring and the runbook, which is what satisfies
criterion 6's "records its consequence" clause for the part that stays open.

**This does not re-open D-19 as a whole.** The class-level `readonly_fields` list stays
`['approval_status']`; editability is narrowed per instance only. Every `legacy`, `csv_import`,
`classical_file`, `lco_queue` and `gemini_queue` row of every approval status keeps an editable
`source`, and the add form is untouched, so a run can still be created with any source.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public submitter → campaign submission form | Untrusted public input creates a `CampaignRun` with `source = WEB` and `approval_status = PENDING_REVIEW` (`campaign_views.py:283`). This is the only writer of `WEB` in the repository. |
| staff user → Django admin change form | Privileged, but not fully trusted for provenance fields: an admin write is a direct field-level write with no domain validation between the form and the row. |
| staff user → `CampaignRunDecisionView` POST | Privileged state transition. Gated only on `approval_status == PENDING_REVIEW` — it does not inspect `source`, so it will approve whatever `source` the row happens to be carrying when it runs. |
| CSV file → `import_campaign_csv` | Semi-trusted operator-supplied bulk data that can collide with an existing row on its natural key and rewrite it. |

The gap this plan closes lives in the composition of boundaries 2 and 3, which is why neither
surface's own tests could see it: each write is individually legitimate.
