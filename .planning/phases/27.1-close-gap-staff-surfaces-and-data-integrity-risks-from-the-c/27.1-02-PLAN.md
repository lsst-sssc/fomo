## Decisions recorded by this plan

### Criterion 6 decision: option (a) -- `source` becomes non-overwritable on an already-approved WEB run

Chosen deliberately over option (b) (leave it editable and record the consequence).

**Why (a).** `CampaignRun.Source`'s own docstring (`solsys_code/models.py:90-94`) states the
CANON-01 derivation rule verbatim: *"`approval_status == APPROVED` together with `source != WEB`
means no approval was required -- a different fact from a human having approved the run."*
On an `APPROVED` + `WEB` row, `source` is the *only* field carrying the fact that a human
reviewed a public submission. Overwriting it does not mislabel a row, it destroys the
distinction the whole vocabulary exists to express, silently and irreversibly -- there is no
audit field on `CampaignRun` to reconstruct it from. This is exactly the "loss of the CANON-01
provenance signal" consequence the roadmap criterion names, and it is cheaper to prevent than to
document.

**Why this does not re-open D-19.** D-19 kept `source` editable so staff could correct a
mislabelled ingest source; `admin.py:129-132` records that as a deliberate omission from
`readonly_fields`. This plan does not add `source` to the class-level `readonly_fields` -- it
narrows editability *per instance*, only on the `APPROVED` + `WEB` combination. Every other row
stays exactly as D-19 left it: a `PENDING_REVIEW` web submission, a `REJECTED` web submission,
and every `legacy`/`csv_import`/queue-sourced row of any approval status all keep an editable
`source`. D-19's correction use case survives; only the one destructive case is closed.

**Accepted cost.** A genuinely mis-recorded `source` on an approved web row can no longer be
corrected through the admin change form; it needs a shell or a data migration. That is the
intended friction -- the correction is rare, the accidental overwrite is not.

### Criterion 4 decision: fix the labels, not the picker widget alone

`CampaignRun.__str__` today is `f'{campaign.name}: {telescope_instrument} on {window_start}'`.
Measured against the live dev DB (44 runs): it renders `on None` for all 6 TBD rows, and pks 27
and 28 (`3I/ATLAS: JWST on None`) are byte-identical to each other. `CalendarEventMeta.__str__`
renders `Verified label for [EXPIRED] 2m0 2M0-SCICAM-MUSCAT` for 7 of the 11 companion rows --
identical text. Fixing `__str__` rather than a per-admin `label_from_instance` means every
surface benefits (change-form title, delete confirmation, admin history `object_repr`,
autocomplete results) instead of one widget.

`autocomplete_fields` is added on top so staff can search instead of scanning 44 flat options;
this is safe because `CampaignRunAdmin.search_fields` already exists (`admin.py:127`), which is
what Django's `admin.E040` check requires. It is added ONLY for `CalendarEventMetaAdmin.run`.
`CalendarEventMetaInline`'s `event` field is deliberately left alone -- it points at upstream
`tom_calendar.CalendarEvent`, whose ModelAdmin registration FOMO does not own, so
`autocomplete_fields` there would risk an `admin.E040` on a third-party admin.
