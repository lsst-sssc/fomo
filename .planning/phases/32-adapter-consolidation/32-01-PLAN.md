<objective>
Build everything the three adapter cutovers stand on, and prove it end to end before any
adapter consumes it: the schema shape Phase 31 specified but never built (nullable
`campaign`, `source_identifier` plus its partial unique constraint, and the `SOAR_QUEUE`
source value), null guards at the five sites that dereference `run.campaign.name`, and one
shared `write_and_reconcile_campaign_run()` helper that creates-or-updates a `CampaignRun`
and hands calendar projection to the existing `reconcile_run()`.

Purpose: nothing downstream can write a non-campaign `CampaignRun` until the migration
lands, and the first null-campaign row to reach `reconcile_run()` crashes on
`campaign_reconciler.event_title()` unless the guards land first. This plan is the phase's
groundwork (ROADMAP scope note) and its cutover-safety machinery (ADAPT-05).

Output: two migrations, a public shared helper plus an adoption bridge in
`campaign_utils.py`, five guarded read sites, a container-branch adopt step in the
reconciler, two new test modules, and a regenerated reconciler demo notebook.
</objective>

  <decision>
    Three architectural decisions must be confirmed before any code lands, because two of
    them are one-way and the third changes what an operator sees on the calendar.

    **1. Queue-sourced calendar fidelity at cutover (NEW finding, not resolved in any
    source artifact).**
    `CampaignRun.window_start`/`window_end` are `DateField`s, and `reconcile_run()` derives
    every event's title and time span from the run. Consequences once
    `sync_lco_observation_calendar` and `sync_gemini_observation_calendar` stop writing
    `CalendarEvent` directly:
      - a placed LCO/SOAR observation's precise `scheduled_start`/`scheduled_end` block
        (often ~1 hour) becomes a whole-window span of `window_start` 00:00 UTC to
        `window_end` 23:59 UTC;
      - the adapters' rich title prefixes (`[QUEUED]`, `[EXPIRED]`, `[FAILED]`,
        `[UNVERIFIED]`, `[ON_HOLD]`) collapse into the reconciler's two-value vocabulary
        (`[CANCELLED]`, `[WEATHERED]`), because status-vocabulary unification is Phase 35
        and is explicitly out of scope here;
      - event titles become `{campaign}: {telescope_instrument}` instead of
        `{telescope} {instrument}`.
    The classical adapter does NOT suffer this: the reconciler recomputes the same
    `sun_event(site, night, kind='sun')` values `load_telescope_runs` already computes, so
    BoN/EoN nights project identically.
    Options:
      (a) **Recommended — adopt-and-converge.** Ship all three adapters this phase. The
          reconciler's container branch gains an adopt step so pre-existing url-keyed queue
          events are re-keyed into the run's `RUN:` namespace instead of being duplicated or
          orphaned (ADAPT-05's bar is met), and their spans/titles converge to the
          reconciler's vocabulary. The fidelity narrowing is recorded in
          `docs/runbooks/telescope_runs_calendar.rst` as a known consequence with Phase 35
          named as where richer status vocabulary returns.
      (b) Ship ADAPT-01 (classical) this phase and defer ADAPT-02/03/06 until Phase 35 has
          unified the status vocabulary. This is a phase split and needs a ROADMAP edit.
      (c) Extend `CampaignRun` with time-of-day window fields so precise queue windows
          survive the round trip. This reopens the schema Phase 31 locked.

    **2. Classical `source_identifier` form.**
    31-DECISION.md's prose says `CLASSICAL:{telescope}:{instrument}:{bucket}` with 5-minute
    bucketing of `start_time`, but its own constraint probe actually round-tripped the DATE
    form (`CLASSICAL:SPIKE-NTT:SPIKE-EFOSC2:2026-09-05`) and flags the datetime form as
    unproven. `load_telescope_runs`'s `start_time` drifts ~2s between ingests from IERS
    refreshes, and `calendar_utils.insert_or_create_calendar_event()`'s own docstring warns
    that any fixed bucketing splits a value that drifts across a bucket boundary — which
    would mint a duplicate `CampaignRun` and break ADAPT-04's no-churn bar.
    Recommended: use the observing-night date,
    `CLASSICAL:{telescope}:{instrument}:{night.isoformat()}` — drift-free, and identical to
    the `window_start`/`window_end` the same row already carries.

    **3. `SOAR_QUEUE` is one-way (D-01, already user-locked).**
    Adding the `TextChoices` member plus its migration is reversible in code but not in
    data: once SOAR-sourced rows exist under `soar_queue`, folding them back into
    `lco_queue` is a data migration. Confirming here only because REVERSIBILITY_GATES
    requires a one-way decision to be gated before the task implementing it — this is a
    re-confirmation of a decision the user already locked, not a reopening.

    **4. SOAR and Gemini runs cannot reach the calendar at all without a resolved
    `Observatory` (NEW blocker, not covered by RESEARCH.md).**
    `campaign_reconciler._skip_reason()` returns `'unresolved site'` for any run with
    `site is None` and a blank `telescope_class`, so such a run is written but never
    projected. `calendar_utils.derive_telescope_class()` returns `''` for SOAR, because
    D-12 deliberately keeps `4m0` out of `CampaignRun.TelescopeClass` and the function has
    an explicit "do not fix this by adding 4m0 to the model" comment; it also returns `''`
    for Gemini, whose 8m aperture matches no token at all. Only LCO's 2m0/1m0/0m4 records
    derive a class. Left unaddressed, ADAPT-03 and ADAPT-06 would ship runs that never
    appear on the calendar — the exact opposite of the phase goal.
    Options:
      (a) **Recommended — resolve a real `Observatory` for the site-less facilities.** LCO
          records that yield a telescope class keep `site=None` and take the container
          branch (one whole-window event, matching today's one-event shape). SOAR and
          Gemini records get `site` resolved by MPC obscode from the `Observatory` table
          (`I33` for SOAR at Cerro Pachón, `I11` for Gemini South, `568` for Gemini North —
          each to be verified against the `Observatory` table before use) and therefore take
          the per-night branch. Consequence: a placed record whose window is a single night
          gets exactly one event, and a banner-stage record with an N-night window gets N
          nightly events instead of one spanning event. A record whose `Observatory` row
          does not exist is written anyway and reported as not projected, so it is
          self-healing the moment an operator creates the record — and the runbook tells
          them which obscodes to create.
      (b) Add `4m0` and an 8m class to `CampaignRun.TelescopeClass`. Directly contradicts
          D-12's explicit prohibition; would need that decision reopened.
      (c) Widen `_skip_reason()`'s site gate so a class-less, site-less queue run still
          projects. Changes reconciler semantics that Phase 29 locked.
      (d) Cut ADAPT-03 and ADAPT-06 from this phase. Same phase split as option 1(b).
  </decision>
