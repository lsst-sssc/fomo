  <name>Task 1: Decide the proposal-code carrier and the unused-hours formula</name>
  <decision>
Two coupled choices must be confirmed before the migration is written, because undoing either
needs a data migration.

**(a) Where does a proposal code live?** RESEARCH.md confirmed by exhaustive grep that no
active write path stores a structured proposal code: `CampaignRun` has no such field, the web
submission form and the CSV importer never capture one, and the classical loader's bracketed
`[proposal]` token is only concatenated into the free-text `observation_details` line.

- **Option A (recommended, RESEARCH.md's own recommendation):** add
  `CampaignRun.proposal_code = CharField(max_length=100, blank=True, default='')`, populated by
  the classical loader from the parsed token, left blank for web/CSV runs until a follow-up
  captures it there too. Pro: D-06/D-07 are buildable now; the "not yet fetched" fallback
  already covers the blank rows. Con: a new column on the main model, and a second follow-up is
  needed before every run has one.
- **Option B:** scope the fetch to `WatchedProposal.proposal_code` only, and treat every
  classical/CSV/web run as not-fetchable. Pro: no new column. Con: a classical allocation — the
  exact case D-06 exists for — never gets an unused-nights figure.
- **Option C:** regex-parse `observation_details` at fetch time. Pro: no schema change. Con:
  RESEARCH.md Pitfall 2 — that field is staff-editable free text; a hand edit silently points
  the fetch at the wrong proposal.

**(b) Which portal time-allocation fields feed the estimate?** RESEARCH.md assumption A2 says
sum `std_allocation` minus `std_time_used` only. If FOMO's watched proposals actually hold
Rapid-Response (`rr_*`) or Time-Critical (`tc_*`) time, that undercounts. Confirming needs one
live `GET https://observe.lco.global/api/proposals/&lt;code&gt;/` with the configured
`FACILITIES['LCO']['api_key']` against one real watched proposal.
  </decision>
  <context>
Undo cost for (a): both options that change the schema require a migration to reverse, and
Option A's column is read by the tally cache (37-04), the Progress column (37-05) and the
pop-up block (37-06) once they land. Undo cost for (b): a wrong formula silently under- or
over-states every public "unused" figure, and the stored rows would need re-fetching.

Recommendation: Option A for (a); for (b), store every allocation-type pair the portal returns
(`std`, `rr`, `tc`) as separate rows so the summation rule can change later without a re-fetch,
and sum only the standard rows into the estimate until a live check says otherwise.
