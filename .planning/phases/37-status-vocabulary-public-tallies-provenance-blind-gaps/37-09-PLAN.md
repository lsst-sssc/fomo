<objective>
Close G-37-5 (CR-01), the one gap 37-VERIFICATION.md leaves open against Phase 37's Success
Criterion 2 / TALLY-01.

The defect, as independently reproduced by the verifier: `CampaignRunTableView.get_table_kwargs()`
(`solsys_code/campaign_views.py`, around lines 216-226) reimplements django-tables2's page
resolution -- it reads the `page` GET param, hardcodes `per_page` from `self.table_pagination`, and
slices `self.object_list` in `get_queryset()`'s order -- and hands the resulting pks to
`campaign_tally.tallies_for_runs()`. But `SingleTableMixin.get_table()` calls
`RequestConfig(...).configure(table)` AFTERWARDS, and `configure()` applies TWO more GET params the
slice never saw: `?sort=` (`table.order_by = request.GET.getlist(table.prefixed_order_by_field)`)
and `?per_page=` (`kwargs['per_page'] = int(request.GET[name])`, which overrides `table_pagination`).
Both change which rows are rendered. Rows outside the mirrored slice have no entry in the table's
`tallies` dict, so `render_progress()` falls into its muted not-available branch. Measured on a
30-run campaign: plain page 0 such cells; `?sort=-telescope_instrument` 5 of 25 rendered rows
without a tally; `?per_page=50` 5 of 30. TALLY-01 names the campaign table row as one of the two
surfaces the public tally must appear on, and the view's own docstring advertises that interactive
column-header sorting still works -- so this is a supported interaction that silently removes the
tally from a public page.

The fix the verifier sanctioned, and the one this plan takes: stop predicting the rendered row set
and start RESOLVING it. Move the tally fetch to after `RequestConfig.configure()` by overriding
`get_table()`, and read the pks off `table.paginated_rows` -- the same `BoundRows` the django-tables2
table template iterates. The tallies dict then covers exactly the rows rendered, for every
combination of `sort`, `page` and `per_page`, with no reimplementation left to fall behind.

**One consequence this plan must carry, not inherit silently.** Today's bug accidentally bounds the
tally pass at 25 runs, because `per_page` is hardcoded. Following the rendered rows removes that
accident: `?per_page=` is attacker-controlled, unauthenticated, and django-tables2 applies it with no
cap, so `?per_page=100000` would fan the per-run tally pass (roughly two to three queries per run)
across every run in the campaign on a public page. This plan therefore caps the incoming `per_page`
parameter at 100 -- the same bound `CampaignListView.paginate_by` already uses -- so `?per_page=50`
is honoured exactly and an unbounded request is not. That is T-37-09-02 in the threat model below,
and it is part of the fix, not a follow-up.

Purpose: Success Criterion 2 of Phase 37 -- "Any visitor -- not only staff -- sees on each run a live
tally". A tally that vanishes when a visitor clicks a column header is not a tally any visitor sees.

Output: a `get_table()` override that resolves the rendered rows, a deleted page-slice

boundary/tie/empty edges on a >1-page campaign, corrected docstrings, and an executed notebook cell
demonstrating the property on a real 30-run campaign.
