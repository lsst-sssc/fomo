<objective>
Close G-36-4. Step 2 of the runbook's "Setting it up on a fresh host" procedure -- the one section
ROADMAP SC 5 names -- tells the operator to put the API key at a nested settings key path inside
``local_settings.py``. That module is imported into its own namespace under an ``except ImportError``
guard (`src/fomo/settings.py:431-434`), so the assignment raises ``NameError``, the guard does not
catch it, and the settings module fails to import: gunicorn, every ``manage.py`` command, the
``run_unattended`` tick, ``check_unattended`` and the failure email that would report any of it all
die before running. The verifier reproduced this. The supported name is the flat ``LCO_API_KEY``,
documented only in settings.py's own comment and nowhere in `docs/`, so recovery requires reading
source -- the precise thing SC 5 forbids. The SOAR half is worse: no fold for SOAR exists at all, so
that facility's key stays an empty string whatever the operator writes.

Two things are fixed here, in this order. First the MECHANISM: the fold in `src/fomo/settings.py` is
extended so the one flat name fills both the LCO and the SOAR facility entries (SOAR authenticates
against the same LCO Observation Portal), and a committed test executes the real fold to prove it --
because prose cannot be made correct until the code's true reach is decided and proven. Then the
PROSE: step 2 names the flat setting, says in one clause why it must be flat, and says which
facilities the single key reaches.

Purpose: SC 5 is the criterion this breaks, and it breaks it in the worst available way -- a fresh
host provisioned from the documented procedure does not reach a running schedule at all. SCHED-08's
mechanism half is satisfied and unchanged; its documented half regresses until this closes. The
phase's SC-5 sufficiency read-through is on hold behind it (36-VERIFICATION.md human item 1), so
this gap also blocks the only measurement that can retire SC 5.

Output: a settings fold whose reach matches what the runbook claims, an executable proof of both the
working instruction and the fatal one, a step 2 an operator can follow verbatim, a slice-scoped gate
that fails if a copy-pasteable nested key path ever returns to the procedure, and a verification
record whose hold note names its release condition.

**No tracer in the plan-shape sense, but Task 1 IS the tracer.** This is gap closure against a
shipped phase, so there is no unproven architecture to slice. Task 1 is nonetheless the thin
end-to-end path the other two build on: the line an operator writes in `local_settings.py` →
Django's settings import → both facility entries → the accessor TOM's SOAR facility actually reads,
wired and proven in one runnable test before a single word of prose is rewritten.

**Scope fence (hard).** This plan closes G-36-4 and nothing else. Plan 36-07 created G-36-4 by
carrying an unrelated "same-class sibling" clarification into the subsection it was fixing; see the
"Deferred (do not touch)" section below for the advisory findings that stay deferred by name.
</objective>

<assumption_delta_decision>
**Seam:** singular → plural. One API-key fold target (`FACILITIES['LCO']['api_key']`) becomes two, as
soon as the SOAR half of G-36-4 is resolved against reality rather than left documenting a route with
no mechanism.

**Noun now primary:** the Observation Portal API key — one credential that authenticates FOMO against
the LCO Observation Portal for both the LCO facility and the SOAR facility — rather than "the LCO API
key", which read as facility-specific and produced the belief that SOAR needed a second one.

**Decision: `promote`.** The single flat setting `LCO_API_KEY` is promoted to feed both facility
entries; the fold pluralizes, the setting name does not. No `SOAR_API_KEY` is added.

**Rationale:** there is one secret, not two. `src/fomo/settings.py`'s own `FACILITIES['SOAR']` entry
already records that SOAR authenticates against the same LCO Observation Portal credentials and that
the entry exists only so the SOAR settings accessor resolves a real `api_key` key. A second flat name
for the same secret would give an operator two things to set, two things to rotate and two things to
let drift, and would make the runbook longer while making the host less likely to be correctly
configured — the opposite of what SC 5 asks for. Verified at plan time that the accessor really does
read the SOAR entry: `SOARSettings('SOAR').get_setting('api_key')` returns `''` today, which is the
silent-unauthenticated state the promote removes.

**What would force a later `add-alongside`:** SOAR issuing its own credential, distinct from the LCO
Observation Portal's. At that point a second flat name is added next to this one and the fold splits
per facility. Nothing in the current portal arrangement points that way, and the Task 1 test would
fail loudly on the day the two stop being the same key, because it asserts both entries carry the
same value.

**Reversibility:** `reversible` (two-way). Two added lines in a settings file, revertible in one
diff, observable by nothing outside this repository. No `checkpoint:decision` is owed.
