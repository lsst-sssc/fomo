# Phase 37.1 Plan 16: The observed telescope comes from the block the record's times came from Summary

**`resolve_placement_block()` now returns the block whose start is the record's stored `scheduled_start` (whichever rule stored the times) and falls back to FOMO's rule only when none matches, with the runbook, help strings, docstrings, two paired notebooks and the review ledger saying so (WR-21 to WR-23, IN-31 to IN-34).**

## Accomplishments

- **Lookup before and after (WR-21, route A).** Before (37.1-15), `resolve_placement_block()` always asked FOMO's rule for a finished request, so a COMPLETED record stored with a leftover pending block's times (by TOM's rule through one of its own routes, or by an earlier FOMO rule) was labelled with the took-data block's telescope: 'coj'/FTS beside times drawn at the pending block's 'ogg' night. After, it reads the block whose start is the stored start, so that record names 'ogg'/FTN, the record stored with the failed block's times names 'coj'/FTS, and a record whose times match no listed block keeps 37.1-15's result ('coj'/FTS).
- **Tracer, failing run before the change.** `test_the_observed_site_comes_from_the_block_the_records_times_came_from` failed at `site-on-pending` with `AssertionError: 'coj' != 'ogg'` on the unmodified code (3 portal calls were asserted and passed first). After the change it passes. It is review IN-33 (2) folded into the WR-21 test, replacing 37.1-15's `test_the_observed_site_of_a_completed_request_comes_from_the_block_that_took_data` with no copy kept.
- **Matching rules (A-43, A-44).** Both sides are read with `coerce_schedule_datetime()` and compared as exact instants (microseconds count). A single match is returned whatever its state now. Ties go to `select_schedule_block()` over the tied blocks alone with the same `request_finished`, else the last tied block. `ValueError`, `OverflowError` (for example `'0001-01-01T00:00:00+01:00'`), non-dict entries, a missing start and `stored_start=None` never match and never raise. One portal call, one `select_schedule_block()` call, no new top-level name in `calendar_utils.py`.
- **Correction pinned (A-45).** `test_the_documented_correction_moves_a_record_to_the_rules_block_and_then_its_telescope` passes: `update_observation_status()` moves a COMPLETED record from the pending block's times to the 4253588 block's (2026-07-12 08:55:50 UTC); the next sweep makes 0 portal calls and keeps 'ogg'/FTN; after the three observed-site parameters are removed one sweep makes one call and stores 'coj'/FTS. This test pins documentation, not new code, so it passed before and after the code change.
- **WR-22 wording (no behaviour change).** Both `--recheck-unscheduled` help strings and the module, `_schedule_lookup_is_needed()`, `_resolve_schedule()` and `Command` docstrings now say the flag reaches records missing a time, TOM's rule stores a leftover pending block's times, the flag never revisits a record that holds both times, and the correction is `FomoLCOFacility().update_observation_status(<id>)` (`FomoSOARFacility` for SOAR) followed by removing `observed_site`, `observed_telescope` and `observed_enclosure`.
- **Ride-alongs.** WR-23 (`[X]` row names the placed-block-never-ran case), IN-31 (embedded-list exception "re-read on every sweep" in the module, `select_schedule_block()`, gate and `_resolve_schedule()` docstrings, runbook rule and one-block paragraphs, backfill notebook cell `d4a7c2e0`), IN-32 (status_refresh step), IN-33 parts (1) and (3), IN-34 (docstring plus list test).

Cleanup removes 900663 (`finished-request records remaining: 0`). `project_observation_calendar_demo.ipynb` changes only markdown cell `7e7bd66e`, edited as JSON and never executed (A-52: a run snapshots the developer database and makes real portal calls). `reconcile_campaign_runs_demo.ipynb` was checked and is unchanged.
