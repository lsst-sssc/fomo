# Phase 37.1 Plan 13: Count a FAILED block that took data (G-37.1-6) Summary

**FOMO's block rule now counts a block the LCO portal reports FAILED after it took data (some configuration summary `time_completed` above zero), so the Didymos `--recheck-unscheduled` run stores those blocks' times and retires their ALLOC nights, proved on the real portal payload.**

## The rule, before and after

Before (37.1-07): `select_schedule_block()` returned the first COMPLETED block, else the last ABORTED or IN_PROGRESS block, else the last PENDING block. A block the portal reports FAILED was ignored, so the four Didymos requests whose only block is FAILED (4253588, 4272067, 4276100, 4282342) got no times and their ALLOC nights stayed.

After: the same tiers, but a FAILED block joins the started tier when `_block_took_data()` is True: `configuration_statuses` is a list with at least one dict entry whose `summary` is a dict whose `time_completed` is an `int` or `float`, not a `bool`, above 0. Ranking is otherwise unchanged (first COMPLETED returns at once, else the last started-tier block, else the last PENDING). A FAILED block with no data is skipped like an unknown state, so it never displaces an earlier started block and never beats a pending one. NOT_ATTEMPTED and CANCELED never give times even when they carry `time_completed` (documented in the module, `BlockState` and `select_schedule_block` docstrings; no members added).

**No-data treatment (A-17):** missing, None, wrong type at any level, a numeric string, a bool, NaN, zero and negative all read as no data; the helper never raises and reads only `time_completed` (never `reason`, never the summary's own `state`; request 4272067's summary says ABORTED inside a FAILED block).
