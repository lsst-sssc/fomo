# Phase 37.1 Plan 15: Finished-request block rule Summary

**select_schedule_block() now reads whether the request is finished (TOM's terminal observing states), so the tick or sweep at which a request finishes stores the block that took data instead of a leftover PENDING block, proved through the real status refresh, the discovery sweep (live and embedded) and the observed-telescope lookup.**

## Accomplishments

- The rule: `is_request_finished(state, facility)` returns `state in facility.get_terminal_observing_states()`; `select_schedule_block(blocks, *, request_finished=False)` returns the first COMPLETED block in both modes. For a request that can still run it is 37.1-14's order unchanged (last PENDING, else last started). For a finished request the started tier (ABORTED, IN_PROGRESS, FAILED-with-data) comes before the leftover PENDING block (developer decision 2026-10-05, review WR-20).
- All three production callers pass the request state: `ScheduleBlockRuleMixin.get_observation_status()` (state from its first GET; covers the status refresh, the sweep's live lookup and the Didymos command), `_resolve_schedule()`'s embedded branch (the listing's own request state) and `resolve_observed_site()` (the stored record's status, through `resolve_placement_block(..., request_finished=)`). An AST probe confirms the set of callers is exactly these.
- IN-30: the module docstring's first paragraph no longer equates a stopped-early block with a COMPLETED one unconditionally; the tiers paragraph states both orders and A-33. IN-29: notebook cell `b9d3e7a1` now shows a pending block against each kind of started block in both orders (six sample lists).
- Q4: the `_schedule_lookup_is_needed()` docstring, the runbook's per-tick-skip paragraph and the `backfill_lco_observations` Command docstring each say why the skip stays safe (the rule reads the request state, so the finishing tick stores the block that took data) and name the A-33 exception.
