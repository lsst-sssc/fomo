# Phase 37.1 Plan 11: Non-list block-list reply is a failed lookup; failed recheck lookups are retried Summary

**A portal block-list reply that is not a list now raises `UnexpectedBlockPayloadError` on FOMO's facility, so no sweep or status refresh can read it as "no block" and erase a time; a failed `--recheck-unscheduled` lookup marks the record so the unattended runner finishes it; the runbook and demo notebook say and show both.**

## Accomplishments

- **WR-01 fixed (developer's 2026-10-05 choice, answering 37.1-VERIFICATION.md human item 5).** `ScheduleBlockRuleMixin.get_observation_status()` assigns the second reply to `blocks` and, when it is not a list, raises `UnexpectedBlockPayloadError` (a `ValueError` subclass) naming only the request id and the body's Python type. An empty list still means "no block". `select_schedule_block()` is unchanged, so `calendar_utils.resolve_placement_block()` still never raises. Every caller already catches a raise: the sweep holds the status back and keeps the times, TOM's `update_observation_status()` writes nothing, `update_all_observation_statuses()` returns the record as failed, the unattended status refresh reports `LCO: failed N | ... | classes: UnexpectedBlockPayloadError`, and the Didymos command counts it under `status sync failed` (its file is byte-identical).
- **WR-02 fixed.** `_failed_lookup_needs_marker()` plus a `mark_lookup_failed` keyword on `_changed_record_fields()`, passed at both comparison sites in `sweep_proposal()`: a lookup that failed on a record the ordinary gate would skip (an unmarked failed-state record with no times at the same portal state, reached only under `--recheck-unscheduled`) writes `schedule_lookup_failed: True` in the same save. A dry run never marks, and a record the ordinary tick already retries (completed record missing a time, state change, non-terminal, already marked) is not given a new mark.
- **IN-04, IN-02, IN-05.** Sweep-level tests pin marked-record repeat failure, parameter drift on a marked record and on a placed record, and a successful no-block lookup clearing the mark; all seven `sweep_proposal()` writes end with a newline so the runner logs one record per failed id; the gate docstring premise now reads "no FOMO path that updates an existing record stores a state change without its block", its ragged wrap is gone, and the constant comment, `_resolve_schedule()`, `_changed_record_fields()`, `sweep_proposal()`, `Command` docstring and `--recheck-unscheduled` help all say a failed recheck lookup marks the record and the runner retries it.
- **Paired docs (CLAUDE.md rule).** Runbook: the "Re-running updates in place" bullet is qualified and points at **Scheduled times**; "Scheduled times" names a non-list reply as a failed lookup and says "Every later real run ... until a lookup (or an embedded block) resolves it"; the recheck paragraph says a failed recheck is marked and retried; the status_refresh step and the "A status_refresh failure names an HTTP status code" entry explain `UnexpectedBlockPayloadError`; the finished-record paragraph's two over-long lines are re-wrapped. Notebook: two new executed sections (records 900605-900607) and cell 0 now says "clears the new request's mark".
