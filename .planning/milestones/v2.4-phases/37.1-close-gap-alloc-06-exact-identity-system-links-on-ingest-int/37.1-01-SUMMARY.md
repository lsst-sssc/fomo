# Phase 37.1 Plan 01: Exact-identity system links on the discovery sweep Summary

**The discovery sweep now links every record that exactly matches one approved run by proposal code, target (or campaign-unique proposal) and window as a `confirmed_by=None` system link, retiring its allocation night on the same sweep through the existing post_save receiver.**

## Performance

- **Duration:** about 45 min
- **Completed:** 2026-10-02
- **Tasks:** 3 (1 tracer, 2 TDD)
- **Files:** 2 created, 5 modified

## Accomplishments

- `solsys_code/campaign_system_links.py`: `find_exact_run()` (pure read, accepts an unsaved record) and `attempt_system_link()` (the single ingest entry point, never raises, writes only exception class names), with `BASIS_*` and `OUTCOME_*` constants. It reuses `campaign_attribution._record_window()` and never consults the similarity scorer.
- `campaign_utils.create_system_link()`: one `get_or_create` inside its own savepoint; `write_and_reconcile_campaign_run(observation_record=...)` now goes through it, so the module holds exactly one `CampaignRunObservation.objects.get_or_create`.
- `sweep_proposal()` offers every touched record (created, updated, unchanged) to the matcher in the real branch, and previews in the dry-run branch with no write path reachable. The summary gains `system links: N, links skipped: M` / `would link: N, links skipped: M` at the end; every existing prefix is byte-identical.
- 35 new matcher/writer/entry-point unit tests, 8 new sweep integration tests, 1 unattended-runner test; the existing exact-summary tests pass through the extended `_expected_summary()`.
