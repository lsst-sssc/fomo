# Phase 37.1: Close gap: ALLOC-06 — exact-identity system links on ingest - Context

**Gathered:** 2026-10-02
**Status:** Ready for planning

<domain>
## Phase Boundary

A newly ingested observation record that matches exactly ONE approved `CampaignRun` by
proposal code, target (or, as a fallback, campaign membership when that proposal code belongs
to exactly one run in the campaign the record's target is a member of) and window is linked to
that run automatically as a **system link** — a `CampaignRunObservation` row with
`confirmed_by=None`, `confirmed_at=now()` — by the two ingest paths that create records:

- `solsys_code/management/commands/backfill_lco_observations.py` `sweep_proposal()` (the
  LCO/SOAR discovery sweep; also what the unattended runner's `step_discovery` calls through
  `sweep_watched_rows()`), and
- `solsys_code/management/commands/backfill_lco_observation_records.py` (the Didymos field
  backfill).

The link, once written, drives everything else through contracts that already exist: the 35
D-11 `post_save` receiver on `CampaignRunObservation` re-projects the run so its allocation
night retires (ALLOC-03), and 35 D-08 `_sync_observation_attribution()` adopts the record's own
projected event into the run. Anything partial or ambiguous stays in the attribution queue for a
person exactly as today. Staff undo a system link from the attribution page's Confirmed table
the same way as a staff-confirmed one. The campaign-list banner and the attribution page count a
record and its own projected calendar event as ONE orphan.

Out of scope (roadmap-locked): similarity-scored auto-attribution (the Phase 28 Out-of-Scope row
stands; `campaign_attribution.py`'s scorer weights are not touched); any link written by the
observation projector's `post_save` receiver or inside a view; any new writer of another layer's
calendar events; automatic `run_status` aggregation (TALLY-03).

</domain>

<decisions>
## Implementation Decisions

### Which records get linked, and when

- **D-01: Every unlinked record an ingest command touches is a link candidate — created,
  updated and unchanged alike.** `sweep_proposal()` re-reads every request of a watched proposal
  on every tick, so this covers the 19 record+event pairs already on the live DB (they link on
  the first tick after deploy) and the common case where staff create the run *after* discovery
  found the records (runs 69–75 were created 2026-10-01 for records discovered 2026-09-29).
  "Newly ingested" in ALLOC-06 is satisfied because the sweep is the ingest path; the rule is not
  restricted to the `created` branch. Idempotence (success criterion 6) comes from the
  `get_or_create(observation_record=...)` contract — a second pass finds the existing row and
  writes nothing, so `confirmed_at` never churns.
- **D-02: `backfill_lco_observation_records` also links existing unlinked records it
  re-encounters.** Today that command `continue`s on an already-existing record before doing
  anything else (`skipped_existing`); the link attempt must happen for those too, so re-running
  it over `LCO2026A-003` links the 10 live Didymos field-pointing pairs. Its `already existed`
  count stays; a system-links count is added.
- **D-03: The record's status is irrelevant to linking.** An expired, cancelled or failed
  request that exactly matches the run is still that run's attempt: the public tally counts it
  under `[X]`/`[F]` (37 D-11), and 35 D-05 already means a never-placed record retires no night.
  Identity and outcome stay separate.
- **D-04: Reporting — a count in the summary line plus one stdout line per link.** The sweep
  summary gains `system links: N` (dry run: `would link: N`), which flows unchanged into
  `WatchedProposal.last_run_summary` and the unattended `step discovery:` log line. Each link
  (or would-be link under `--dry-run`) also writes one stdout line naming record → run and the
  match basis (D-11), so a dry run shows exactly which pairs would link. `--dry-run` writes no
  link (T-kpy-01 discipline: reads only).

### What staff see, and what undo means

- **D-05: A system link renders as "System (exact match)" in the Confirmed table's existing
  "Confirmed by" column** (`campaign_tables.AttributionConfirmedTable.confirmed_by`, where
  `confirmed_by=None` is blank today). No new model field, no new column; the same rendering is
  used wherever else `confirmed_by` is shown for a link (e.g. the calendar pop-up's attributed-run
  block, if it names the confirmer). `confirmed_by=None` *is* the provenance — the contract
  `allocation_projector.py:958` and `campaign_utils.py:1050` already rely on.
- **D-06: Undo of a system link is the existing staff undo, unchanged.**
  `AttributionDecisionView._undo_confirmation()` deletes the `CampaignRunObservation` row and
  writes an `ObservationRecordDismissal` for the pair (28 D-13). That dismissal is exactly what
  stops the next discovery tick re-linking the pair (D-09), and the matcher already excludes
  dismissed runs, so the record may become a zero-candidate orphan — accepted. The 35 D-11
  `post_delete` receiver restores the allocation night (success criterion 4). The default undo
  reason text is reused.
- **D-07: The match basis ("proposal + target + window" vs "proposal unique within campaign +
  window") is named in the per-link log line only.** Nothing new is stored on the row.
- **D-08: A failed link write for one record is skipped and counted, never a step failure.**
  If the write raises (e.g. `IntegrityError` because staff linked the record to another run
  between the sweep's read and its write), the record keeps whatever state it has, a
  `links skipped: N` counter and a stderr line record it, and the discovery step is not marked
  failed — a lost race is not an operator-visible failure (Phase 36 D-01..D-03 per-step /
  per-proposal isolation). Each link write runs in its own `transaction.atomic()` savepoint, as
  `_do_confirm_record()` does, so a caught `IntegrityError` cannot poison the sweep's outer
  transaction or a test transaction.

### Counting a record and its event once

- **D-09: A record-backed calendar event is never an event-side orphan.**
  `campaign_attribution.orphan_calendar_events()` excludes any event whose
  `CalendarEventMeta` carries `observation_record` (set by the observation projector, Phase
  33/34). Its attribution is worked only through its record — confirming or system-linking the
  record attributes the event via 35 D-08. Consequences, all by construction: the "Calendar
  events awaiting attribution" worklist lists only hand-entered / legacy / reconciler events;
  `orphans_needing_attribution_count()` (the banner and the page sections) counts the pair once;
  `unattributable_orphan_count()` (the done-state "N orphans still have no matching run" copy)
  counts it once. The existing test
  `TestOrphanQuerysets.test_event_with_observation_record_but_no_run_is_still_included`
  (`solsys_code/tests/test_campaign_attribution.py:739`) asserts the old behaviour and must be
  inverted, not deleted. — **Reversibility:** reversible — one queryset filter and its tests.
- **D-10: Every count still comes from the shared helpers in `campaign_attribution.py`** —
  no inline `.count()` anywhere (success criterion 5; the silent-drift hazard
  `orphans_needing_attribution_count()`'s docstring names).

### Exact-match rules at the edges

- **D-11: The match rule, in order.** Let *P* be the record's proposal code
  (`ObservationRecord.parameters['proposal']`, the flat key both backfill commands write), *T*
  its `target_id`, and *(s, e)* its window from `calendar_utils.record_time_window()` reduced to
  UTC dates (the placed block once scheduled, else the request window — the same derivation
  `campaign_attribution._record_window()` uses). Candidates are `CampaignRun` rows with
  `approval_status=APPROVED`, `proposal_code == P`, both `window_start` and `window_end` set,
  and `window_start <= s` and `e <= window_end` (inclusive containment, D-12).
  1. If exactly one candidate has `target_id == T` → link it (the 10P case: runs 69/71/73 share
     proposal and campaign and differ only by target).
  2. Else, if no candidate carries *T* and exactly one candidate sits in a campaign
     (`TargetList`) that *T* belongs to → link it (the Didymos field-pointing case: run 1 is the
     only `LCO2026A-003` run in the campaign the sidereal field targets were added to).
  3. Anything else — zero candidates, two or more by target, two or more by campaign, a
     candidate set with no target match and no campaign match — stays in the queue, untouched.
  A pair with an `ObservationRecordDismissal` row is never linked (success criterion 3), and a
  record that already has any `CampaignRunObservation` row is never touched.
- **D-12: "Window inside the run's" = containment, compared as dates, inclusive.** Both the
  record window's start date and end date fall within `[window_start, window_end]`. A request
  window that straddles the run's edge is left for a person. Dates, not site-local nights, so
  the rule also works for class-wide runs (`site=None`) where no observing night can be derived.
- **D-13: A run with no window (a TBD row, `window_start`/`window_end` null) is never a
  system-link candidate and never counts toward ambiguity.** It stays a scorer candidate in the
  queue as today.
- **D-14: Only `approval_status=APPROVED` runs count — for linking and for ambiguity.** Pending
  and rejected runs neither link nor block a link. `run_status` is ignored: a cancelled or
  weathered approved run still receives an exactly-matching record (same reasoning as D-03).
- **D-15: Target match takes precedence over the campaign fallback** (the ordering in D-11).
  The fallback applies only when no containing same-proposal run carries the record's target —
  it must not be reached in the 10P case, and it must be reached in the Didymos case.

### Plan-phase amendments (2026-10-02, decided by the operator after research)

- **D-11 step 2 amended — uniqueness is judged across the campaign, before the window
  filter** (roadmap success criterion 2 wins over the earlier wording). Let the candidate set
  be ALL `approval_status=APPROVED` runs with `proposal_code == P` and both window fields set,
  that sit in a campaign (`TargetList`) the record's target belongs to. If no candidate anywhere
  carries *T* and that campaign-scoped set has exactly one run, link it only if that run's
  window contains the record's window (D-12); otherwise leave the record in the queue. A second
  same-proposal run in the campaign blocks the fallback even when its window does not contain
  the record's. The three live cases (10P by target, Didymos by campaign fallback, the ambiguous
  pair) come out the same under this rule.
- **D-06 addendum — undoing a dismissal is documented, not changed.** After staff undo a
  dismissal, an exactly matching record is re-linked by the next discovery tick; the undo
  dialog text ("It will return to the worklist above") and the runbook must say so.
- **D-04 correction (research finding, not a new decision):** the `system links: N` count
  reaches `WatchedProposal.last_run_summary`, and the per-link stdout lines reach the log as
  `discovery stdout:` lines; the `step discovery:` log line itself stays `swept: N, failed: M`.
  The runbook wording follows what the code actually emits.
