# Phase 37.1 Plan 10: Failed block lookup keeps the stored schedule Summary

**A raised live block lookup in the discovery sweep no longer erases stored times or commits the failed status: an existing record keeps its times, status and retired allocation night and is looked up again next tick, and a new request first seen during a failure is created marked `schedule_lookup_failed` and retried until a lookup succeeds.**

## Accomplishments

- Closed the failure path of G-37.1-1-alloc (37.1-REVIEW CR-01, the open `gaps:` entry of 37.1-VERIFICATION.md): on the unattended discovery path a failed lookup neither erases stored times nor disarms its own retry.
- Held-back status rule: `compare_schedule = (embedded or (lookup_needed and not dry_run)) and not lookup_failed`, and `_changed_record_fields(..., lookup_failed=True)` compares neither the two schedule fields nor `status`. Both the dry-run and the real update branch pass `lookup_failed=lookup_failed`, so the two modes keep one comparison. The held-back status means the next sweep sees a state change, looks the request up again, and stores the new status and the block's times in the same save. A successful lookup is the only thing that writes either.
- `schedule_lookup_failed` marker semantics: `SCHEDULE_LOOKUP_FAILED_KEY` is written only by the real create path, when the lookup failed. `_has_failed_lookup_marker()` makes the gate return True for a marked record (even finished, even with both times). `_changed_record_fields` carries the marker when the run resolved no schedule (dry run, skipped lookup, another failed lookup) and drops it when a schedule was resolved, because the freshly built parameters never contain it; so the marker is removed in the same save that writes the times. It is never added to an existing record, and a dry run never writes or removes it.
- Gate docstring, `_changed_record_fields` docstring, `_resolve_schedule` docstring and the Command docstring now describe the rule; the false "it already holds whatever block the request had" claim is gone, replaced by why no FOMO path stores a state change without its block.
- Runbook discovery section corrected ("never erases", "held back", `schedule_lookup_failed`, the per-tick skip safety text, the Didymos `status sync failed` recovery via `--recheck-unscheduled`, and marked records in the still-looked-up list).
- Paired notebook gained a section (records 900603/900604, request group 900610) with freshly executed output.
