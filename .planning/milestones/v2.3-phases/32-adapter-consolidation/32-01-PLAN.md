<objective>
Build everything the three adapter cutovers stand on, and prove it end to end before any
adapter consumes it: the schema shape Phase 31 specified but never built (nullable
`campaign`, `source_identifier` plus its partial unique constraint, and the `SOAR_QUEUE`
source value), null guards at the five sites that dereference `run.campaign.name`, one
shared `write_and_reconcile_campaign_run()` helper that creates-or-updates a `CampaignRun`
and hands calendar projection to the existing `reconcile_run()`, and a genuinely new
reconciler capability: a queue-sourced run whose adapter recorded exactly one exact-identity
`CampaignRunObservation` link projects its calendar entry using that linked
`ObservationRecord`'s own `scheduled_start`/`scheduled_end`, narrowing automatically — with
no staff or adapter action — from the run's whole request window to its scheduled block and
then its observed block, as those two fields become known.

Purpose: nothing downstream can write a non-campaign `CampaignRun` until the migration
lands, and the first null-campaign row to reach `reconcile_run()` crashes on
`campaign_reconciler.event_title()` unless the guards land first. The precision capability
closes a real, working feature (`sync_lco_observation_calendar`'s own minute-precise
calendar block, computed by `calendar_utils.record_time_window()`) that ADAPT-02/03's
cutover would otherwise remove with no replacement — the calendar-fidelity regression a
2026-09-03 checkpoint surfaced and the user rejected shipping as-is. This plan is the
phase's groundwork (ROADMAP scope note), its cutover-safety machinery (ADAPT-05), and the
reconciler-side half of ADAPT-02/03's "no regression" bar, all proven before plan 32-03's
adapter cutover consumes any of it.

Output: two migrations, a public shared helper plus an adoption bridge in
`campaign_utils.py`, five guarded read sites, a container-branch adopt step and a new
precision-narrowing read path in the reconciler, two new test modules, and a regenerated
reconciler demo notebook.

**Signal detected:** "second facility with real read-back" (SOAR joining LCO as a facility
whose portal actually reports scheduled/observed times) fired this phase's assumption-delta
architecture checkpoint. The question it forces: is `reconcile_run()`'s two-condition
dispatch rule (`telescope_class` non-blank OR resolved satellite `site` -> container branch;
everything else -> per-night branch) still the right model now that a third case exists — a
site-resolved, url-keyed queue run that wants the container branch's continuous,
current-state-re-derived narrowing, not the per-night branch's freeze-after-create fields?

**Recorded: add-alongside.** The dispatch model gains a genuinely new third condition —
`run.observation_links.count() == 1` — checked after the existing `telescope_class` and
satellite-`site` conditions and before the per-night fallback. The two existing conditions
are unchanged in meaning and unchanged in which runs they match; the new condition only
ever fires for a run neither of them already claims. This is "add-alongside" rather than
"promote" because no existing field's *priority* changes — `telescope_class` still wins
outright when set, satellite `site` still wins next — and rather than "no-change" because a
SOAR run's calendar shape genuinely differs after this plan (one narrowing event instead of
N per-night events). Rationale: 31-DECISION.md's SOAR/Gemini site-resolution design and
`campaign_reconciler.py`'s own module docstring already treat "no fixed observing site" as
the single question the dispatch answers; a queue run with an exact-identity single
observation link is not asking that question at all — it already has one concrete, narrowing
observation to render, the same shape a class-wide LCO allocation already gets. Confirmed by
the checkpoint task below before Task 3 implements it (REVERSIBILITY_GATES: this changes
already-tested reconciler branch selection, 45 existing tests in
`test_campaign_reconciler.py`, so it is gated rather than decided silently).

## Flagged assumptions

- The classical `source_identifier` form uses the observing-night date
  (`CLASSICAL:{telescope}:{instrument}:{night.isoformat()}`), not 31-DECISION.md's
  originally-proposed 5-minute bucket of `start_time` — confirmed by the user (2026-09-03
  addendum, Decision 2) because the bucketed form is not drift-free against
  `load_telescope_runs`'s ~2s IERS-refresh jitter. Implemented by plan 32-02.
- Queue-sourced calendar events (LCO and SOAR) do **not** lose time-span fidelity at
  cutover: Task 3's `_linked_observation_window()` plus the new dispatch condition make a
  single-observation queue run's event track its linked `ObservationRecord`'s own
  `scheduled_start`/`scheduled_end`, narrowing from the whole request window to the placed
  block to the observed block automatically, on every sync. Title-prefix vocabulary
  (`[QUEUED]`/`[EXPIRED]`/`[FAILED]`/`[UNVERIFIED]`) still collapses into the reconciler's
  two-value vocabulary (`[CANCELLED]`/`[WEATHERED]`) — that narrowing is unaffected by this
  fix and Phase 35 is still where the richer status vocabulary returns.
- SOAR and Gemini runs need a resolved `Observatory` to be projectable at all (pass
  `_skip_reason()`'s `'unresolved site'` gate), because no `CampaignRun.TelescopeClass`
  value exists for a 4m or 8m aperture and D-12 forbids adding one. Confirmed obscodes,
  independently re-verified against the live `Observatory` table this session: `I33`
  (SOAR, Cerro Pachón — no row yet, self-healing) and `I11` (Gemini South — row already

  Gemini-North-specific one.** Implemented by plans 32-03 (SOAR) and 32-04 (Gemini); a
  missing row degrades to a reported, self-healing not-projected count, never a silent
  drop. A resolved SOAR site with exactly one linked observation now takes the container

  `<assumption_delta_decision>` block above.
- `confirmed_at=timezone.now()` (rather than `None`) on an adapter-created
  `CampaignRunObservation` — RESEARCH.md Assumption A2. Chosen because a link that is
