which schema shape a non-campaign `CampaignRun` takes (SCHEMA-01), and what write-time identity
field and uniqueness constraint carry it (SCHEMA-02).

32 adapter targets, and changing it after adapters ship means re-migrating all three adapters'
writes. This plan therefore opens with a human decision gate rather than an autonomous pick.

each stating a single decision plus the evidence behind it.

<assumption_delta_decision>
The assumption-delta detector fired on this phase with a `chosen` signal ("the doc states the
unattended-invocation mechanism **chosen** against the real target host's constraints"), and the
schema track is itself a singular-to-plural identity question: `CampaignRun.campaign` has been a
required, always-present FK, and this phase asks whether it keeps that monopoly.

- **Noun now primary:** the write-time run identity of a `CampaignRun` - the value an ingest path
  keys on to find or create its row. Until now that identity was implicitly "the campaign plus the
  telescope/instrument plus the window". This phase asks whether the campaign is still part of it.
- **Decision for Phase 31:** `no-change`. This is an investigation-only phase (CONTEXT.md "Phase
  Boundary"): no migration is applied and no adapter code is written, so there is no promotion to
  perform here.
- **Recorded for Phase 32:** the promote-versus-add-alongside guidance belongs to the phase that
  actually writes the adapters. Task 3 records it in `31-DECISION.md` as informational guidance:
  if the recommended shape makes a new identity field the general representation, Phase 32 should
  **promote** it to the primary lookup key and demote the campaign-plus-window tuple to a detail of
  the campaign-submission variant, rather than adding the new key alongside a still-required old
  one. Adding alongside is accepted debt only if named as such, with the condition that would force
  a later promote stated.
- **Suggested (not required) for Phase 32:** an invariant test asserting that every
  `CampaignRun` written by any ingest path is findable again through the primary identity key, for
  every supported `CampaignRun.Source` value. That test goes red the moment a later phase
  reintroduces the campaign-is-always-present assumption. This is a suggestion recorded in the
  decision doc, not a task in this phase, which writes no source code.
</assumption_delta_decision>

<task type="checkpoint:decision" gate="blocking-human">
  <name>Task 1: Decide the schema shape for a non-campaign CampaignRun (one-way door, D-05)</name>
  <decision>Which schema shape gives a routine, non-campaign LCO/Gemini queue observation a persistent `CampaignRun` identity</decision>
  <context>
    D-05 records no lean between three candidates and rates this choice **one-way**: whichever shape
    wins becomes the write-time identity surface every Phase 32 adapter targets, and changing it
    after those adapters ship means a re-migration across all three adapters' writes. Plan 31-01
    has already put all three against the real dev-DB population and both existing partial
    `UniqueConstraint`s; the evidence is in `31-DECISION.md` under `#### SCHEMA-01 evidence - real
    dev-DB snapshot`, `#### SCHEMA-01 evidence - campaign FK read-path blast radius` and
    `#### SCHEMA-02 evidence - candidate-shape constraint probe`. Read those three sections before
    choosing; the pros and cons below are the shapes' inherent trade-offs, and the measured numbers
    that decide between them are in the document.
  </context>
  <options>
    <option id="nullable-fk">
      <name>Option A - make `CampaignRun.campaign` nullable</name>
      <pros>Cheapest migration: a single `AlterField`, with no data backfill needed if the measured null-campaign count is zero. No placeholder rows accumulate. The absence of a campaign is represented by the absence of a value, which is what it actually means.</pros>
      <cons>Widest read-path blast radius: every site in plan 31-01's inventory that reads the related object must be audited, starting with `CampaignRun.__str__`. Both existing partial constraints key on `campaign`, and a NULL is never equal to a NULL in a unique index, so those constraints may silently stop discriminating for exactly the rows this phase is trying to give identity to - block (B) of the constraint probe measured this.</cons>
    </option>
    <option id="single-sentinel">
      <name>Option B - one shared sentinel campaign row</name>
      <pros>No schema change to the FK at all; it stays required. Every existing read path keeps working untouched, so the blast radius is zero. One row to create, found or created by exact name.</pros>
      <cons>Collapses every non-campaign run at every facility onto one campaign value, which is the discriminator both existing constraints rely on. Two genuinely distinct non-campaign runs at the same telescope and instrument with the same window would collide - block (C) of the constraint probe measured whether that happens in practice. Also makes "no campaign" look like a campaign to every campaign-listing surface.</cons>
    </option>
    <option id="per-proposal-placeholder">
      <name>Option C - one auto-created placeholder campaign per proposal</name>
      <pros>Splits Option B's collision risk by proposal, so two proposals' runs cannot collide with each other. Keeps the FK required, so no read path changes. Gives each queue proposal a natural grouping surface for free.</pros>
      <cons>Grows one placeholder row per proposal identifier ever seen. Raises a design question the other two do not have: what happens to a placeholder's existing runs when that proposal later acquires a real coordinated campaign - are they re-pointed, or does the placeholder persist alongside the real campaign forever? Block (D) of the constraint probe measured the collision behaviour but cannot answer that question.</cons>
    </option>
  </options>
  <resume-signal>Select: nullable-fk, single-sentinel, or per-proposal-placeholder</resume-signal>
</task>
