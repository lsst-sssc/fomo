  <action>
Create `solsys_code/management/commands/reconcile_campaign_runs.py` as a `BaseCommand` subclass.

Class docstring: this is the single idempotent sweep that projects and refreshes calendar events for
every `CampaignRun` (RECON-01), replacing the retired `backfill_range_calendar_events` and the
per-gap backfill pattern generally (RECON-09). Note that all projection math lives in
`solsys_code.campaign_reconciler` and this command only loops it — and that unlike the retired
command, which imported the private `_project_calendar_event` out of the views module, this one
imports a public function from a dedicated pure module.

`help` text: one sentence describing the sweep plus the `--dry-run` behaviour.

`add_arguments()` adds `--dry-run` with `action='store_true'` and help text
'Report what would be reconciled without writing any CalendarEvent rows.' — copy the shape from the
retired command verbatim.

`handle()`:
- Iterate `CampaignRun.objects.all().select_related('site', 'campaign').order_by('pk')`. Deliberately
  unfiltered: RECON-01 says "every run, regardless of window length, source, or site-resolution
  state", and `reconcile_run()`'s own `_skip_reason()` guard (including its `'not approved'` gate) is
  the single place that decides what does not project — the command must never grow a second,
  divergent copy of that rule.
- For each run call `reconcile_run(run, dry_run=dry_run)` inside a `try/except Exception` — this is
  the **only** catch point (D-06: no per-run `transaction.atomic()`, no try/except inside
  `reconcile_run()`). On an exception, `logger.debug` the run pk and exception, write
  `f'Run pk={run.pk}: reconcile failed ({exc}) -- skipping'` to `self.stderr`, increment the failed
  counter and `continue`. A mid-run failure leaves that run's already-written nights in place —
  accepted partial projection, matching Phase 25's precedent, safe because a re-run is idempotent.
- When the returned `ReconcileResult` carries a `skipped_reason`, write
  `f'Run pk={run.pk}: skipped ({result.skipped_reason})'` to `self.stderr` and increment the skipped
  counter — this is D-05's "itemized, not a bare count", satisfied through the existing
  stderr-per-row convention rather than an in-memory structured list.
- Otherwise accumulate `result.created`, `result.updated`, `result.unchanged` and `result.blocked`
  into plain int locals. Write a `self.stderr` line for any run with a non-zero `blocked` count
  naming the run pk, since a blocked write means an event in this run's key namespace is owned by
  someone else and needs a human look.
- Final summary via a single `self.stdout.write(...)` f-string, mirroring `import_campaign_csv`'s
  shape exactly (plain int counters, no dict or dataclass wrapper): non-dry-run reports
  `Done. runs: N, created: C, updated: U, unchanged: X, skipped: S, failed: F, blocked: B`; the
  `--dry-run` branch reports `Done (dry run). runs: N, would_create: C, would_update: U,
  would_leave_unchanged: X, skipped: S, failed: F, blocked: B` with no writes issued anywhere in
  that branch — the counter-substitution pattern the retired command already used.
- Return None.

Do not add a per-stage (0-4) breakdown line: CONTEXT.md leaves it to discretion and it is declined
here to keep the summary byte-shaped like its two precedents.
Do not add `--campaign`/`--run` filters: no requirement asks for them and CONTEXT.md's
no-scope-creep posture rules them out.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator shell -> management command | The only input is the boolean `--dry-run` flag; no user-supplied identifier reaches the ORM |
| batch loop -> per-run failures | One run's failure must not silently consume the rest of the sweep |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-08 | Repudiation | Mid-batch failure leaving some runs reconciled and some not, with no record of which | mitigate | D-05/D-06: every failure and every skip writes a `self.stderr` line naming the run pk and reason, and the summary reports `skipped`/`failed` counters; `TestFailureIsolation` asserts both |
| T-29-09 | Tampering | A `--dry-run` invocation that nonetheless writes | mitigate | The dry-run branch issues no write call at all; `TestDryRun` asserts `CalendarEvent` and `CalendarEventMeta` counts both stay 0 |
| T-29-10 | Elevation of Privilege (business logic) | Command projecting a PENDING_REVIEW or REJECTED web submission onto the public calendar | mitigate | The command does not filter runs itself; `reconcile_run()`'s `_skip_reason()` `'not approved'` gate is the single decision point, so the command and the staff actions can never diverge |
| T-29-11 | Denial of Service | Unbounded sweep over a large `CampaignRun` table | accept | The real table is tens of rows; `select_related('site', 'campaign')` avoids the N+1 that would dominate cost, and the command is operator-invoked, not request-triggered |
| T-29-SC | Tampering | npm/pip/cargo installs | accept | No packages installed in this phase; no legitimacy audit applies |
</threat_model>
