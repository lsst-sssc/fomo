<objective>
Build the write path: the staff-only routes and the POST endpoint that confirms a candidate,
dismisses one with a reason, undoes a confirmation, and undoes a dismissal -- for both orphan
kinds -- each re-validated server-side against the matcher rather than trusted from the form.

Purpose: ROADMAP criterion 3 ("no association without an explicit per-candidate staff
confirmation, and no suggestion across a campaign/target boundary") and criterion 4 ("undone from
the same screen that created it, and both attributable to a person and a time") are decided here,
not in the template. The template in 28-04 renders what this plan makes safe.

Output: `AttributionQueueView` (GET context assembly, its template arrives in 28-04),
`AttributionDecisionView` (POST, five actions), two URL routes, the campaign-list banner count,
and the POST/race/gating half of `test_campaign_attribution_views.py`.
</objective>

Add `AttributionDecisionView(StaffRequiredMixin, View)` to `solsys_code/campaign_views.py`, with
`http_method_names = ['post']` so a GET (crawler prefetch, bare anchor) can never trigger a state
change. `StaffRequiredMixin` must be declared explicitly on this class -- it is not inherited.

POST parameters: `action` (one of `confirm`, `confirm_selected`, `dismiss`,
`undo_confirmation`, `undo_dismissal`), `kind` (`event` or `record`), `orphan_pk`, `run_pk`,
`reason` (dismiss only), and `candidate_ids` (bulk only, multi-valued, each value the string
`"{kind}:{orphan_pk}:{run_pk}"`). Any `action` or `kind` outside its literal allow-list returns
`HttpResponseBadRequest()`, keyed on the literal tuple and never derived from request text.
Non-integer `orphan_pk`/`run_pk` also return `HttpResponseBadRequest()`. Every branch finishes
with `redirect('campaigns:attribution')`, preserving the `band` GET parameter if one was
submitted as a hidden field so the staff member returns to the filter they were working in.

**Server-side re-validation, on every action that creates an association.** Before writing,
call `campaign_attribution.is_offered_candidate(kind, orphan_pk, run_pk)` and abort with
`messages.warning(request, 'This candidate was already confirmed or dismissed by someone else.')`
when it returns None. Never trust that a button or checkbox was only rendered for an eligible
row -- this is the guard that stops a tampered POST creating an association across a
campaign/target boundary, which ROADMAP criterion 3 forbids absolutely. Write a comment stating
that in the same voice as `CampaignRunDecisionView._resolve_site()`'s existing business-logic
bypass guard.

**confirm, event side.** First `CalendarEventMeta.objects.get_or_create(event_id=orphan_pk,
defaults={'is_verified': True})` -- a classical event has no companion row at all, and creating
an unowned one with the documented default changes nothing observable. Then the atomic
conditional update, generalising `CampaignRunDecisionView`'s idiom by keying on the "unclaimed"
precondition instead of a status enum:
`CalendarEventMeta.objects.filter(event_id=orphan_pk, run__isnull=True).update(run_id=run_pk,
confirmed_by=request.user, confirmed_at=timezone.now())`. Reuse the same three-way branch: one
row updated is success; zero rows updated with the meta row still present is
`messages.warning(...'already confirmed or dismissed by someone else.')`; the orphan or run gone
is `messages.error(request, 'This candidate no longer exists.')`. Success copy:
`messages.success(request, 'Attribution confirmed.')`.

**confirm, record side.** Structurally different -- a row is CREATED, not a field set (Phase 27
D-01). Use `CampaignRunObservation.objects.get_or_create(observation_record_id=orphan_pk,
defaults={'run_id': run_pk, 'confirmed_by': request.user, 'confirmed_at': timezone.now()})`
inside its own `transaction.atomic()` savepoint, catching `IntegrityError` and surfacing the same
warning copy. The savepoint is required for the reason
`CampaignRunSubmissionView.form_valid()`'s comment gives: without it the caught error poisons the
outer request/test transaction. Note in a comment that the guarding constraint
`unique_campaign_run_observation_record` is on `observation_record` ALONE -- one run per record
globally -- so the race this catches is two staff confirming the same record against two
DIFFERENT runs, not two confirmations of the same pair (RESEARCH.md Pitfall 3).

**confirm_selected (bulk, D-09).** Parse each `candidate_ids` value, discarding malformed ones
silently. For each parsed triple, re-derive with `is_offered_candidate()` AND require both
that the candidate's band is `BAND_HIGH` and that it is its orphan's `sole_high_candidate_pk`.
Reject anything else -- the checkbox gate is enforced here, on the server, not by the fact that
the template only rendered checkboxes on eligible rows (ASVS V5). Loop the per-pair single
confirm inside one `transaction.atomic()` block; do NOT issue a single combined
`.filter(pk__in=...).update(run=X)`, which can only set one run for every matched row while each
checked pair may name a different run (RESEARCH.md Anti-Pattern). Sum the successes and report
`messages.success(request, f'{n} candidates confirmed.')`, adding
`messages.warning(request, 'This candidate was already confirmed or dismissed by someone else.')`
when at least one submitted pair failed re-validation. Bind nothing from POST onto a model
instance beyond the three integers and the parsed kind -- there is no form and no
`**request.POST` expansion anywhere in this view.

**dismiss (D-05/D-06).** Require a non-empty stripped `reason`; a blank one aborts with
`messages.error` and no write, so the browser's `required` attribute is a convenience rather
than the control. Then `get_or_create` on the matching dismissal model keyed on the (orphan, run)
pair with `defaults={'dismissed_by': request.user, 'dismissed_at': timezone.now(), 'reason':
reason}`, inside a `transaction.atomic()` savepoint catching `IntegrityError` from the named pair
constraint. Success copy: `messages.success(request, 'Candidate dismissed.')`. Store the reason
raw -- never `mark_safe`, never string-concatenated into markup.

**undo_confirmation (D-13).** Inside one `transaction.atomic()` block: first create the dismissal
row for the pair being un-confirmed (same `get_or_create` as dismiss, with a reason recording
that it was an undo -- use the literal `'Undone by staff.'` when no reason is supplied), then
clear the link. Event side:
`CalendarEventMeta.objects.filter(event_id=orphan_pk, run_id=run_pk).update(run=None,
confirmed_by=None, confirmed_at=None)` -- still conditional on the currently-owning run so a
concurrent re-point cannot be silently clobbered. Record side:
`CampaignRunObservation.objects.filter(observation_record_id=orphan_pk, run_id=run_pk).delete()`.
Write a comment recording why the dismissal row is written rather than a soft-undo flag: clearing
the link erases the very fields recording who confirmed it, so the trace has to live elsewhere,
and a soft-undo flag would break Phase 27 D-01's invariant that a link row's existence means
"confirmed". It also stops the matcher immediately re-suggesting the pair just undone. Success
copy: `messages.success(request, 'Confirmation undone — back in the queue.')`.

**undo_dismissal (D-07).** Delete the matching dismissal row, returning the pair to the queue.
Success copy: `messages.success(request, 'Dismissal undone — back in the queue.')`. A missing row
is `messages.error(request, 'This candidate no longer exists.')`.

All message strings must match UI-SPEC's Copywriting Contract exactly, including the em dashes in
the two undo strings -- they are the contract 28-04's tests assert against.
