# Phase 28 — UI Design Contract

> Visual and interaction contract for the staff attribution worklist. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker. This is a server-rendered Django/Bootstrap 4
> page — there is no component library build step and no new frontend dependency is permitted
> (milestone-locked constraint, ROADMAP.md "Locked constraints"). Every token below is expressed
> as a Bootstrap 4 utility class or an existing project convention, not a new CSS system.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — no shadcn, no component-library build step (Django/TOM Toolkit server-rendered app) |
| Preset | not applicable |
| Component library | Bootstrap 4 (`bootstrap4` app) + django-crispy-forms/crispy-bootstrap4 + django-tables2 + django-htmx (already used for the site-search live-suggestion pattern) |
| Icon library | Font Awesome 4 (`<i class="fa fa-...">`, e.g. `fa-exclamation-circle`, `fa-clock-o` — precedent in `campaign_list.html`, `campaignrun_gap_analysis.html`) |
| Font | Bootstrap 4 default system font stack — no custom `font-family`/`@font-face` exists anywhere under `src/templates` or project CSS; do not introduce one |

No new dependency, no CSS framework swap, no design-token JS file. This spec exists to pin down
*which* Bootstrap 4 utilities and *which* existing template conventions this phase's markup uses,
so four staff-only sections (two worklists + Dismissed + Confirmed) read consistently with
`approval_queue.html` rather than inventing a parallel visual language.

## Spacing Scale

Bootstrap 4's spacer utilities already are the project's 8-point scale (`$spacer: 1rem = 16px`,
multiplied by `.25/.5/1/1.5/3`). Use the existing utility classes, not raw CSS:

| Token | Value | Bootstrap utility | Usage |
|-------|-------|--------------------|-------|
| xs | 4px | (none used at this size in precedent templates) | not used on this page |
| sm | 8px | `mb-2`, `mr-2`, `p-2` | Icon-to-text gaps, evidence-chip internal padding, badge-to-number gaps within a row |
| md | 16px | `mb-3`, `p-3`, `mt-4`→partially | Card body padding (`card-body`), form-group spacing, gap between evidence columns in a candidate row |
| lg | 24px | `mb-4`, `mt-4` | Space between the four page sections (worklist / worklist / Dismissed / Confirmed), space below the page `<h4>` title (matches `approval_queue.html`'s `mb-4` on its `<h4>`) |
| xl | 32px | (compose `mb-4` + `mt-4` between adjacent cards) | Not used as a single utility; achieved by stacking `lg` margins between sections |
| 2xl | 48px | not used | No section on this page needs a break this large |
| 3xl | 64px | not used | No section on this page needs a break this large |

Exceptions: none. This is a staff desktop worklist, not a touch surface — no 44px touch-target
minimum applies. Checkbox controls (D-09) use Bootstrap's default `form-check-input` size
unmodified.

## Typography

Match the existing heading hierarchy exactly (`approval_queue.html`, `campaign_list.html`,
`campaignrun_table.html` all use this pair of weights and this `<h4>`/`<h5>` split — do not
introduce a third weight or a fifth size).

| Role | Size | Weight | Line Height | Bootstrap class |
|------|------|--------|-------------|------------------|
| Body | 16px | 400 (regular) | 1.5 | default `<p>`/`<td>` — Bootstrap `$font-size-base` |
| Label | 14px | 700 (bold) | 1.5 | `.small.font-weight-bold` — column headers, evidence-chip labels ("Telescope:", "Date overlap:"), filter-form labels (matches `campaignrun_table.html`'s `<label class="font-weight-bold">`) |
| Heading | 20px | 700 (bold) | 1.2 | `<h5 class="font-weight-bold">` — the four section titles: "Calendar events awaiting attribution", "Observation records awaiting attribution", "Dismissed", "Confirmed" (matches `approval_queue.html`'s `<h5 class="font-weight-bold mb-3">`) |
| Display | 24px | 700 (bold) | 1.2 | `<h4 class="font-weight-bold mb-4">` — the page title, "Attribution" (matches `approval_queue.html`'s page-title pattern exactly) |

Exactly 2 weights (400, 700) and 4 sizes, all already present in the codebase — nothing new.

## Color

The project has no custom color token file; every color below is a Bootstrap 4 contextual class
already load-bearing elsewhere in `solsys_code/campaign_tables.py` and the `campaigns/` templates.
Reuse the exact same class-to-meaning mapping already established there — do not invent a new
mapping for this page.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` (Bootstrap body background) | Page background, table row background |
| Secondary (30%) | `#f8f9fa` (`.bg-light`) / `#e9ecef` (table striping, `.table-striped`) | Card bodies (filter card, Dismissed/Confirmed collapsed-section containers), table zebra striping, the "gate" background behind non-checkboxable candidate rows (see Confidence Band Contract below) |
| Accent (10%) | `#007bff` (`.btn-primary`) | **Only** the "Confirm" button (single-candidate) and the "Confirm selected" bulk-submit button (D-09, high band only) — the page's sole constructive/positive-outcome actions, matching the existing precedent where `.btn-primary` means "Resolve" (site search) / "Submit a Run" (nav) elsewhere in `campaigns/` |
| Destructive | `#dc3545` (`.btn-danger`) | **Only** the "Dismiss" button, matching the existing Reject button in `ApprovalQueueTable.render_actions()` (`campaign_tables.py:407`) exactly |

Accent reserved for: the per-row "Confirm" button and the bulk "Confirm selected" button — nothing
else on this page uses `.btn-primary`. "Undo" (in the Dismissed and Confirmed sections) is
deliberately **not** accent and **not** destructive — it uses `.btn-outline-secondary`, matching
the existing "Mark Cancelled"/"Mark Weathered" precedent (`campaign_tables.py:375,377`): a
single-click state reversal that is not the page's primary action and is not literally destroying
data (D-13: it writes a dismissal row, it does not delete anything).

Confidence-band badges (D-10) are a separate, informational use of Bootstrap's contextual palette
— not part of the 60/30/10 split, since they classify data rather than surface area:

| Band | Badge class | Hex |
|------|-------------|-----|
| High | `.badge-success` | `#28a745` |
| Medium | `.badge-warning` (pair with `.text-dark`, matching `approval_queue.html`'s `bg-warning text-dark` card header) | `#ffc107` |
| Low | `.badge-secondary` | `#6c757d` |

The campaign-list count banner (D-02) reuses the **existing** `alert-warning`/`btn-warning`
treatment already in `campaign_list.html` (lines 20-28) rather than accent blue — it is the same
mechanism as the pending/site-review banner, so it must look identical, not merely similar. Extend
that banner's existing count clauses (or stack a second `alert-warning` block immediately beneath
it) rather than introducing a blue "info" banner.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (per-candidate) | "Confirm" (`.btn-success .btn-sm`, mirroring the existing "Approve" button's success-green semantics — a confirmed attribution is a positive determination) |
| Primary CTA (bulk, high band only) | "Confirm selected" (single submit button below the high-confidence candidates, disabled/hidden until at least one checkbox is checked) |
| Empty state heading (single worklist table drained) | "No {calendar events / observation records} awaiting attribution" |
| Empty state body (single worklist table drained) | "Every {calendar event / observation record} with a candidate run has been confirmed or dismissed." |
| Empty state heading (both worklists drained — the D-15 "Done" state) | "Attribution complete" |

The reconcile sweep in Phase 29 is safe to run." (`remaining_orphan_count` = orphans excluded by D-03's no-candidate rule; render 0 as "None" rather than "0 orphans", so the sentence reads cleanly at true completion) |
| Explanatory note (always visible, both worklist section headers) | "Only events and records with at least one candidate run are listed here — an orphan with no candidate never appears." (states D-03's consequence plainly, per context instruction) |
| Error state (race lost to the per-pair `UniqueConstraint`, D-08) | `messages.warning`, matching the existing tone exactly: "This candidate was already confirmed or dismissed by someone else." (mirrors `campaign_views.py:658`'s "This run was already decided by someone else.") |

| Destructive confirmation — Undo | Browser `confirm()` dialog, matching the "Mark Cancelled"/"Mark Weathered" precedent (`campaign_tables.py:375-377`) exactly in tone: `confirm('Undo this {confirmation/dismissal}? It will return to the {Confirmed/Dismissed} worklist.')` |
| Success feedback — Confirm | `messages.success`: "Attribution confirmed." (single) / "N candidates confirmed." (bulk) |
| Success feedback — Dismiss | `messages.success`: "Candidate dismissed." |

## Page Layout & Component Inventory

Extends `tom_common/base.html`, staff-only via `StaffRequiredMixin` (mirrors
`ApprovalQueueView`). Route lives in the `campaigns` namespace alongside
`campaigns:approval_queue` (naming left to planner per 28-CONTEXT "Claude's Discretion").

Page title: `<h4 class="font-weight-bold mb-4">Attribution</h4>` (Display token).

Four sections, top to bottom, each an `<h5>` (Heading token) immediately followed by its content,
spaced `mb-4`/`mt-4` between sections (lg token) — same rhythm as `approval_queue.html`:

1. **"Calendar events awaiting attribution"** — open by default, a `django_tables2` table where
   each row is one orphan `CalendarEvent` expanded to its candidate runs (see Candidate Grouping
   Contract below).
2. **"Observation records awaiting attribution"** — open by default, same shape, different
   evidence columns (facility, status, parameters instead of title/window).
3. **"Dismissed"** — collapsed by default (Bootstrap `collapse` component, a `<button
   data-toggle="collapse">` header, same interaction as any Bootstrap 4 accordion — no new JS).
   Read-only table plus one "Undo" button per row.
4. **"Confirmed"** — collapsed by default, same shape as Dismissed, "Undo" per row.

Do not use a `card border-warning` action-required treatment (the pattern
`approval_queue.html` uses for "Sites Needing Review") for the two worklist sections — that
styling means "requires escalation"; this page's worklists are routine triage, not an alert
condition. Reserve `border-warning`/`bg-warning` here only for the D-02 count banner on the
campaign list, matching its existing meaning.

### Evidence Column Contract (ROADMAP criterion 1 — "not a bare score")

Every candidate row shows, as separate labeled columns/cells (Label token, 14px bold, one line
each) — never collapsed into a single "score" cell:

| Evidence | Rendering |
|----------|-----------|
| Matched telescope | Plain text, e.g. "2m0 / Siding Spring E10" — the telescope/site string both the orphan and the candidate run resolve to |
| Date overlap | Plain text stating the actual overlap, e.g. "7–20 Jul overlaps run's 7–21 Jul window (1-day span difference)" — state the mismatch in words when there is one; do not hide it |
| Campaign | The campaign/target-list name the run belongs to (this is also the pre-filter per D-11, so it is never actually mismatched — shown for staff legibility, not as a differentiator) |
| Instrument-string similarity | Plain text showing both strings side by side, e.g. `"2M0-SCICAM-MUSCAT" vs "MuSCAT4"` plus the similarity used, not just a percentage |
| Numeric score (D-10) | A small `.badge-light .border` chip, e.g. "0.74", positioned after the evidence columns, visually subordinate to them (smaller, muted) — additional information, never a replacement for the evidence columns |
| Confidence band (D-10) | The colored badge from the Color section (`.badge-success`/`.badge-warning`/`.badge-secondary`), positioned first/leftmost in the row so band is the first thing a scanning eye hits |

### Confidence Band & Checkbox Gate Contract (D-09 — "make it obvious which rows are checkboxable and why")

- A checkbox (`form-check-input`) renders in the row's leading cell **only** for High-band
  candidates. Its cell is otherwise identical in width/alignment to the non-checkboxable rows'
  leading cell (do not let the checkbox change column alignment between bands).
- Non-High rows render **no empty checkbox placeholder** — render the confidence badge itself in
  that leading cell instead, so the presence/absence of a checkbox is never ambiguous with a
  disabled or unchecked one.
- High-band rows additionally get a `border-left border-success` (3-4px) on the row, so the
  checkboxable rows are visually grouped even when the table is scrolled and badge color alone
  might be missed (a second signal, not a replacement for the badge — do not rely on color alone
  per WCAG).
- The "Confirm selected" bulk button lives directly below the High-band candidates it applies to,
  not at the page or table bottom — it must be visually adjacent to the only rows it can act on.

### Candidate Grouping Contract ("alternatives, pick one" vs "independent items")

One orphan (one `CalendarEvent` or one `ObservationRecord`) may have several candidate runs. Group
candidates for the same orphan inside one bordered block within the table (a `<tbody>` per orphan,
or nested rows sharing a `rowspan` orphan-identity cell) so it reads as "pick one of these" rather
than a flat list of independent rows:

- The orphan's own identity (event title + window, or record facility + window) renders **once**,
  at the top of its group, in the Label weight (14px bold) — not repeated per candidate.
- Each candidate run inside the group renders as its own row with its own evidence columns, its
  own Confirm/checkbox, and a light `border-top` between candidates in the same group (not a full
  table row separator — visually lighter than the separator between two different orphans' groups).
- The separator between two different orphans is a full-width `mt-3` gap or an alternating
  zebra background switch (Secondary token, `#f8f9fa`) so group boundaries are unambiguous even
  when a group has only one candidate.
- Confirming any one candidate in a group is understood to resolve that orphan — the group
  disappears from the worklist and its other candidates (if any) are implicitly no longer offered
  (they were never independently dismissed; this is a consequence of D-01's "association writes
  the link", not a second dismissal action).

### Multi-Select Form Shape (D-09)

Following `ApprovalQueueTable.render_actions()`'s documented idiom but adapted, since D-09 needs
"one form spanning many rows" rather than "one form per row": wrap the High-band checkboxes in a
single `<form>` around the whole worklist table (not per-row `<form>` tags), with each checkbox
named `candidate_ids` (multi-value) and the single-candidate "Confirm" buttons using the same
`form=` HTML5 attribute pattern the Site column already uses to target an out-of-line form
(`campaign_tables.py` render_site's `form=` cross-reference) — so a per-row Confirm button can
coexist inside a table whose checkboxes belong to one page-spanning bulk form.
