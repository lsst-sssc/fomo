### WR-08: The CR-02 duplication regression test passes vacuously if the admin POST fails

**File:** `solsys_code/tests/test_admin.py:145-155`

**Issue:** `test_posting_a_different_event_pk_does_not_duplicate_the_row` is the *only* test proving
CR-02's fix, and it never inspects the POST response:

```python
self.client.post(
    reverse('admin:solsys_code_calendareventmeta_change', args=[self.original_event.pk]),
    {'event': str(self.other_event.pk), 'is_verified': 'on', '_continue': 'Save and continue editing'},

self.assertEqual(CalendarEventMeta.objects.count(), 1)
```

Every assertion that follows (`count() == 1`, `event_id` unchanged, no row for `other_event`) is
equally satisfied by a request that 403'd, 500'd, or re-rendered the change form with validation

was never reached". Its own sibling two methods up (`test_change_form_does_not_expose_event_as_editable`)
does assert `status_code == 200`, so the omission is inconsistent within the same class as well as
unsafe. A future change that breaks the change view outright would leave this test green.

**Fix:** assert the redirect and assert the save actually landed, so the test fails on a broken
write path:

```python
response = self.client.post(
    reverse('admin:solsys_code_calendareventmeta_change', args=[self.original_event.pk]),
    {'event': str(self.other_event.pk), 'is_verified': '', '_save': 'Save'},

self.assertEqual(response.status_code, 302)          # the save was processed, not re-rendered
self.assertEqual(CalendarEventMeta.objects.count(), 1)
```

### WR-10: The accepted "relabel to web" residual is irreversible through every FOMO write path, and neither documented as such nor tested

**File:** `solsys_code/admin.py:175-186`; `docs/runbooks/telescope_runs_calendar.rst:229-234`

**Issue:** The docstring accepts the one-way ratchet on the grounds that relabelling *to* web
"fabricates provenance rather than destroying it, requires a deliberate staff act, and is recorded
by Django's admin `LogEntry`". Two consequences that make the residual materially worse than that
framing are stated nowhere and covered by no test:

1. **It is a trapdoor with no admin-side exit.** The instant the relabel is saved, `obj.source ==
   WEB` makes `source` readonly, so the same staff user cannot undo their own mis-click through the
   admin at all. The runbook's own "The cost" paragraph (line 225-227) says correcting a web run's
   source "needs a shell or a data migration" — but it is written as if that only ever applies to
   genuinely-web rows, when in practice the most likely way to land there is an accidental
   selection in the `source` dropdown of a `legacy`/`csv_import` row.
2. **The CSV path cannot repair it either.** `import_campaign_csv.py:308-310` pops both `source` and
   `approval_status` for any row whose existing `source` is `WEB`, so re-importing the sheet that
   originally produced the row will not restore `csv_import`. The docstring cites this same carve-out
   as evidence of *parity*, without noting that it is also what removes the second repair route.
   A mis-clicked `APPROVED` row therefore reads permanently as "a human approved this public
   submission" — a fact that never happened — and `LogEntry.change_message` records only that
   `source` changed, not what it changed *from*.

Neither `SourceProvenanceLockTests` nor `SourceProvenanceTwoStepBypassTests` exercises the
non-web → web direction at all, so the behaviour the docstring describes as "accepted" is entirely
unpinned: a future refactor could change it silently in either direction.

**Fix:** if the residual stays accepted, make it honest and pinned. Add a test:

```python
def test_relabel_to_web_locks_the_row_and_cannot_be_undone(self) -> None:
    """Pins the accepted one-way ratchet: relabelling a non-web row to web locks `source`,
    and neither the admin nor a CSV re-import can put it back."""
    request = self._staff_request()
    form_class = self.admin_obj.get_form(request, obj=self.approved_legacy, change=True)
    data = model_to_dict(self.approved_legacy, exclude=['id'])
    data['source'] = CampaignRun.Source.WEB
    form_class(data=data, instance=self.approved_legacy).save()
    self.approved_legacy.refresh_from_db()
    self.assertEqual(self.approved_legacy.source, CampaignRun.Source.WEB)
    self.assertIn('source', self.admin_obj.get_readonly_fields(request, self.approved_legacy))
```

and extend the runbook's "What stays possible" paragraph with the two consequences above, so an
operator learns *before* the click that it cannot be undone in the admin or by re-import. If that
reads as too sharp an edge, the alternative is to also withhold `source` when
`obj.approval_status == APPROVED` regardless of source — which costs D-19 only the ability to
relabel already-approved backfill.

### WR-01 (carried forward, still open): Site-preservation guard silently discards a legitimately corrected `Site Code`

**File:** `solsys_code/management/commands/import_campaign_csv.py:328-331`

**Issue:** Unchanged since the last review. `preserve_site` (line 230-232) is true whenever
`site is None or site_resolution_failed`, which includes the case where the operator *corrected* the
sheet's `Site Code` to a new code that MPC does not know or that exceeds `_MAX_OBSCODE_LEN`. The run
then keeps its old `site` **and** its old `site_raw`, and the correction is dropped with no stderr
line, no `logger` call, and no summary counter. `insert_or_create_campaign_run()` compares only the
surviving keys in `fields`, so the row is reported as `unchanged` — indistinguishable from a row
where nothing was attempted. The comment at line 322-324 ("A CSV cell that DOES genuinely resolve
still wins") is true but says nothing about the operator being unable to tell which branch they got.

**Fix:** as previously proposed — emit a per-row diagnostic and a summary counter:

```python
if preserve_site:
    fields.pop('site', None)
    fields.pop('site_raw', None)
    fields.pop('site_needs_review', None)
    site_preserved_count += 1
    self.stderr.write(
        f'Row {row_num}: kept existing resolved site {existing.site_id} '
        f'(Site Code={site_raw!r} did not resolve); CSV site/site_raw discarded'
    )
```

and append `site_preserved: {site_preserved_count}` to the `Done.` line.

### WR-02 (carried forward, still open — characterisation corrected): Orphan placeholder `Observatory` rows are created and never linked

**File:** `solsys_code/management/commands/import_campaign_csv.py:194, 328-331`

**Issue:** `resolve_site(site_raw)` runs unconditionally at line 194 with the default
`create_placeholder=True`, *before* `existing` is even fetched (line 223), so a tier-3 placeholder
`Observatory` is fabricated for an unresolvable `Site Code` and the guard at line 328 then pops
`site` from `fields`, leaving the placeholder linked to nothing.

Correction to the previous review's wording: this does **not** accumulate on every re-import. On the
next run, `resolve_site()`'s tier 1 matches the existing orphan by obscode and returns
`(orphan, True)` (`campaign_utils.py:200-205`), so no second row is created. The accurate statement
is: **one permanent orphan per distinct unresolvable `Site Code` value**, created the first time
that value meets an already-sited run. It still satisfies `is_placeholder_observatory()`, still
enters the site-search suggestion pool, and still wins tier 1 for that obscode on every future
resolution — the pollution `CampaignRunDecisionView._resolve_site()`'s cleanup
(`campaign_views.py:756-774`) exists to prevent, except that cleanup only deletes a placeholder it
*replaces on a run*, and this one is on no run.

There is a second cost worth folding into the fix: reaching tier 3 requires a live MPC Obscodes API
call per unresolvable row (`campaign_utils.py:207-220`), and the guard throws the result away — so
every re-import pays a network round-trip per preserved row for a value that is discarded.

**Fix:** fetch `existing` before resolving, and skip placeholder creation when the row will be
preserved:

```python
existing = CampaignRun.objects.filter(**lookup).first()   # move the lookup build above this
site, site_resolution_failed = resolve_site(
    site_raw, create_placeholder=existing is None or existing.site_id is None
)
```

(The lookup no longer depends on anything computed from `site`, so it can be hoisted freely.)
Alternatively, delete the just-created orphan when the guard fires, reusing `_resolve_site()`'s
"no other CampaignRun still references it" guard.

### WR-05 (carried forward, still open): The repo-wide template-comment sweep stops scanning a file after the first unterminated `{#`

**File:** `solsys_code/tests/test_calendar_template.py:591-604`

**Issue:** Unchanged. When `content.find('#}', start + 2)` returns `-1`, the loop records the failure
and `break`s out of the whole file, so any further multi-line `{# ... #}` blocks later in that same
template are never examined. A single stray `{#` — inside a JS object literal, a CSS selector, or a
`{% verbatim %}` block — silently disables the guard for the rest of that file, which is exactly the
kind of content that makes the heuristic fire in the first place.

**Fix:** continue scanning past an unterminated marker instead of abandoning the file:

```python
if end == -1:
    line_no = content.count('\n', 0, start) + 1
    failures.append(f'{html_file}:{line_no}: unterminated "{{#" (no matching "#}}")')
    search_from = start + 2
    continue
```

and either skip `<script>`/`{% verbatim %}` regions or require the opening `{#` to be at the start
of a (possibly indented) line, matching how the real defect appeared.
