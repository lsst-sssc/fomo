## Decisions recorded by this plan

### Criterion 5 decision: a re-import may only overwrite the site fields when the CSV's own cell genuinely resolves

**The rule, in full.** When `import_campaign_csv` matches an existing `CampaignRun` on the
natural key, it drops `site`, `site_raw` and `site_needs_review` from the update when **both**
of these hold:

1. the existing row already has a resolved site (`existing.site_id is not None`), and
2. the CSV row's own `Site Code` cell did **not** genuinely resolve -- i.e. `resolve_site()`
   returned `site is None`, **or** it returned a site with `site_resolution_failed=True` (the
   tier-3 placeholder case, which `import_campaign_csv` can hit because it calls `resolve_site()`
   with its default `create_placeholder=True`).

The three fields are preserved as a unit, never individually, for the same reason the existing
WEB guard preserves `source` and `approval_status` together: keeping `site` while reverting
`site_raw` would leave the row's recorded provenance contradicting its resolved site, and
`repair_stale_campaign_run_sites` deliberately corrects `site_raw` on one known row (D-16b), so
`site_raw` is exactly as repairable as `site`.

**Why this rule and not "never overwrite a non-null site".** The blunter rule would also block a
genuine correction: an operator who fixes a wrong `Site Code` cell in the sheet and re-imports
expects the site to move. Under the chosen rule that still works -- the corrected cell resolves,
so the CSV wins. The only case the guard blocks is the one that produced the stale row in the
first place: an unresolvable cell trying to overwrite something better. This mirrors the shape of
the WEB carve-out (`import_campaign_csv.py:263-276`), which is narrow and states its reasoning at
the call site rather than blanket-freezing a field.

**Why this is the right reading of CANON-05's provenance intent.** `27-CONTEXT.md`'s D-16/D-16a/
D-16b treat site resolution as a *repair* path whose results are domain-authoritative: D-16b's
`site_raw='C52'` for the Swift row is described as "supplied by the project owner as domain
authority -- it is not inferred". A CSV cell that cannot resolve carries strictly less
information than a repaired row, so letting it win inverts the authority ordering the phase
established. D-17 already records that the repair "clears the flag the way it always does"; a
re-import that re-raises the flag undoes a decision, not a guess.

**Accepted cost.** A site can no longer be *cleared* through the CSV. Clearing now requires the
Django admin or a shell. The runbook must say so.

**Extension: a re-import never clears `telescope_class` either.** The importer computes
`telescope_class = derive_telescope_class(...) if site is None else ''` and writes it
unconditionally, so a re-import whose CSV cell resolves writes `''` over a non-blank class. That
directly contradicts `solsys_code/models.py:207-219`, which states the value is "NEVER cleared by
any writer once a site later resolves elsewhere for the same run", and which the user affirmed by
REJECTING code-review finding CR-01. This is one `fields.pop` at the same guard site, it upholds
an invariant the user has already ruled on, and leaving it out would make the runbook note this
plan writes incomplete. It is in scope. **It is not WR-02**: nothing here touches
`repair_stale_campaign_run_sites`, and no code added by this plan clears `telescope_class` --
this makes clearing *less* possible, not more.

**Summary-counter correction.** `site_needs_review_count` is currently incremented as soon as
`needs_review` is computed from the CSV cell, before the guard can decide whether the flag is
written. Under the new rule that would report a flag the command did not set. The increment moves
below the guard and fires only when `site_needs_review` is still present in `fields`.
