<objective>
The per-telescope stripe shipped in quick-260724-osc / quick-260724-tiz renders directly on top of
each classical-schedule chip's own `NEUTRAL_SLOT_COLOR` (#5a6268) fill. A pixel-sampled review of a
rendered calendar found every one of the 8 TELESCOPE_PALETTE colors fails the WCAG 1.4.11 non-text
3:1 minimum against that fill (measured 1.26–2.02:1). The palette's block comment claims it was
chosen "for against-gray-fill stripe contrast", but it was only ever validated against white.

The root cause is that one palette is being asked to serve two different backgrounds. The legend
chip sits on the page's white background; the stripe sits on the gray chip fill. No single hue can
clear 3:1 against both (see key_finding). This plan splits the one palette into two parallel
palettes — one per context — and fixes the stripe's remaining white-facing boundary with a thin
opaque edge line rather than a hue change.

Purpose: make both the stripe/fill boundary and the stripe/cell boundary genuinely perceivable, and
replace the "validated against white only" habit with a contrast gate that lives in the test suite
so this cannot silently regress a third time.

Output: a new TELESCOPE_STRIPE_PALETTE plus a `telescope_stripe_color` tag sharing one hashing
helper with `telescope_color`, a retuned TELESCOPE_PALETTE, a one-sided opaque edge on the stripe
pseudo-element in calendar.html, a `_contrast_ratio()` helper plus a WCAG audit test class, and
corrected docstrings/comments.

<key_finding>
**One palette cannot serve both backgrounds, and the planner verified that arithmetically rather
than assuming it.** Solving the WCAG contrast equations for the two backgrounds this palette is
currently asked to sit on:

- To clear 3:1 against **#ffffff** (the legend chip's background), a color's relative luminance must
  satisfy **L ≤ 0.30000**.
- To clear 3:1 against **#5a6268** (the classical chip fill, L = 0.11909), it must satisfy
  **L ≥ 0.45726** (lighter side) or **L ≤ 0.00636** (darker side).

The lighter band never intersects the white constraint. The darker band is effectively black-only:
the darkest fully-saturated sRGB primary, pure blue #0000ff, already sits at L = 0.0722 — more than
11x above that ceiling — so no set of 8 mutually distinguishable hues exists inside it. **No
8-color palette can clear 3:1 against both backgrounds simultaneously.**

That is precisely why this plan ships **two** palettes instead of retuning one. The usage sites were
confirmed by reading the template, not assumed:

- `.cal-legend-chip` (calendar.html:274 and :281) renders only on the page's white background. It is
  fed by `visible_classical_telescopes()`, which calls `telescope_color()` internally (line 296 of
  calendar_display_extras.py). This path keeps **TELESCOPE_PALETTE**, gated against white.
- `.cal-event-classical::before` (calendar.html:102-112) is `position: absolute; left: 0; top: 0;
  bottom: 0` inside the chip. Its **right** edge borders the chip's own `background-color`
  (NEUTRAL_SLOT_COLOR). This path gets a new **TELESCOPE_STRIPE_PALETTE**, gated against #5a6268.

The two palettes are parallel arrays sharing one hash function and one length, so a given telescope
name lands on the same index in both and therefore renders as the same hue family in legend and
stripe. They are not independently shuffled sets.

**The stripe's outer boundary needed re-derivation, and it is three sides, not one.** Because the
pseudo-element spans the full chip height (`top: 0; bottom: 0`), the sides facing *outside* the chip
are its **left, top and bottom** edges; only the **right** edge faces the gray fill. A pastel stripe
clears 3.45:1 against the fill on the right, but measures only ~1.8:1 against the white day cell on
the other three — which would leave the chip's rounded top-left and bottom-left corners visibly
bleeding into the cell background. So the outer boundary gets a 1px opaque dark edge
(`STRIPE_OUTER_EDGE_COLOR`, candidate #343a40 at **11.51:1** vs white) on left/top/bottom, and the
right edge gets none, because color choice already solved that side.

This same geometry resolves the secondary finding in the brief. The terminal status ring
(`rgba(160, 0, 0, 0.55)` from `status_border_css`, compositing to **#cb7373** over the white cell,
3.37:1 vs white) is painted immediately outside the chip's border box, so on a `[CANCELLED]` /
`[EXPIRED]` classical chip the ring's inner neighbour along the chip's left flank is exactly that
outer boundary. Against a bare pastel stripe the ring would measure **1.87:1**; against
`STRIPE_OUTER_EDGE_COLOR` it measures **3.42:1**. Same edge, same fix — Task 3 asserts it.

The current CSS carries a *partial* seam — `box-shadow: inset -1px 0 0 rgba(255, 255, 255, 0.55)` —
which is on the wrong edge (right, the inner one that no longer needs help), at 55% alpha so it
composites toward the stripe hue instead of reading as a line. That half-measure is what gets
replaced.
