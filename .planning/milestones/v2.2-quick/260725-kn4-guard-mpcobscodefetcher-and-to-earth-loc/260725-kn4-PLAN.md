<objective>
`MPCObscodeFetcher.to_observatory()` crashes with `TypeError: float() argument must be a string or a
real number, not 'NoneType'` for every space-based MPC obscode (250 HST, 258 Gaia, C51 NEOWISE, ...),
because `utils.py:124-127` unconditionally does `float(self.obs_data['longitude'])` and
`float(...['rhocosphi'])` / `float(...['rhosinphi'])`, all three of which the MPC API returns as
`null` for satellite sites. Verified live against the API for obscode 250.

The same class of bug exists one layer down: `Observatory.to_earth_location()` (`models.py:173`)
does `self.lon * u.deg` with no null check, which raises
`TypeError: unsupported operand type(s) for *: 'NoneType' and 'Unit'` for a coordinate-less site.
This path is genuinely reachable — `telescope_runs.py:279` calls it, and a satellite Observatory is
already attached as the `site` on a real CampaignRun in the dev database.

Purpose: make both layers handle a space-based site as a first-class, coordinate-less record rather
than a crash. `Observatory.lon`, `.lat` and `.altitude` are all already `null=True`, so a
position-less row is a valid model state — the code just never expected one.

Output: two guards, four test additions, and one corrected stale comment.

## Emergent consequence — read before executing

Fixing `to_observatory()` changes what `campaign_utils.resolve_site()` does for satellite obscodes,
**without changing a line of `campaign_utils.py`**. Today: Tier 2 calls `to_observatory()`, it raises
`TypeError`, `campaign_utils.py`'s WR-04 `except (KeyError, ValueError, TypeError)` swallows it, and
the code falls through to Tier 3, fabricating a `NEEDS REVIEW: 250` placeholder Observatory with
`needs_review=True`. After the fix: Tier 2 succeeds and returns a real Observatory named
`Hubble Space Telescope` with `observations_type=SATELLITE_OBSTYPE` and `needs_review=False`.

This is an improvement, not a regression, and it is in scope:

- It requires no edit to `campaign_utils.py` or to gap-analysis behavior — the out-of-scope boundary
  is respected. The WR-04 `except` clause stays exactly as-is and still guards genuinely malformed
  responses.
- It replaces a fabricated placeholder needing manual staff review with a correctly-identified,
  correctly-typed site.
- `campaign_views._project_calendar_event()` (line 437) already has a `SATELLITE_OBSTYPE` branch that
  produces a whole-day-span CalendarEvent and short-circuits *before* ever calling `sun_event()`. So
  the fix actually unblocks the satellite calendar-projection path Phase 25 built, rather than
  routing satellites into the ground `sun_event()` path.

The existing satellite tests in `test_campaign_approval.py`
(`test_approve_single_night_space_run_creates_midnight_utc_placeholder_event`,
`test_approve_range_run_space_site_creates_single_whole_day_span_event`) create their satellite
`Observatory` locally, so they hit Tier 1 and are unaffected. Task 3 adds explicit coverage for the
new Tier-2 behavior and corrects the now-false comment in `campaign_views.py` that documents the old
`TypeError` fall-through.

## Two decisions this plan makes deliberately

**1. A satellite record gets `altitude = None`, not the model default `0.0`.**
`altitude=0.0` is not "unknown" — it is the concrete, false claim "this site sits on the WGS84
ellipsoid at sea level". `None` states the truth and is consistent with `lon`/`lat` being `None`; the
field is `null=True`, so it is a legal value. Audited every reader of `.altitude`: `models.py:133`
(`to_parallax_constants`) and `models.py:150` (`to_geocentric`) already guard with
`if self.lat and self.lon and self.altitude:` (truthiness — so `0.0` and `None` behave identically);
`models.py:165` (`to_geodetic`) would raise on `radians(None)` just as it already would on
`radians(self.lon)` with `lon=None`, so it is no worse off; `telescope_runs.py:283`
(`horizon_dip(site.altitude)`) is unreachable for a position-less site because
`to_earth_location()` on line 279 now raises first; `forms.py:28` filters
`Observatory.objects.filter(altitude__gt=0)`, which excludes NULL rows in SQL exactly as it already
excluded `0.0` rows — the ephemeris-form dropdown keeps hiding satellites either way.

**2. `to_earth_location()` raises `ValueError`, it does not return `None`.**
Returning `None` would defer the crash into `_find_crossing()`/astropy with a far more confusing
traceback, as the task brief notes. `ValueError` specifically (rather than a new custom exception
class) because it makes the guard free for every existing caller — verified by reading all three:

| Caller | Existing handling of `ValueError` from `sun_event()` | Reaction after this fix |
|--------|------------------------------------------------------|--------------------------|
| `campaign_gap.observable_dates()` (`campaign_gap.py:109-112`) | catches, logs debug, skips the date as unknown (D-03) | satellite site contributes unknown dates instead of crashing gap analysis |
| `campaign_views._project_calendar_event()` (`campaign_views.py:473-481`) | catches, logs, re-raises (CR-01); `approve()` catches it at the call site so approval still succeeds without an event | unchanged; and satellites short-circuit at line 437 before reaching here anyway |
| `load_telescope_runs.handle()` (`load_telescope_runs.py:223`) | `except (ValueError, Observatory.DoesNotExist)` → stderr message + per-line skip | a satellite in a run file is reported and skipped, not a traceback |

`sun_event()` itself already raises `ValueError` for the directly analogous "this site is not
configured for this computation" case (blank `timezone`, `telescope_runs.py:273-277`) — same shape,
same message style. So: **no caller needs to change**, and the new message must be written in the
same actionable style as that existing timezone one.
