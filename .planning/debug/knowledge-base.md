## start-time-idempotency-key — load_telescope_runs silently duplicated CalendarEvents on re-ingest because its lookup key required exact equality on a drift-prone computed sunset time
- **Date:** 2026-07-08
- **Error patterns:** load_telescope_runs, insert_or_create_calendar_event, get_or_create, CalendarEvent, duplicate, idempotency, start_time, sun_event, IERS, Earth-orientation, UT1-UTC, AltAz, astropy, exact-match lookup key, telescope_runs, SYNC-04, silent duplicate creation
- **Root cause:** The create-or-update lookup key {telescope, instrument, start_time} used exact datetime equality on start_time, a value computed fresh each run by telescope_runs.sun_event(). sun_event() is deterministic within a process but its output is a direct function of astropy's IERS Earth-orientation data (UT1-UTC / polar motion) applied in the get_sun/AltAz transform, which astropy refreshes over time — so independent ingests of the identical (site, night) days apart produced start_time values ~2s apart, defeating get_or_create's exact match and creating near-duplicate rows.
- **Fix:** Added an optional `start_time_tolerance` kwarg to the shared insert_or_create_calendar_event() helper; when set (only load_telescope_runs passes it, at 5 minutes) it matches an existing event whose start_time is within a +/- window (start_time__range, a proximity window rather than minute-bucketing which would still split events across a bucket boundary) scoped by the other lookup keys, leaving the stored start_time pinned to avoid churn. Default None keeps exact get_or_create behaviour, so URL-keyed sync callers (sync_lco/sync_gemini, lookup {'url': ...}) are unaffected.
- **Files changed:** solsys_code/calendar_utils.py, solsys_code/management/commands/load_telescope_runs.py, solsys_code/tests/test_calendar_utils.py, solsys_code/tests/test_load_telescope_runs.py, docs/notebooks/pre_executed/load_telescope_runs_demo.ipynb

## site-search-mpc-no-match — site-search widget returned "No matches" for real MPC codes (G96/Mt. Lemmon) because list-shaped old_names silently discarded the entire MPC candidate pool
- **Date:** 2026-07-16
- **Error patterns:** site-search, site_selection, build_site_candidates, _flatten_mpc_candidates, MPCObscodeFetcher, query_all, old_names, list, TypeError, unhashable type: 'list', dict membership, candidate pool, No matches for this search, mpc_obscode_candidates, FileBasedCache, cache poisoning, degraded fallback, TTL, approval queue, Sites Needing Review, CampaignRun, G96, Mt. Lemmon Survey
- **Root cause:** _flatten_mpc_candidates() treated each MPC record's `old_names` as a string, but the live MPC bulk obscodes API (MPCObscodeFetcher.query_all()) returns it as a JSON **list** for 60 of 2712 records (e.g. G96 -> ['Mt. Lemmon Survey']; 0 are strings). The dict-membership test `if candidate and candidate not in mapping:` used the list as an operand, raising `TypeError: unhashable type: 'list'`. build_site_candidates()'s broad `except (RequestException, ValueError, KeyError, TypeError, AttributeError)` swallowed it and fell back to a local-only 23-string pool, discarding all 2712 MPC candidates — then cached that degraded pool under 'mpc_obscode_candidates' for 24h (FileBasedCache shared with runserver), so any MPC-only obscode never surfaced in the widget.
- **Fix:** New _old_name_strings() helper normalizes old_names (list | str | None/missing) into a flat list of non-empty strings; _flatten_mpc_candidates() folds each prior name in as its own candidate, so a list-valued old_names no longer reaches a dict key/membership op. Degraded (MPC-failed) fallback pool now cached for only MPC_CANDIDATE_FALLBACK_TTL_SECONDS (60s) instead of 24h, so a transient MPC outage can't poison search for a day; full pool still cached 24h. 4 regression tests added. RELATED LATENT BUG (same root-cause family, separate session site-resolve-list-old-names): to_observatory() assigns list-shaped old_names to Observatory.old_names (a CharField) on the tier-2 resolve-and-create path.
- **Files changed:** solsys_code/campaign_utils.py, solsys_code/tests/test_campaign_approval.py

## site-resolve-list-old-names — placeholder-replacement "Could not resolve that site" because the widget's combined "display (obscode)" click value never round-tripped through the candidate pool
- **Date:** 2026-07-16
- **Error patterns:** Could not resolve that site, site_selection, _resolve_site, resolve_site, build_site_candidates, selection_to_obscode, oversized obscode, _MAX_OBSCODE_LEN, site_search_results.html, onclick, display (obscode), placeholder Observatory, NEEDS REVIEW, approval queue, Resolve action, approve action
- **Root cause:** The site-search suggestion fragment's onclick handler writes the COMBINED string `f'{display} ({obscode})'` (e.g. 'Lowell Discovery Telescope (G37)') into the `site_selection` input on click. Both `CampaignRunDecisionView._resolve_site()` and its approve-path sibling mapped that selection back to an obscode via `build_site_candidates().get(selection, selection)`, but the pool is keyed only on bare display strings and bare obscodes — never the combined form. The exact lookup missed, the 32-char combined string passed through unchanged, and `resolve_site()` rejected it as an oversized obscode (`len > _MAX_OBSCODE_LEN=4`), returning `(None, True)` — surfaced as the generic "Could not resolve that site" error for a genuine MPC candidate the user had just selected from the list. Initially misdiagnosed as the same `old_names`-list issue as the G96 bug above; disconfirmed — the single-code `query()` endpoint returns `old_names=None` for G37, not a list, and `to_observatory()` succeeds fine.
- **Fix:** New `selection_to_obscode()` helper in `campaign_utils.py`: exact pool hit -> else parse the widget's trailing `' (obscode)'` token (preferring a pool hit on the leading display part) -> else passthrough. Both call sites (`_resolve_site()` and the approve path) now use it instead of the raw `build_site_candidates().get(selection, selection)`. Backward-compatible with bare obscodes/display strings.
- **Files changed:** solsys_code/campaign_utils.py, solsys_code/campaign_views.py, solsys_code/tests/test_campaign_approval.py

## site-search-degraded-pool-recurrence — site-search "No matches" regression caused by the test suite and the dev runserver sharing one FileBasedCache key
- **Date:** 2026-07-16
- **Error patterns:** No matches for this search, mpc_obscode_candidates, FileBasedCache, shared cache, cache.clear(), test isolation, override_settings, LocMemCache, cross-contamination, warmed pool wiped, cold rebuild, degraded fallback, name_utf8, short_name
- **Root cause:** `settings.CACHES` is a `FileBasedCache` under `/tmp`; Django does not isolate that cache between the test runner process and the dev `runserver` process — both read/write the same `mpc_obscode_candidates` key. Running the site-resolve-list-old-names bug's verification suite (which calls `cache.clear()` in setup) immediately before a browser test wiped the runserver's warmed ~5,700-entry MPC pool, forcing a cold rebuild that briefly served the tiny local-only fallback pool (no G37) — reproducing the exact "No matches" symptom the G96 fix had already resolved, for terms that had worked minutes earlier. The "another live-MPC record shape throws" hypothesis (same class as the G96 bug) was checked and disconfirmed — `build_site_candidates()` rebuilds a clean full pool from live data with no exception.
- **Fix:** Cache-touching test classes in `test_campaign_approval.py` and `test_campaign_site_search.py` now use `@override_settings(CACHES=<LocMemCache>)` so running tests can never again evict the shared runserver cache. Also hardened `_flatten_mpc_candidates()` defensively (new `_candidate_str()` helper) so `name_utf8`/`short_name` degrade per-field instead of dropping the whole pool if either ever comes back non-string-shaped in the future (same failure family as `old_names`, not yet observed for these two fields in live data).
- **Files changed:** solsys_code/campaign_utils.py, solsys_code/tests/test_campaign_approval.py, solsys_code/tests/test_campaign_site_search.py

## duplicate-mpc-candidate-match — site-search suggestion dropdown showed the same site twice because whitespace-variant candidate strings survived exact-string dedup
- **Date:** 2026-07-16
- **Error patterns:** duplicate suggestion, duplicate candidate, site-search, dropdown, Nordic Optical Telescope, name_utf8, old_names, whitespace, candidate not in mapping, exact-string dedup, visual duplicate, build_site_candidates, _flatten_mpc_candidates, _local_observatory_candidates
- **Root cause:** A single MPC record can carry two byte-distinct candidate strings that render identically once whitespace collapses in HTML — e.g. Z23's `name_utf8` is `'Nordic Optical Telescope, La Palma'` (1 space) but its `old_names` entry is the same text with 5 spaces after the comma. The existing pool-build dedup (`if candidate and candidate not in mapping`) is exact-byte, so both survive as separate keys, both substring-match the same query, and the suggestion dropdown shows the identical text twice. Live audit found 32 of 2,712 MPC records affected (mostly trailing-space `old_names` variants) — systemic, not Z23-specific.
- **Fix:** New `_normalize_candidate()` helper (`' '.join(value.split())` — collapses whitespace runs, matching how HTML renders text) applied to each candidate string BEFORE the first-seen dedup check, in both `_flatten_mpc_candidates()` (MPC pool) and `_local_observatory_candidates()` (local pool), so visual-duplicate keys collapse to one at the pool's source rather than needing per-consumer fixes.
- **Files changed:** solsys_code/campaign_utils.py, solsys_code/tests/test_campaign_site_search.py

## negative-altitude-horizon-dip — resolving a real near-sea-level MPC site crashed sun-event projection because horizon_dip() rejected its slightly-negative parallax-derived altitude
- **Date:** 2026-07-16
- **Error patterns:** altitude_m must be a non-negative number, horizon_dip, ValueError, sun_event, _project_calendar_event, _resolve_site, negative altitude, below sea level, from_parallax_constants, rhocosphi, rhosinphi, parallax constants, obscode 434, S. Benedetto Po, Benedetto, gc2gde, erfa, Sites Needing Review, calendar projection, dip
- **Root cause:** `horizon_dip()` (telescope_runs.py) raised `ValueError('altitude_m must be a non-negative number')` for any negative altitude, but `Observatory.from_parallax_constants()` legitimately produces a small NEGATIVE geodetic height (-18.834226888866702 m) for the real near-sea-level MPC site obscode 434 "S. Benedetto Po" (~19 m real elevation, lat 45.052, lon 10.92). This is NOT a conversion bug: MPC publishes parallax constants to only 5 decimal places (1 LSB = _r*1e-5 = 63.78 m of altitude), so a genuine near-sea-level site cannot be distinguished from a slightly-below-ellipsoid one — round-tripping real altitudes of 0/10/19/24 m all reproduce the published (0.70765, 0.70419) constants and convert back to -18.83 m. When `_resolve_site()` replaced the placeholder Observatory with this real record and ran `_project_calendar_event()` -> `sun_event(kind='sun')` -> `horizon_dip(site.altitude)`, the guard raised. That raise was CORRECTLY caught by `_resolve_site()`'s non-reverting `try/except Exception` (CR-01) and logged via `logger.exception` (the traceback in the runserver log was that logging, NOT an unhandled 500), but because every retry hit the same guard the site could never be projected — permanently stuck in Sites Needing Review.
- **Fix:** Relaxed `horizon_dip()` to return a 0 dip for any altitude <= 0 instead of raising. Physically correct: the Nautical Almanac dip model `1.76'*sqrt(h) = sqrt(2h/R)` only describes horizon depression for an observer ELEVATED above the reference surface; at/below sea level there is no elevated horizon to depress, so dip = 0 (the discarded sub-arcminute correction for a near-sea-level site is far inside the <=2 min sun-event tolerance). The `None` guard is retained (an unset altitude is a genuine data error, not a physical location). Updated the two Stage-1 tests that encoded the reject-negative contract and added an end-to-end `sun_event` regression for a below-sea-level site.
- **Files changed:** solsys_code/telescope_runs.py, solsys_code/tests/test_telescope_runs.py

## range-window-calendar-event — approved, site-resolved range-window CampaignRuns never projected a CalendarEvent because a single equality sub-clause in the projection guard forced an early return
- **Date:** 2026-07-17 (diagnosed) / 2026-07-18 (resolved, Phase 25)
- **Error patterns:** _project_calendar_event, window_start, window_end, range-window CampaignRun, zero-event, CalendarEvent count 0, silent-by-design, Gemini FT-115, GS-2026A-FT-115, awarded telescope time, ground branch, satellite branch, sun_event, dip-corrected, backfill, TestGeminiFtScenario, D-06 behavior preservation
- **Root cause:** `_project_calendar_event()`'s guard included `run.window_start == run.window_end`, so any run whose window was a genuine date range (not a single concrete night) returned False before the projection branch ever ran — confirmed for the real GS-2026A-FT-115 Gemini South run (CampaignRun pk=34), approved and site-resolved yet with zero CalendarEvents. Not a model limitation (CalendarEvent.start_time/end_time are plain non-nullable DateTimeFields with no inter-field constraint) and not an intentional product rule — traced to a Phase 19 D-06 behavior-preservation choice that deliberately deferred range projection as out-of-scope, never revisited by Phases 20-23. A secondary finding: the ground branch (the real Gemini I11 OPTICAL case) computed both event timestamps from a single `sun_event(window_start)` call and never read `window_end`, so a bare guard flip alone would have mislabelled a multi-day allocation as its first night only.
- **Fix:** Phase 25 dropped the equality sub-clause (kept both `window_start`/`window_end` non-null), gave the ground branch real per-night dip-corrected date-math (one CalendarEvent per night, per-night title/description synced by `_set_run_status()`), kept the satellite branch's existing whole-day span, added a window-context title suffix via a shared title helper, and added a one-off `backfill_range_calendar_events` command to catch already-approved runs (including the real pk=34 case) that predate the fix.
- **Files changed:** solsys_code/campaign_views.py, solsys_code/tests/test_campaign_approval.py, solsys_code/management/commands/backfill_range_calendar_events.py (new), solsys_code/tests/test_backfill_range_calendar_events.py (new)
- **Full diagnosis:** .planning/debug/resolved/range-window-calendar-event.md

## gemini-vs-soar-facility-scope — planning treated Gemini as a third live queue facility, but tomtoolkit's GEMFacility is submit-only; SOAR is the real third facility and was already handled inside the LCO sync path
- **Date:** 2026-09-02 (diagnosed) / 2026-09-11 (resolved, by v2.4 re-scope)
- **Error patterns:** GEMFacility, get_observation_status stub, submit-only facility, no read path, Gemini queue visibility, sync_gemini_observation_calendar, SOARFacility(LCOFacility), observe.lco.global, ocs.py get_observation_status, facility__in=['LCO', 'SOAR'], CampaignRun.Source, SOAR_QUEUE, GEMINI_QUEUE, three-adapter framing, archived requirements, provenance loss, out-of-scope table
- **Root cause:** AND-gate of three conditions. (1) Library reality: `GEMFacility` (tom_observations/facilities/gemini.py) has exactly one outbound call, `submit_observation()`; `get_observation_status()` returns `{'state': ''}` unconditionally, `get_observation_url()` returns `''`, `data_products()`/`_archive_frames()` return `[]` — there is no Gemini read path at all, so `sync_gemini_observation_calendar` only replays FOMO's own outbound ToO submissions from the local DB (zero HTTP calls, GEMFacility never imported). `SOARFacility` subclasses `LCOFacility`, uses the LCO API key and portal, and inherits the real live `get_observation_status()` (ocs.py). (2) Vocabulary: `CampaignRun.Source` minted `GEMINI_QUEUE` and no `SOAR_QUEUE` in v2.2, baking the wrong three-facility framing into the model layer before v2.3 planning — even though `sync_lco_observation_calendar` had treated LCO and SOAR as distinct facilities since v1.3. (3) Provenance loss: the stub was a KNOWN limitation recorded in archived `v1.5-REQUIREMENTS.md` (Out of Scope: "Live Gemini ODB status polling") and `10-CONTEXT.md`, but never carried into PROJECT.md's active limitations or v2.3's REQUIREMENTS/ROADMAP, so Phase 31 planned against a stale facility inventory. Phase 31's own probe measured `gemini_queue=0` and read it as missing test data rather than an unreachable facility.
- **Fix:** No code fix from this session (diagnose-only). The v2.3 roadmap was superseded; v2.4 was scoped to LCO/SOAR from the outset, Phase 34 shipped the LCO/SOAR observation projector and retired the LCO sync command while leaving the `GEM:` calendar namespace untouched, and Phase 32 added `CampaignRun.Source.SOAR_QUEUE` (models.py, D-01 in 32-CONTEXT.md). Lesson for future planning: when a facility class is cited as an ingest source, check that it has a *read* path (not just submit) before building an adapter or requirement on it — and check archived milestones' Out-of-Scope tables for limitations that were never promoted to PROJECT.md.
- **Files changed:** none (planning artifacts only)
- **Full diagnosis:** .planning/debug/resolved/gemini-vs-soar-facility-scope.md

## 34-updatestatus-receiver-attributeerror — the post_save projector receiver crashed on every real `updatestatus` save because the LCO portal hands back ISO strings, not datetimes, and Django never coerces the in-memory attribute
- **Date:** 2026-09-11 (diagnosed) / 2026-09-14 (resolved, Phase 34 G-34-2)
- **Error patterns:** AttributeError, 'str' object has no attribute 'strftime', unprojectable observation_id, post_save receiver, updatestatus, update_observation_status, get_observation_status, OCSFacility, ocs.py:1570, BaseObservationFacility, facility.py:563, record_time_window, event_fields_for, stage_for, observation_projector, calendar_utils, scheduled_start, scheduled_end, current_block['start'], portal ISO string, ISO 8601, trailing Z, DateTimeField no coercion on assignment, in-memory instance vs DB-fetched, stale CalendarEvent, receiver never narrows, sweep passes but receiver fails, project_observation_calendar updated: 33, SCHED-06, UAT Test 4, TRIG-02, test fake fidelity
- **Root cause(s):** AND-gate of three conditions, none of which is a bug on its own. (1) **data** — `OCSFacility.get_observation_status()` (tomtoolkit 3.0.1, `tom_observations/facilities/ocs.py:1570`) returns the portal's raw ISO strings for `scheduled_start`/`scheduled_end` (straight from `current_block['start']`), not `datetime` objects; (2) **environment** — `BaseObservationFacility.update_observation_status()` (`facility.py:563`) assigns those strings onto the `ObservationRecord` and calls `save()`, and Django's `DateTimeField` coerces on write-to-DB but *not* on attribute assignment, so `post_save` fires with `record.scheduled_start` still a `str`; (3) **code** — `record_time_window()` (`solsys_code/calendar_utils.py`) returned those attributes unchanged and `event_fields_for()` (`observation_projector.py:291`) called `.strftime()` on them, raising. `project_record()` correctly caught it (TRIG-02, receivers never raise), logged `unprojectable`, and left the CalendarEvent stale — so `updatestatus` still reported "Update completed successfully" while narrowing nothing. The sweep path re-fetches from the DB (real `DateTimeField` values) and so never saw it, which is why `project_observation_calendar` and all 296 tests were green while the real path failed on *every* record.
- **Fix:** Added `calendar_utils.coerce_schedule_datetime()` — normalizes `str`/`datetime`/`None` to an aware UTC datetime (handles `Z`, `+00:00`, non-UTC offsets, naive values) and **raises** rather than degrading to `None` on an unusable value, so a bad value surfaces as a visible D-13 `unprojectable` record instead of an event drawn over the wrong window. Routed both `record_time_window()` branches and `event_fields_for()`'s 'inconsistent' branch through it, so a post_save instance holding portal strings now derives an identical window to a DB-fetched one. Rewrote the signals test to feed the portal's real ISO-string contract, keeping a datetime case alongside it. Verified by revert test (restoring the raw-attribute read reproduces the exact AttributeError and fails exactly 2 targeted tests), 1239+40 tests green, ruff/ruff-format clean, and a human overnight `updatestatus`-only run that narrowed all 33 previously-stale LCO events with no sweep.
- **Files changed:** solsys_code/calendar_utils.py, solsys_code/observation_projector.py, solsys_code/tests/test_observation_projector_signals.py, solsys_code/tests/test_calendar_utils.py, docs/notebooks/pre_executed/project_observation_calendar_demo.ipynb
- **Why not caught:** The receiver's own unit test (`test_updatestatus_narrows_the_event_with_no_command_run`) existed, ran, and passed — but its fake `get_observation_status` returned `datetime` objects instead of the ISO strings the real facility returns. It asserted the right *behaviour* against the wrong *contract*. Lint and type hints could not help either: the facility status dict is untyped `dict[str, Any]` at the library boundary, so nothing declared those values were strings. A test-fake fidelity gap, not a missing test.
- **Recurrence guard:** (1) contract-faithful regression test `solsys_code/tests/test_observation_projector_signals.py:TestUpdateObservationStatusPath.test_updatestatus_narrows_the_event_with_no_command_run`, which now feeds `block_start.isoformat().replace('+00:00', 'Z')` byte-identically to the portal, with `test_updatestatus_with_datetime_valued_facility_still_narrows_the_event` retained as the datetime case (revert test proved the pair bites); (2) fail-loud assertion — `coerce_schedule_datetime()` (`solsys_code/calendar_utils.py:460`) raises on unusable input rather than returning `None`; (3) boundary-neighbour coverage at `solsys_code/tests/test_calendar_utils.py:TestCoerceScheduleDatetime` pinning the whole equivalence class. **Generalizable rule:** when a tomtoolkit facility method's return value is assigned onto a model instance and read back *without* a DB round-trip, verify the library's real return types before trusting the field's declared type — and fake it in tests exactly as the library returns it, not as the model declares it.
- **Full diagnosis:** .planning/debug/resolved/34-updatestatus-receiver-attributeerror.md
